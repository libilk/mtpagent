# 方向二:个性化学习教练 Agent — 方向设计文档

> 状态:**方向待确认**(本文只定方向,不写实现)
> 定位:作品集项目,面向 Agent / 后端工程师岗位

---

## 1. 一句话场景

> **Agent 常驻跟踪你的学习行为,构建"学习者画像",用知识图谱规划路径,在你快要忘记之前主动推复习。**

不是"一个能回答问题的题库",而是**一个会持续认识你的教练**。

---

## 2. 为什么是这 8 个功能(反 feature-soup 论证)

判据:**如果去掉这个功能,场景还成立吗?** 成立的话它就是装饰品。

| 功能 | 去掉它会怎样 | 结论 |
|---|---|---|
| **用户画像** | 退化成普通题库 —— 所有人收到同样的题,个性化消失 | **刚需** |
| **GraphRAG** | 无法回答"他为什么学不会 X"。只能推荐"和 X 相关的东西",推不出"你缺的前置知识是 Y" | **刚需** |
| **常驻 loop** | 遗忘是**随时间发生**的。没有常驻循环,就无法"在遗忘前"提醒,退化成"用户来查才有反馈" | **刚需** |
| **消息队列** | 答题事件、定时扫描、题目生成三种负载混在请求路径里,互相阻塞 | **刚需** |
| **FastAPI** | 没有入口,无法演示 | **刚需** |
| **工作流** | "批改 → 更新画像 → 查缺口 → 规划 → 出题 → 推送"是多步有依赖的流程,散落在各处就不可测、不可恢复 | **刚需** |
| **异步** | LLM 调用、图查询全 IO 密集,同步串行会让单次响应不可接受 | **刚需** |
| **WebSocket** | 主动推送需要长连接 | 加分 |

**关键点:GraphRAG 在这里不是装饰。** 下面是三个真实的图查询,全是多跳:

```
Q1: "学 X 之前需要先掌握什么?"
    X ──(prerequisite_of)逆──► [P1, P2] ──逆──► [P1a, P1b]     ← 2 跳

Q2: "他为什么学不会 X?"                                        ← 根因定位
    X 的前置节点 ∩ 他掌握度 < 0.4 的节点 = 真正的缺口

Q3: "下一步该学什么?"                                          ← 路径规划
    目标 Z 的前置闭包 ∩ 已掌握 = 可推进的节点
```

扁平向量检索**做不到**这些 —— 它只能说"X 和 Y 语义相似",说不了"Y 是 X 的前置"。

## 3. 核心概念设计(这是项目的灵魂)

### 3.1 学习者画像 / Learner Profile

这是整个系统的状态核心。建议包含四层:

| 维度 | 内容 | 更新方式 |
|---|---|---|
| **掌握度** | 每个知识点 0~1 的熟练度 | **BKT**(贝叶斯知识追踪):经典 4 参数模型,`P(学会|答对)` 增量更新。可解释,能讲原理 |
| **记忆强度** | 每个知识点"现在还记得的概率" | **FSRS**(Anki 用的现代间隔重复算法):建模 difficulty / stability / retrievability,输出**回忆概率** |
| **易错模式** | 错误类型聚类:概念混淆 / 计算失误 / 条件遗漏 | 错题文本 → LLM 打标签 → 聚类 |
| **偏好与目标** | 例题派 vs 理论派;目标岗位/考试;每日可用时长 | 显式收集 + 行为隐式推断 |

> **为什么选 BKT + FSRS 而不是"让 LLM 记住"?**
> 因为这两个是**可测量的数学模型**,有明确的输入输出,能被评测(见 §7)。
> "让 LLM 维护一个 JSON 画像"听起来酷,但你无法回答"画像准不准"。
**可评测性是这个项目的护城河。**

### 3.2 知识图谱 / Knowledge Graph

```
节点:KnowledgePoint(知识点)
      {id, name, subject, difficulty, externals: {教材锚点, 题库标签}}

边:
  prerequisite_of   ★核心。X 是 Y 的前置。决定所有多跳查询
  related_to        弱相关,用于横向推荐
  part_of           属于某个主题/章节
  assessed_by       知识点 ←→ 题目
  explained_by      知识点 ←→ 教材段落
```

**为什么图的构建是这个项目最难也最有价值的部分:**
- 公开数据里,题目标签多、**前置依赖关系少**
- 所以要做:**LLM 抽取候选依赖 → 人工/规则校验 → 环检测**(前置关系必须是 DAG,有环就崩了)
- 这一段能讲的东西极多:实体消歧、关系抽取、**拓扑校验**、稠密子图

### 3.3 常驻循环 / Agent Loop

**两种触发,缺一不可:**

| 类型 | 触发源 | 动作 |
|---|---|---|
| **事件驱动** | 用户答题 → MQ | 更新掌握度 → 检测前置缺口 → 规划下一步 → 异步出题 |
| **时间驱动** | 定时器(如每小时)→ MQ | FSRS 扫描 → 找出"即将遗忘"的知识点 → 生成复习任务 → 推送 |

**这是"常驻 Agent"和"请求-响应 Agent"的本质区别:** 后者只在你问的时候工作,前者在做你**没问但它认为该做**的事。

## 4. 架构

```
┌──────────────────────────────────────────────────────┐
│ FastAPI                                                │
│   POST /answer        提交答题                          │
│   GET  /profile       查看学习者画像                     │
│   GET  /plan          今日学习计划                       │
│   GET  /graph/{id}    查知识点及其前置链(演示 GraphRAG)  │
│   WS   /ws            实时推送(复习提醒 / 新题)          │
└───────────────────────┬──────────────────────────────┘
                        │ publish(event)
                        ▼
┌──────────────────────────────────────────────────────┐
│ Redis Stream  (消息队列)                                │
│   learn.answer        答题事件                          │
│   learn.tick          定时扫描触发                       │
│   learn.generate      异步生成题目(慢任务)               │
│   learn.notify        推送任务                          │
│   *.dlq               死信队列                          │
└───────────────────────┬──────────────────────────────┘
                        │ consume
                        ▼
┌──────────────────────────────────────────────────────┐
│ Worker Pool (asyncio)                                  │
│                                                        │
│  ① 画像 worker        判分 → BKT 更新 → FSRS 重置       │
│  ② 规划 worker ★      画像 + 图谱 → 多跳遍历 → 建议      │
│  ③ 遗忘 worker(定时)  FSRS 扫描 → 到期集合 → 生成任务    │
│  ④ 出题 worker(慢)    LLM 生成变式题 / 题库检索         │
└──────┬──────────────────┬──────────────────┬──────────┘
       │                  │                  │
       ▼                  ▼                  ▼
┌─────────────┐  ┌──────────────┐  ┌─────────────────┐
│ 图库 (Kuzu)  │  │ 向量 (Chroma) │  │ 画像 (SQLite)    │
│ 前置依赖关系  │  │ 题/教材语义   │  │ 掌握度/记忆/错题  │
└─────────────┘  └──────────────┘  └─────────────────┘
```

**分层职责:**
- **FastAPI** —— 只做校验 + 入队 + 查询,**不含任何 LLM 调用**(否则又被阻塞)
- **Redis Stream** —— 解耦、削峰、重试、死信
- **Worker** —— 真正的 Agent 逻辑,可独立伸缩
- **存储** —— 图、向量、画像分开,各用各的最优结构

## 5. 工作流

用 **LangGraph** 编排一次答题的完整流程(而不是手写拓扑排序——上一个项目的教训):

```
[提交答案]
    │
    ▼
[1] 判分           规则匹配 / LLM 判主观题
    │
    ▼
[2] 更新掌握度      BKT: P(known) 增量更新
    │
    ▼
[3] 重置记忆强度     FSRS: 重新计算 stability
    │
    ▼
[4] 缺口检测 ★      GraphRAG 多跳:该知识点的前置闭包
    │                ∩ 掌握度 < 0.4 → 缺口集合
    ├── 有缺口 ──► [4a] 生成补救路径(回到前置节点)
    │
    └── 无缺口 ──► [4b] 沿图谱推进到下一节点
    │
    ▼
[5] 规划今日计划     在目标路径上取 top-k
    │
    ▼
[6] 异步出题         publish(learn.generate)  ← 慢,不阻塞
    │
    ▼
[7] 推送            WS 推给前端
```

**为什么必须用 LangGraph 而不是自己写:**
- **checkpointer** —— 第 4 步崩了能从第 3 步恢复,不用重跑 LLM。长流程刚需
- **human-in-the-loop** —— 可以让用户确认"是否接受补救路径"
- 上一个项目手写 orchestrator 的教训:自己实现持久化/重试/恢复**做不对**

## 6. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| Web | **FastAPI** + WebSocket | 原生 async,和 worker 的 asyncio 同构 |
| MQ | **Redis Stream** | 项目已有 Redis 经验,不引入新中间件。比 Kafka 轻 |
| 图库 | **Kuzu**(嵌入式) 或 Neo4j | Kuzu 零运维,像 SQLite;需要可视化时再上 Neo4j |
| 向量 | **Chroma** | 已有经验,直接复用 |
| 画像 | **SQLite** → 后期 Postgres | 结构化数据,不需要图 |
| 工作流 | **LangGraph** | checkpointer + HITL,现代 agent 框架的加分项 |
| 掌握度 | **BKT** | 经典,4 参数,可解释 |
| 遗忘 | **FSRS**(fsrs4anki 开源实现) | Anki 在用,有现成 Python 库 |
| 异步 | **asyncio + asyncpg/redis-py** | worker 全异步 |

**关于 GraphRAG 的重要决策:不要用 Microsoft GraphRAG。**
它用 LLM 抽全图,又慢又贵且黑盒。**自己写"实体/关系抽取 → 图存储 → 遍历 → 结合向量召回"更能讲清原理**,面试被追问时也答得上。

## 7. 数据从哪来

| 需要 | 来源 | 难点 |
|---|---|---|
| 知识点清单 | 公开教学大纲:CS 课程体系、Khan Academy 知识树、MIT OCW | 容易 |
| **前置依赖关系** | **公开数据几乎没有** → LLM 从教材/大纲抽取 + 校验 | **★最大工作量** |
| 题目 | LeetCode / 公开题库 / LLM 生成变式 | 中等 |
| 教材段落 | 公开教材 / 技术文档 | 容易 |
| 答题记录(用于评测) | **需自己造**:模拟学生 or 小规模真人试用 | 中等 |

**建议第一版只做 30~50 个知识点的小图**(比如"Python 基础"或"算法入门"),把管道跑通,而不是一上来铺几千个点。

## 8. 评测(承接上个项目的思路,这是差异化关键)

上一个项目证明了"有评测"是稀缺品。这个项目继续:

| 评测什么 | 怎么评 | 指标 |
|---|---|---|
| **画像准不准** | 用留出的答题记录,预测"下次答对概率" | **AUC / Brier score** |
| **遗忘预测准不准** | 预测"该知识点何时会遗忘",与实际对比 | 误差 / 校准曲线 |
| **规划有没有用** | A/B:图谱规划 vs 随机推荐 vs 顺序推荐,比较后续答题正确率 | 提升幅度 |
| **GraphRAG vs 扁平检索** | 缺口检测任务上对比,GraphRAG 是否真的更好 | 缺口定位准确率 |

> **最后一个对比是最有说服力的:** 它能证明"我加 GraphRAG 不是赶时髦"。
> 如果测出来图没比向量强,那也是个诚实且有价值的发现。

## 9. 分阶段路线

| 阶段 | 产出 | 可验收标准 |
|---|---|---|
| **P0 图底座** | 30~50 个知识点的小图 + 前置依赖 | 图无环;能回答"X 的前置闭包" |
| **P1 入口 + 队列** | FastAPI + Redis Stream + 1 个 worker(画像更新) | `POST /answer` 立即返回,worker 异步更新画像 |
| **P2 GraphRAG 规划** | 多跳查询 + 下一步建议 | `GET /graph/{id}` 能看到前置链;规划有输出 |
| **P3 常驻循环** | FSRS 定时扫描 + WS 推送 | 到期的知识点会主动推给前端 |
| **P4 工作流** | LangGraph 替换手写流程 + checkpointer | 中途 kill 进程,能从中断处恢复 |
| **P5 评测** | 四项评测跑出数字 | README 有一张结果表 |
| **P6 收尾** | README + demo 视频 | 别人能 clone 跑起来 |

**建议做到 P3 就有一个完整可演示的东西**,P4/P5 是加分。

## 10. 面试叙事(2 分钟版)

> "我做的是个性化学习教练。起点是一个观察:**市面上所有'AI 学习助手'本质都是题库 + 检索,它们记不住你。**
>
> 我的核心是三层状态:用 BKT 建模'每个知识点你掌握到什么程度',用 FSRS 建模'你什么时候会忘',用知识图谱建模'知识点之间的前置依赖'。
>
> 有意思的是 GraphRAG 的用法:当一个学生反复做错某个题,扁平检索只能推荐'相似题目',而我可以沿前置依赖反向遍历,定位到**他真正缺失的那个基础知识点**,然后从他缺的地方补起。
>
> 工程上我做了三件事:FastAPI 只管入队不阻塞;Redis Stream 把答题事件、定时扫描、出题三种负载解耦;工作流用 LangGraph 加 checkpointer,长流程崩了能从断点恢复。
>
> 而且我给它建了评测:预测'下次答对概率'的 AUC 是多少,图谱规划相比随机推荐把后续正确率提了多少,以及**GraphRAG 相比纯向量检索在缺口定位上到底强多少**——这个数字我诚实汇报,如果没强很多我也会说。"

**三个支点:可测量的数学模型 + 图推理的真需求 + 有数字的评测。**

## 11. 风险与诚实的顾虑

| 风险 | 说明 | 缓解 |
|---|---|---|
| **前置依赖数据难搞** | 公开数据里几乎没有,得自己抽 | 先做小图(30 点),用 LLM 抽 + 规则校验 |
| **没有真实用户** | 评测缺答题数据 | 模拟学生(可指定"掌握度分布")跑评测;或小规模真人试用 |
| **工作量远大于合同审查** | 图 + MQ + 常驻 + 工作流,四个新东西 | 严格按 P0→P3 分阶段,每阶段独立可演示 |
| **图可能是过度设计** | 如果测出来 GraphRAG 没比向量强 | 这本身就是有价值的结论,诚实汇报(见 §8) |
| **做题场景偏窄** | 面试官可能觉得"就是个背单词 App" | 强调"可迁移":这套(BKT+FSRS+图谱+常驻)同样适用于**客服技能培训、新员工 onboarding** |

## 附:这个项目在能力栈上覆盖了什么

面试官会关心"你懂什么"。这个项目覆盖:

- **Agent**: 常驻 loop、工具调用、状态管理、断点恢复
- **RAG 进阶**: GraphRAG(图 + 向量混合)、多跳推理
- **系统工程**: 消息队列、异步 worker、解耦、削峰、死信、幂等
- **Web 后端**: FastAPI、WebSocket、长连接推送
- **工作流**: DAG 编排、checkpointer、human-in-the-loop
- **算法**: BKT、FSRS —— 证明你不只是"调 API"
- **评测**: 把"好不好"变成数字

**这是它相对于"又一个 RAG 问答机器人"的核心优势。**
