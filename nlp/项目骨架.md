# 第一部分 · 讲稿

> 用法：按序讲，不必背逐字。**每段的「钩子」留着** —— 它决定面试官往哪追问。

## 开场 · 一句话定位（10 秒）

> "这是一个电商售后助手，叫云集优选。它能答售后政策、查订单物流、**真的办理退换货**、
> 受理投诉、识别破损商品照。
>
> 和'问答机器人'的分水岭是最后两条：**它会写数据，而且在动数据之前有一道人工审批。**"

## 1. 业务与难点（20 秒）

> "难点不在问答 —— 政策问答谁都做得出来。
>
> 难在两件事：
> **一是它要能改数据库**（提退货申请、建工单），这类操作不可逆；
> **二是它必须真的读懂政策**，不能套模板。
>
> 举个设计好的例子：主场景订单是'**已激活的 3C 耳机要退货**'——
> 而'已激活的 3C'恰好**不适用七天无理由**。
> 所以系统必须一路读到质量问题那条 **15 日**通道上去，套模板的答案是错的。"

## 2. 分层（40 秒）

> "整个系统分五层，从上到下：**接入 / 编排 / Agent / 能力 / 数据**。
>
> 接入层是 FastAPI 加一个单文件前端，用 **SSE 逐节点推进度** ——
> 用户能看见'正在检索政策''正在查订单'，不是转圈等。
> 会话用 `thread_id` 隔离。
>
> 编排层是 **LangGraph 的状态机**，也是整个系统最核心的一层 ——
> 复杂度分流、任务图波次调度、人工介入断点都在这里。
>
> Agent 层有 **5 个现役 Agent**：知识检索、数据库查询、售后主 Agent、识图、闲聊兜底。
> 接口极简 —— **鸭子类型，只要实现 `handle(query, context) -> str`**，不要求继承基类。
>
> 能力层是**混合检索**（向量 + BM25）、**Text-to-SQL**、**固定写方法**，以及
> **写操作审批闸门**。
>
> 数据层是 **10 篇售后政策 + 一个 6 张表的 SQLite 订单库**，向量库 34 个 chunk。"

**钩子**：*"这五层里，编排层和能力层是两个我特别想展开的地方。"*

## 3. 编排主干（60 秒）

> "请求进来先做一件事：**判断这一个问题要不要多个 Agent 协作**。这是个 LLM 二分类，
> 判据是'是否需要多个**不同类型**的 Agent'。而且**解析失败就降级为简单路径** ——
> 宁可少拆，不可拆错。
>
> 于是有两条路：
> **简单问题** → 选一个 Agent，直接答。**复杂问题** → 规划器拆成带依赖的任务图，
> 并行扇出。
>
> 任务图的调度是**波次**的：每波只派发'**依赖已经全部完成**'的任务。
> 这里有一个我比较得意的细节 —— **它不维护'现在是第几波'这个游标**，
> 就绪判定完全由**已完成的集合反推**。
>
> 为什么这很重要？'第几波'是一个需要**同步**的状态：某个任务重跑、或某个 Agent 跑得慢，
> 游标和实际进度就对不上，而且**这类 bug 只在并发下出现**。
> 用已完成集合当唯一真相源，这类缺陷从根上就没有了。
>
> 收尾是三级质量把关：**重复检测**（结果和历史重复就熔断，跳过汇总）→
> **三维打分**（相关性、完整性、准确性加权）→ **人工介入检查**。"

**钩子**：*"这里有两个我觉得更有意思的：五条人工介入通道其实只有两条真能触发；以及并行扇出的循环必须有配额，不然会死循环。"*

## 4. 核心机制（每个 30 秒，挑三个讲）

> **① 写操作审批闸门**
> "系统能改数据，所以写之前停下来等人确认。这里有一处**设计判断**：
> 触发审批的判据是 `state['write_operations']` 非空 ——
> 也就是**程序实际有没有调用写工具** ——
> 而**不是**'用户原话里有没有出现写操作关键词'。
>
> 后者永远不可能命中，用户只会说'我要退货'。
> **措辞可以被绕过，实际动作不能。**
>
> 代价是用户会看到一次打断、点一下才继续 —— 但这是**有意的摩擦**。
> 对不可逆操作，摩擦是特性，不是缺陷。"

> **② 防幻觉兜底**
> "LLM 最危险的失败模式不是答错，而是**描述没发生的事**。
> 实测中模型会写出'已为您提交退货申请，单号 RF2026xxx'，而数据库里什么都没有。
>
> 所以有一道输出后校验：**答复里声称办过事，就必须本轮真调用过写工具**，
> 否则改写答复、明确告诉用户'并未提交'。
>
> 幻觉分两类：**幻觉知识**（答错，用户自己能判断）和**幻觉动作**
> （让用户以为办了而实际没办）。后者严重得多，而且只能靠'拿声称比对执行记录'来防。"

> **③ 读写分离**
> "读和写用完全不同的安全模型。
> **读**：Text-to-SQL，让 LLM 自由构造，加一道只允许 SELECT 的前缀检查 ——
> 因为读的形态无法穷举。
> **写**：根本不给 LLM 构造权，只让它**选函数、填参数** ——
> 因为写的形态可以穷举。
>
> 写方法里有**三重校验**：订单存在、归属正确、状态允许售后。
> 三条各挡一个具体的错 —— 尤其第二条：**订单真实存在，也不能证明是本人下的**，
> 挡的是 A 用户退 B 的订单。"

**钩子**：*"还有一个检索层面的：为什么两路召回融合时只能用排名、不能用分数。"*

## 5. 关键取舍（60 秒）—— 这段是分水岭

> "我想说说**放弃掉的东西**，因为架构就是取舍。
>
> **第一，这套系统没有单任务回退能力。**
> 共享状态 + 单向无环的任务图，带来的是'**必然终止、不会静默卡死**'。
> 代价是'A 检索 → 发现需要 B 的数据 → 回到 A 回答'这种形态
> **拆得出来、跑得起来，但语义是错的** —— A 的第二次执行看不到 B 的产出。
> 这是**设计边界，不是缺陷**，我知道它在哪。
>
> **第二，会话不持久化。** 图状态在进程内存里。
> 这带来一个直接后果：**人工介入的断点恢复，只在进程活着时成立**。
> 要做生产级，第一件事是把 checkpointer 换成持久化的。
>
> **第三，也是最该说的 —— 有一些设计超出了真实需求。**
> 五条人工介入通道有**三条是死的**；参数校验整条链路被一道守卫永远挡死；
> `user_id` 全项目只读不写，日志和审计全记成 `anonymous`。
> 这些是我把每个字段、每个 context 键做了**双向核对**（谁写、谁读，各 grep 一遍）
> 之后挖出来的。"

**钩子**：*"这里面最反直觉的一条是：那两条死通道不报错、也不打日志。"*

## 6. 边界与失败（40 秒）

> "最后说三条边界，我觉得讲清楚'到哪为止'比讲功能更能说明问题："
>
> | 边界 | 后果 |
> |---|---|
> | 会话不持久化 | 重启即丢；人机协同的断点恢复只在进程活着时成立 |
> | 无单任务回退 | 共享状态 + 单向无环图的固有代价，换来"必然终止" |
> | 5 条介入通道只有 2 条可达 | 另 3 条触发条件恒不成立，不报错不打日志 |

> "还有一条**最有价值的经验**，比代码值钱：
>
> **看到一条链路带着齐全的配套 —— 触发文案、前端按钮、事件推送 —— 先怀疑它不跑。**
> 完整度不是活性证据，是'曾经被设计过'的证据。
> 判断一条链路活不活，**不要看它周围有多少配套，要看它的入口有没有人喂。**"

## 收尾 · 留钩子

> "整体骨架大概是这样。有两块我觉得更有意思，
> 一个是**波次调度为什么刻意不维护'第几波'游标**，
> 另一个是**五条人工介入通道只有两条能触发、而且死的那两条不报错**。
> 您想深入哪块？"

## D. 一次请求的数据流

```
用户问句
  │
  ├─ SSE 连接建立（前端 EventSource）
  ├─ thread_id 取会话状态（MemorySaver，进程内）
  │
  ├─ 复杂度分类（LLM）
  │     ├─ simple  → 选 Agent → handle()
  │     └─ complex → 规划 → 扇出 → 波次调度 → 汇合
  │
  ├─ Agent 执行
  │     ① 指代消解（把「它」「那个订单」补全）
  │     ② 构造 context（history / dependencies / 图片 / 文件）
  │     ③ handle(query, context)：
  │          ReAct 循环：推理 → 调工具 → 看结果 → 再推理
  │          工具并行执行（线程池），写操作登记到线程本地
  │     ④ 取出本轮登记的写操作 → 写入 state
  │
  ├─ duplicate_detection（重复 → 熔断）
  ├─ aggregator（多 Agent 汇总）
  ├─ evaluator（三维打分；低分带 feedback 重跑）
  ├─ human_intervention_check
  │     ├─ 有写操作 → interrupt_before 挂起 → 前端审批 → /resume
  │     └─ 无 → END
  │
  └─ 全程 SSE 逐节点推送进度事件
```

## F. 核心机制速查（问题 → 方案 → 代价）

| # | 机制 | 解决什么 | 方案 | **代价** |
|---|---|---|---|---|
| 1 | **复杂度分流** | 不是所有问题都值得起任务图 | LLM 二分类；解析失败降级 simple | 多一次 LLM 调用；分类错会走错路 |
| 2 | **DAG 波次调度** | 子任务有依赖 | 就绪 = **已完成集合反推**，不维护波次游标 | 已完成只增不减 → **无单任务回退** |
| 3 | **汇聚自判轮次** | 每波都调 LLM 判断"还有没有"太贵 | `wave_scheduler` 自己挑，挑不出就 `done` | 无全局预算上限 |
| 4 | **混合检索 RRF** | 向量与 BM25 分数量纲不可比 | **只用排名，丢弃原始分数** | 丢弃了"分数差距"的信息 |
| 5 | **读写分离** | LLM 生成写语句是灾难 | 读：Text-to-SQL + SELECT 前缀检查；写：固定方法 + **三重校验** | 写的形态必须能穷举 |
| 6 | **★ 写操作审批闸门** | 写操作不可逆 | 判据 = `write_operations` 非空（**实际动作**，非措辞） | 用户看到一次打断（有意的摩擦） |
| 7 | **★ 防幻觉兜底** | 模型"演"出完整流程却没调工具 | 声称办过事 → 必须本轮真调过写工具 | 只能覆盖写操作，管不住幻觉知识 |
| 8 | **质量三维评分** | 答案质量无客观判据 | 0.4/0.3/0.3 加权 + 单项否决线 6 + 带 feedback 重跑 | 评分本身是 LLM 自评，主观 |
| 9 | **迭代配额** | 自评回路可能死循环 | `iteration` 无条件 +1，硬上限 | 可能提前放弃一个本可救回的答案 |
| 10 | **重复熔断** | 重试重复结果纯浪费 | 指纹比对 → 跳过 critic/aggregator | 语义重复的判定可能误杀 |
| 11 | **两层缓存** | 重复问答开销 | 精确缓存 + 语义缓存 | ⚠️ 语义缓存**只有 knowledge_agent 接线** |
| 12 | **长期记忆** | 跨会话记事实，但不能无限膨胀 | 结构化沉淀 → 三段式检索注入 → 规则治理 | 治理是离线批处理，非实时 |

## G. 契约表（系统最容易被写坏的地方）

> **为什么单列**：`state` 和 `context` 的类型都是 `Dict[str, Any]` ——
> **塞什么取什么都不报错**。所以系统里"看起来在工作、实际没接线"的链路，
> 全都出在这两处。

### G.1 `context` 全键（构造点唯一：`make_agent_node`）

| 键 | 写方 | 读方 | 状态 |
|---|---|---|---|
| `_agent_name` | nodes.py:207 | 4 个 Agent | ✅ 活 |
| `_stream_writer` | nodes.py:206 | 4 个 Agent | ✅ 活 |
| `history` | nodes.py:193 | customer_service · database · knowledge | ✅ 活 |
| `image_urls` / `image_paths` / `image_base64_list` | nodes.py:171-176 | vqa_agent | ✅ 活 |
| `file_paths` | nodes.py:178 | **无** | ❌ 只写不读 |
| `dependencies` | nodes.py:164 | **无** | ❌ 只写不读（上游数据改走 query 拼接） |
| `original_query` | nodes.py:167 | **无** | ❌ 只写不读 |
| `image_url` / `image_path` / `image_base64`（单数） | **无** | vqa_agent（兜底分支） | ❌ 只读不写，永不触发 |
| `user_id` | **无** | 4 处（日志 / 审计 / 记忆隔离） | ❌ **恒为 `"anonymous"`** |
| `conversation_history` | **无**（注入的是 `history`） | chat_agent | ❌ **键名不匹配** → 恒拿空历史 |

### G.2 `state` 里没有读取方、或值恒定不动的字段

| 字段 | 情况 |
|---|---|
| `messages` | 只累积、无人消费（Agent 读的是 `context["history"]`） |
| `parameters_aligned` / `parameter_alignment_errors` | 只在入口初始化，**无读方** |
| `critic_passed` | 恒为初始 `True`（唯一写方 critic **从未进图**） |
| `critic_validation` / `critic_issues` | 同上，恒为初始值 |
| `stop_reason` | 会写，但**代码内无读方**，仅留档 |
| `validation_*` 一族 | 因守卫挡死，**整条链路从不执行** |

### G.3 写操作生命周期（全链路 ✅ 活）

```
① Agent 执行写工具（submit_return_request / create_ticket）
② _record_write_operations 登记到线程本地     customer_service_agent/agent.py:680
③ 节点 consume_write_ops() 取出               nodes.py:249
④ 写入 state["write_operations"]（挂 operator.add）
⑤ human_intervention_check 通道 2 读它 → 挂起
⑥ 前端弹审批 → 人点批准 → POST /resume
⑦ 入口 resume 分支置 write_approved = True
⑧ 继续执行
```

> **必须在线程内、`handle()` 之后立刻读** —— 登记器是**线程本地**的，
> 而工具是**并行执行**的（跑在线程池里）。
> 根因：`handle() -> str` 只能返回字符串，结构化信号（"我刚改了数据"）带不出来，
> 才逼出这套线程本地登记机制。

### G.4 人工介入的 5 条通道

| # | 触发条件 | 状态 | 死因 |
|---|---|---|---|
| 1 | `plan["complexity"] == "complex"` 且未批准 | ❌ **不可达** | plan 里**从没有** `complexity` 这个键 |
| **2** | `write_operations` 非空且未批准 | ✅ **活** | — 唯一可靠的写操作闸门 |
| 3 | 用户原话含写关键字 且 Agent 名含 `database` | ❌ **不可能命中** | 查的是用户**中文原话**里的 `INSERT`/`UPDATE` |
| **4a** | `quality_score < 0.4` 且 `iteration >= 2` | ✅ **活** | — |
| 5 | `critic_passed` 为假 | ❌ **不可达** | `critic_passed` 恒为初始 `True` |

**两条死通道是两种不同的死法**（这张表本身就是教材）：

- 通道 1 死于 **"key 从没被写过"** → 条件恒为 `None`
- 通道 5 死于 **"字段值恒定不动"** → 条件恒为假

**两条都不报错、不打日志**，静默跳过 —— 光看逻辑是对的，
必须去追"条件里那个值从哪来"。

### G.5 Agent 协议

```python
handle(query: str, context: Dict[str, Any]) -> str
```

- **鸭子类型**：`runtime_checkable` 的 `Protocol`，`isinstance` 检查 —— 不要求继承基类
- **代价**：`isinstance` **只核对方法名在不在，不核对签名** ——
  实测 `handle(self)`（一个参数都没有）**同样能注册成功**
- **返回类型限定 `str`** —— 结构化信号带不出来，逼出线程本地登记（见 G.3）

## I. 边界与已知缺陷

### 设计边界（刻意为之的取舍）

| 边界 | 换来什么 |
|---|---|
| **无单任务回退** | 流程**必然终止**，不会静默卡死 |
| **会话不持久化** | 零外部依赖即可跑起来 |
| **Agent 之间不互调**（契约只有 `handle`） | 接口极简，任意类都能当 Agent |
| **死通道不删** | 保留将来接回 critic / 计划审核的位置 |

### 当前未解决的缺陷

| 项 | 说明 |
|---|---|
| 参数校验整条链路不执行 | 被"Agent 返回纯文本 → 跳过字段校验"的守卫挡死（契约就是 `handle() -> str`，守卫永远触发） |
| 计划审核通道不可达 | 条件依赖从没被写过的 key；**且即使修好 key 语义也不对** —— 它的唯一入边来自 `evaluator`，即答案已生成之后才检查，属"事后告知"而非"事前审核" |
| `user_id` 从未被设置 | 日志、审计、记忆隔离全部记成 `"anonymous"` |
| chat_agent 恒拿空历史 | 键名不匹配 |
| 申请原因不受政策校验 | 用户说什么理由都收，不与政策条款比对 |
| 语义缓存只在一个 Agent 接线 | 其余 Agent 走不到语义缓存 |
| `config/` 两个 yaml 未被消费 | 改了不生效 |
| `document_agent` / `critic_agent` 未注册 | 有类有工具，不在图里 |

### 最有价值的一条经验（比代码值钱）

> **看到一条链路带着齐全的配套 —— 触发文案、前端按钮、事件推送 —— 先怀疑它不跑。**
>
> 完整度不是活性证据，是"**曾经被设计过**"的证据。
> 判断一条链路活不活，不要看它周围有多少配套，**要看它的入口有没有人喂**。

**三种死法，各有查法**：

| 死法 | 特征 | 怎么查 |
|---|---|---|
| **只写不读** | 写方在、读方为零 | 对键名 grep 两次 |
| **只读不写** | 读方一堆、写方为零 → **恒取默认值** | 同上，看写方是否为空 |
| **键名不匹配** | 两边都"有"，键名不同 | 逐字比对 |
| **条件恒假** | 条件依赖一个从没被写过的值 | 顺着条件里的 key 往回找写入点 |
| **守卫挡死** | 整段被一个永远成立的前置条件挡住 | 找**最前面的 if** |
