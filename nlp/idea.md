### 1. 思路

环境这块只有一个核心目标：**让"跑起来"这件事不成为一个反复消耗时间的问题**。

改造是个长活儿，如果环境本身不稳（装到一半报错、改了代码不知道是环境影响还是代码问题），后面每一阶段都会被拖累。所以阶段 0 要一次性把地基铺平，具体拆成三件事：

- **隔离** —— 项目自己的依赖装进项目自己的 venv，不污染全局、也不复用别人的
- **可复现** —— 依赖清单落在 `requirements.txt`，任何人重新装能得到一样的结果
- **不泄密** —— API key 只存在于本地磁盘，任何情况下都不进 git

### 2. 为什么这么改

**为什么用 Python 3.12，而不是系统里现成的 3.14.5？**

这是本阶段最有意思的一个决策。Python 生态有个规律：**新版本发布后，大型库的预编译轮子（wheel）往往要滞后几个月**。`chromadb` 这类库依赖链很深（还会牵扯 onnxruntime、pydantic-core 这些带 C/Rust 扩展的包），在没有对应版本的预编译包时，pip 会尝试**从源码编译** —— 在 Windows 上这基本等于失败（缺编译器、缺构建工具链，报一堆看不懂的错）。

3.12 是当前兼容性最好的版本，几乎所有库都提供了它的 wheel。**"最新"不等于"最合适"**，这是工程上很常见的一个反直觉点。

> 顺带纠正一个我自己的错误判断：我先前说"机器上没有 Python 3.12"，其实只对系统的 `py` 启动器成立。`uv` 自己管理了一套 Python，里面就有 3.12.13 —— 所以这个选择从"退而求其次用 3.13"回到了原本的最优解。

**为什么用 `uv` 而不是 `pip`？**

- 它自带 Python 版本管理（`uv python install 3.12`），**不依赖系统装了什么** —— 换台机器也能复现同样的环境
- 依赖解析器是 Rust 写的，装几十个包通常几秒到几十秒，pip 要几分钟
- 解析更严格，会提前暴露版本冲突，而不是装完才在运行时崩

代价是它比 pip 新，遇到冷门问题时的资料少一些。但对这个项目来说收益明显更大。

**为什么用国内镜像？**

`pypi.org` 在国内访问经常几十 KB/s，装 chromadb 这种大包会卡很久甚至超时。清华镜像（`pypi.tuna.tsinghua.edu.cn`）是国内同步最及时的之一。这只是"从哪儿下载"，装出来的包内容完全一样。

其他可选镜像：阿里云 `mirrors.aliyun.com/pypi/simple`、中科大 `pypi.mirrors.ustc.edu.cn/simple`。

**为什么密钥要放 `.env`，而不是直接写在代码里？**

三条理由，按重要性排：

1. **一旦提交就撤不回来** —— git 历史是不可变的。就算你下一个 commit 删掉那行，密钥仍然躺在历史里，任何 clone 过的人都能翻出来。**密钥泄漏只能靠轮换补救，不能靠删除补救。**
2. **代码和配置应该分离** —— 同一份代码要能在开发机、测试机、生产环境跑，区别只在配置。这是 "12-factor app" 的核心原则之一。
3. **换 key 不用改代码** —— 改一行 `.env` 重启即可。

**那为什么还要额外加一个 pre-commit 钩子？有 `.gitignore` 不够吗？**

不够，两者防的是**不同的东西**：

- `.gitignore` 按**文件名**拦截 —— 它只知道"叫 `.env` 的文件不要提交"
- 钩子按**文件内容**拦截 —— 它能发现"`config.py` 里赫然写着一行 `sk-xxxxx`"

真实事故里，密钥更多是从第二种路径漏出去的：开发者图省事把 key 硬编码进某个 Python 文件，而那个文件完全正常、不该被忽略。`.gitignore` 对此无能为力，钩子能拦住。

**为什么根目录那个 `.venv` 要弃用而不是删掉？**

它能跑（Python 3.14.5），只是里面 0 个包、且版本太新。删掉没有任何收益，留着也不占多少空间，万一以后有别的用途。**不确定用途的东西，不要顺手删掉** —— 这是接手陌生代码库时的一条保命原则。

### 3. 人类怎么学这部分

#### 3.1 该动手看的（按顺序，20 分钟够）

1. **读 `.git/hooks/pre-commit`** —— 一共 30 来行，是理解"git 钩子"最轻量的入口。
   重点看 `git diff --cached --name-only --diff-filter=ACM` 这一句：它取出**即将进入这次提交的文件列表**。
   想明白一个问题：*为什么钩子里是"检查暂存区"而不是"检查工作区"？*（提示：钩子要拦的是"这次提交"，工作区里没被 `git add` 的文件这次并不会进仓库）
2. **亲手验证钩子**：
   ```bash
   # 现场"造"一个长得像密钥的字符串 —— 别把完整的假 key 直接写进文档
   python -c "print('key = \"sk-' + 'a'*24 + '\"')" > ./t.py
   git add t.py
   git commit -m "test"        # 应该被拦下，退出码 1
   git reset t.py && rm t.py   # 清理
   ```
   看到它**真的拒绝提交**，比读十遍说明都管用。

   > **这里踩了个很真实的坑，值得单独说：**
   > 我写这份文档的第一版，直接把一串 `sk-` 开头的假 key 敲进了上面的代码块。
   > 结果提交时 —— **被这个钩子自己拦下了**。
   >
   > 这正是"扫内容"相对于"匹配文件名"要付的代价：**它会误报**。
   > 而正确的处理方式**不是关掉钩子**（那样真正的泄漏也会被放行），
   > 而是**让文档里根本不出现那串字符** —— 改成运行时现造一个。
   >
   > 这也解释了一个工程常见现象：安全工具刚上线时，团队第一反应往往是"太烦了，关掉"。
   > 更稳的做法是**把它调准**，或者**改变自己的写法去适应它**。
3. **看 `nlp/.env` 和代码怎么读它** —— 在项目里搜 `os.getenv("DASHSCOPE_API_KEY")`，看这个 key 最终流到了哪里。

#### 3.2 背后的通用概念（这些才是能带走的东西）

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **虚拟环境隔离** | 每个项目一套独立依赖，互不干扰 | 两个项目依赖同一个库的不同版本时，没有隔离就是死局 |
| **12-factor config** | 配置放环境变量，不放代码 | 云原生部署的事实标准，面试常问 |
| **git 钩子** | git 在特定时机自动执行的脚本 | CI 之前的第一道自动化闸门；pre-commit / pre-push / commit-msg 各有用途 |
| **语义化版本与轮子** | PyPI 的包要针对每个 Python 版本、每个平台分别编译 | 解释了"为什么新 Python 版本装不上老库" |
| **最小权限 / 密钥轮换** | 密钥假定终将泄漏，要有轮换能力 | 安全工程的基本假设 |

#### 3.3 看完应该能回答的问题

- 为什么 `.gitignore` 挡不住"密钥写在代码里"，而钩子可以？
- 为什么把密钥从最新 commit 里删掉，仍然算泄漏？
- `uv` 和 `pip` 除了速度，最本质的区别是什么？（提示：Python 版本管理）
- 如果换一台新电脑，怎么用三条命令把我的环境完全复现出来？

  参考答案：
  ```bash
  uv venv --python 3.12 .venv
  uv pip install -r requirements.txt --index-url https://pypi.tuna.tsinghua.edu.cn/simple
  cp .env.example .env   # 然后填自己的 key
  ```

### 4. 本阶段的意外收获：两个值得记住的教训

#### 教训一：验证清单要来自代码，不能来自记忆

装完依赖后我做验证，第一版写的是：

```python
import langgraph, chromadb, dashscope, fastapi   # ← 报错：No module named 'dashscope'
```

我当时"记得"这个项目用的是通义千问的官方 SDK。但翻代码才发现，它压根不依赖 `dashscope` 包 ——
`requirements.txt` 里写的是 `openai>=1.0.0`，走的是 **DashScope 的 OpenAI 兼容接口**。

> 这是很典型的情况：README 里满篇"通义千问""DashScope"，很容易让人以为要装官方 SDK。
> 但**它把模型厂商抽象掉了** —— 对这个项目来说，通义千问只是"一个 OpenAI 协议的服务端"。
>
> 这个抽象有实际好处：换模型厂商时，改的是 base_url 和 model 名，代码不用动。
> 所以**遇到「兼容 OpenAI 接口」的服务，一律可以用 `openai` SDK 去调**，这是现在的行业惯例。

**教训：验证一个环境，清单应该从 `grep` 代码得到，不是从印象里翻出来。**

#### 教训二：`>=` 下限约束，是个温柔陷阱

`requirements.txt` 里写的是：

```
chromadb>=0.4.0
openai>=1.0.0
```

我当时没在意，装完一看实际解析到的是 **chromadb 1.5.9** 和 **openai 3.14.1**。

问题在于：**这两个库都经历过大版本破坏性变更**（chromadb 0.4 → 1.x、openai 1.x → 2.x → 3.x）。
而这个项目的代码，很可能是在 0.4.x / 1.x 年代写的。`>=0.4.0` 这个约束**允许**装 1.5.9，但没人验证过 1.5.9 还能不能跑。

这就是「下限约束」的陷阱：**它表达的是"至少要多新"，而不是"验证过哪个版本"**。依赖解析器会老老实实给你装最新版，然后你在运行时才发现 API 变了。

三种做法的取舍：

| 做法 | 写法 | 优点 | 缺点 |
|---|---|---|---|
| 只写下限 | `chromadb>=0.4.0` | 不限制升级 | 可能装到没验证过的新版本 |
| 写死版本 | `chromadb==0.4.6` | 一定复现 | 永远拿不到安全更新 |
| **锁文件** | `uv.lock` / `poetry.lock` | 装的时候用最新，**锁住验证过的组合** | 需要额外维护锁文件 |

**业界结论是：用锁文件。** 让解析器去挑最新兼容版本，但把它挑出来的结果**记下来**，之后所有人装的是同一套。
这个项目原仓库其实是有 `uv.lock` 的（在归档区里躺着），只是 nlp/ 目录下没有 —— 等改造稳定下来，值得给 nlp/ 也补一个。

> **当前状态：** 已确认没有 import 层的破裂（5 个核心模块都能导入）。
> 但运行时的 API 差异还没验证 —— 阶段 1 重建向量库时会第一次真正调用 Chroma，届时见分晓。

#### 人类怎么学这部分

- **概念：语义化版本（SemVer）** —— `主版本.次版本.补丁`，主版本变动 = 有破坏性变更。理解了它，才能读懂 `>=` / `^` / `~` 这些约束符的真实含义
- **概念：可复现构建** —— "我这能跑"和"任何人任何时候都能跑出一样的结果"是两件事，锁文件是后者
- **概念：依赖注入 / 抽象边界** —— 这个项目用 OpenAI 协议把模型厂商隔离在外，是"面向接口而非实现"的一个活例子
- **动手：** 跑一遍 `uv pip list`，看看这个项目到底装了 143 个什么样的包；再打开 `requirements.txt` 对照，感受一下"直接依赖"和"传递依赖"的数量差距（直接依赖 30 来个，实际装了 143 个）

### 1. 思路

阶段 0 铺好了环境，阶段 1 要铺**数据**。RAG 系统里，检索答不对，后面编排得再漂亮也没用 —— 所以这一步的验收标准不是"脚本跑通"，而是**"问真实问题能不能命中对的文档"**。

拆成两条独立的线：

- **知识线**：文档 → 切块 → 向量化 → 进 ChromaDB。这条线决定"答得对不对"
- **数据线**：订单/物流/退款/工单进 SQLite。这条线决定"查得准不准"

两条线互不依赖，但都必须在阶段 2 之前就绪 —— 因为阶段 2 要让 Agent 去用它们。

### 2. 为什么这么改

**为什么政策文档里要写那么多具体数字？**

因为**检索是靠字面匹配和语义相似度工作的**。如果文档写「一定时间内可以退货」，用户问「七天无理由怎么算」，两者语义相关但**没有共同的具体词**，向量相似度上不去，可能就检索不中。

写成「自物流签收之日起计算，按自然日计算，签收当日计为第 1 天」，效果完全不同 —— 用户问题里的「时间」「怎么算」和文档里的「之日起计算」「按自然日计算」能对上。

> 这是个反直觉的点：**写给人看的文档可以含糊，写给 RAG 用的文档必须具体**。
> 因为人能从上下文推断「一定时间」大概是几天，向量检索不能。

**为什么每篇第一行必须是 `# 标题`？**

因为 [init_vector_db.py:213](tools/scripts/init_vector_db.py#L213) 用 `content.split('\n')[0]` 取**第一行**当文档标题写进元数据。前面多一个空行，标题就成了空字符串。这是个隐式的格式契约 —— 脚本不报错，只是默默存了个空标题，出问题很难查。

**旧文档到底该删还是该留？白名单不是已经能过滤了吗？**

这两个动作语义不同，我做了两个都做：

- **白名单过滤** = 「这文件在仓库里，但不进知识库」。它是个**开关**，好处是留退路 —— 哪天想恢复某篇文档，改一行白名单重新建库就行
- **物理删除** = 「这文件不该在这儿了」

场景已经彻底变了（RAG 技术文档 → 电商售后政策），留着那 12 篇只会让 `data/knowledge/` 的含义变模糊 —— 看到的人会以为它们还在被索引。所以删掉。

**删了会不会丢？** 不会。它们都在 git 历史里，一条 `git checkout ce756f1 -- nlp/data/knowledge/` 就能找回。**这正是版本控制存在的意义 —— 它让"删除"变成可逆操作，所以该删的时候可以果断删。**

**为什么数据库要写脚本生成，而不是直接把 `.db` 文件提交进仓库？**

1. **二进制文件在 git 里存不了增量**。git 对文本做 diff，对二进制只能整个存。每次数据一改就是一个全新的完整副本，仓库体积线性增长，再也降不下来
2. **它是纯生成物**。任何时候 `python tools/scripts/init_ecommerce_db.py` 都能精确复现 —— 那就不需要在仓库里存一份
3. **可审查**。改一个 Python 脚本，你能在 diff 里一眼看出"哦加了个订单"；改一个 `.db`，diff 只会告诉你"二进制文件已更改"

原项目对 `chinook.db` 就是这么处理的（`.gitignore` 里写着"可由用户自行下载或初始化"），我沿用了同一个约定。

> **判断标准很简单：能由代码从零重建的东西，就不该进版本控制。**
> 反之，**不能**重建的东西（手写的文档、配置、种子数据源文件）就必须进。

**为什么建库脚本里的日期是写死的，不用 `datetime.now()`？**

如果订单日期跟着运行时间走，那每次重建数据库，数据都不一样 —— 今天跑出来「上周买的耳机」，下个月跑就是「上个月买的」。这会导致：

- **没法写测试**：断言里不能出现具体日期
- **没法复现 bug**：别人拿到同样的代码，跑出的是另一套数据

所以基准日钉死在 **2026-09-16**，所有日期都是相对于它手算好的字面量。**可复现性 > 方便性**。

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **RAG 的数据准备（ingestion）** | 文档 → 解析 → 分块 → 向量化 → 入库 | RAG 效果的上限由它决定，模型再好也救不回烂数据 |
| **分块（chunking）策略** | 块太大丢精度、太小丢上下文，靠 overlap 衔接 | 最常被忽视、但对检索质量影响最大的参数 |
| **元数据（metadata）** | 挂在每个 chunk 上的结构化信息 | 支持按来源过滤、追溯引用、按权限裁剪 |
| **生成物 vs 源文件** | 能代码重建的不入库，不能的必须入库 | 决定仓库会不会随时间臃肿 |
| **可复现性** | 同样的输入永远产出同样的结果 | 没它就写不了测试、复现不了 bug |
| **幂等（idempotent）** | 跑一次和跑十次结果一样 | 建库脚本先 DROP 再 CREATE 就是在保证幂等 |

数据库这块有个关键选择：**让 LLM 现场写 SQL**，还是**给人预先写好一批查询函数**？

### 2. 为什么这么改

**为什么选「让 LLM 写 SQL」而不是「预定义查询函数」？**

| 做法 | 优点 | 缺点 |
|---|---|---|
| **Text-to-SQL**（本项目） | 能回答**没预料到**的问题 | 会写错 SQL、可能幻觉 |
| 预定义函数 `get_order_status(order_id)` | 稳、可控 | 只能回答预先设计好的问题 |

电商售后的提问方式是发散无穷的 —— 「我上周买的耳机到哪了」「帮我看看有没有还没发货的订单」「这个月退款一共多少钱」。你没法穷举。所以选 Text-to-SQL。

代价是要防幻觉，这就引出了下面三件事。

**为什么要把「表名 → 中文描述」的映射喂给 LLM？**

因为 LLM 只看到 `order_items` 这种英文表名，得靠猜。而它的判断依据来自训练数据 —— 在别的项目里 `order_items` 是什么样，它就按什么样理解。

给它一句「订单明细表，记录每笔订单买了什么商品、数量、单价、小计」，它就能在「我要查某个商品买了几件」这类问题上**准确挑中这张表**，不用先 `describe_table` 把每张表都看一遍。

**这是省钱又提准的一招**：一段文字描述，换掉了成百上千 token 的探索过程。

> 映射里没写的表也不会坏 —— `_get_table_description()` 会退化成「从 DDL 解析列名」。
> 有映射是加分项，没映射是兜底，不会崩。**这种「增强而非依赖」的设计值得学。**

**为什么 few-shot 示例要写得那么详细？**

因为 few-shot 示例**其实是隐式的 schema 文档**。LLM 会照着示例的模式办事：

- 示例里写「先 `list_tables` → 再 `describe_table` → 最后 `query_database`」，它就会走这个流程
- 示例里的 SQL 写了 `WHERE order_id = 'SO20260909001'`，它就知道订单号长这样、要加引号
- 示例二特意演示了 **JOIN**（orders 和 logistics 用 order_id 关联），它遇到跨表问题就知道要 JOIN

**没有这个 JOIN 示例会怎样？** LLM 很可能只查 orders 表，然后**编造**一个物流状态 —— 因为它不知道还该查 logistics。这就是幻觉的典型来源：不是模型想骗人，是它不知道去哪儿找。

所以我在示例后面加了一句硬约束：

> 「查不到某个订单的物流记录，通常意味着订单还没发货 —— 这时要如实回答『该订单尚未发货，暂无物流信息』，不要编造轨迹。」

**为什么换 CRM 要让新类保持和旧的完全一样的接口？**

因为 `EcommerceCRM` 和 `MockCRM` 有完全相同的方法签名：

```
get_user_info(user_id)              get_ticket(ticket_id)
create_ticket(user_id, issue, ...)  update_ticket_status(id, status)
                                    get_user_tickets(user_id)
```

这样 Agent 那边**只需要改一行**（换实例化的类），其余代码一行不动：

```python
self.crm = crm or MockCRM()      →   self.crm = crm or EcommerceCRM()
```

这就是**鸭子类型**的威力 —— Python 不要求你继承同一个基类，只要"叫起来像鸭子"（方法名和签名对得上）就行。代价是**没有编译期检查**，所以接口要刻意保持一致，这是靠约定而不是靠编译器保证的。

**为什么每次操作都新开数据库连接？**

```python
def _connect(self):
    conn = sqlite3.connect(self.db_path)
    conn.row_factory = sqlite3.Row
    return conn
```

因为 **SQLite 的连接不能跨线程共享**，而 Agent 可能在多个线程里被并发调用（FastAPI 就是多线程的）。共享一个连接，迟早会遇到「SQLite objects created in a thread can only be used in that same thread」这个经典报错。

开连接的开销很小（就是打开一个文件），**不值得为这点性能去做连接池** —— 那是 MySQL 那种网络数据库才需要考虑的事。

> 顺带一个设计细节：`_next_ticket_id()` 用 `MAX(ticket_id)` 而不是 `COUNT(*)` 算序号。
> 用 COUNT 的话，中间删掉一个工单，序号就会重复 —— **生成主键时要看"最大值"而不是"数量"**，这是个容易踩的坑。

**为什么不抛异常，只打警告？**

```python
if not os.path.exists(self.db_path):
    logger.warning(f"数据库不存在: {self.db_path}，请先运行 ...")
```

因为数据库文件缺失时，**更好的结果**是"客服 Agent 回一句『工单系统暂时不可用』"，而不是"整个服务起不来"。这叫 **fail-soft（软失败）**：让故障局限在一个功能内，不要扩散成整体宕机。

### 4. ★ 本阶段最有价值的教训：一个自己埋的 bug

我的建库脚本里给每列都写了中文行注释，这本来是好习惯：

```sql
CREATE TABLE customers (
    user_id   TEXT PRIMARY KEY,   -- 会员ID，如 U10001
    name      TEXT NOT NULL,      -- 姓名
    ...
)
```

结果验证时看到这个：

```
customers  会员表...约6行。列: [user_id, --, --, --, member_level, --, --, --]
                                    ↑ 列名变成 -- 了
```

**根因**：SQLite 把建表语句的**原始文本**（含注释）原样存进 `sqlite_master.sql`。而 `_extract_columns_from_ddl()` 的逻辑是「按逗号切分，取每段第一个词」——

```
"user_id TEXT PRIMARY KEY"  →  第一个词 user_id   ✓
"  -- 会员ID，如 U10001\n  name TEXT NOT NULL"  →  第一个词 --   ✗
```

**为什么这个问题严重？** 这串描述正是 `list_tables` 喂给 LLM 的东西。列名全变成 `--`，等于 LLM **看不到表有哪些字段** —— 只能靠 `describe_table` 多跑一轮补回来，既费 token 又降准确率。

**修法**：解析前先剥掉 SQL 注释。

```python
body = re.sub(r'--[^\n]*', '', body)   # 先剥注释，再按逗号切
```

**这个 bug 教了三件事：**

1. **"注释是好习惯"只在人读代码时成立。** 当注释进入机器解析路径（这里是 SQLite 的 DDL 存储），它就成了噪声。**写得漂亮不等于写得正确。**
2. **验证不能只看"跑通没报错"。** 脚本一路绿灯，输出也在正常打印，只是内容悄悄退化了。所以验证要**看输出内容是否合理**，不能只看退出码。
3. **元编程/文本解析的代码最脆弱。** `_extract_columns_from_ddl` 是个"用正则解析别人生成的 SQL"的函数 —— 它比普通业务代码更容易被输入格式搞崩。这类代码值得额外写几个边界用例。

### 1. 思路

### 2. 为什么这么改

#### 2.1 提示词为什么写成"决策树"而不是"工具清单"？

原提示词是「知识咨询 → hybrid_search；投诉 → create_ticket」这样的罗列。
但它没回答一个关键问题：**同一个问题可能同时需要多步**（退货要查订单 + 查政策 + 提交申请）。

改成按**意图**组织的决策树，把每类意图的**完整步骤序列**写清楚：

```
申请退货 → ① query_order 确认订单 → ② hybrid_search 检索政策 → ③ submit_return_request 提交
```

同时把 **4 个业务陷阱**写进提示词。其中最重要的是这条：

> 不是所有商品都能七天无理由退货。已激活的 3C 数码、贴身衣物等属于法定例外，
> 只能走"质量问题"通道（时限更长、运费平台承担）。

**为什么提这条？** 因为它是**反直觉**的。我们埋的主场景订单恰好就是「已激活的无线耳机」——
如果不提醒，模型会照最熟悉的"七天无理由"模板回答，把运费责任说反（本该平台承担，说成用户自付）。

注意我只写了"存在这个例外"，**没写具体时限和金额** —— 那些必须去检索。
这是刻意的：**提示词负责指路，知识库负责给答案**。把政策条文抄进提示词，RAG 就白做了。

#### 2.2 为什么删掉 `context["urgent"]` 那段？

原代码里有：

```python
if context.get("urgent"):
    sentiment = context.get("sentiment", {})
    prompt += f"当前用户情绪：{sentiment.get('sentiment')}..."
```

看起来很合理。但**全项目搜不到任何地方给 `urgent` 赋过值** —— 这段提示词从写下的那天起就没生效过。

**这段代码的危险之处不在于它没用，而在于它"看起来有用"** —— 读代码的人会以为情绪已经被接进去了，
于是不去做真正该做的事。

替代方案是把映射规则**写死进提示词**，让 LLM 自己去串：先调 `analyze_sentiment`，
再把结果作为 `sentiment` 参数传给 `create_ticket`，优先级按分数映射。

**为什么不改成在 Agent 里存 `self._last_sentiment`？** 因为 Agent 实例是**全局共享**的，
多个请求并发时会互相覆盖 —— A 用户的情绪会影响 B 用户的工单优先级。
改成"参数显式传递"就没有这个隐患。**能在函数参数里传的东西，不要挂在对象状态上。**

#### 2.3 ★ 发现的第一个真问题：Agent 会"演"给你看

第一次端到端测试，Agent 的回答非常漂亮：

> ✅ 已为您成功提交退货申请：售后类型：退货退款 ...

但我查数据库 —— **refunds 表里什么都没有**。

它的 ReAct 轨迹是：`query_order` → `hybrid_search` → `query_user_info` → **收工**。
三轮都在收集信息，**`submit_return_request` 从头到尾没被调用过**。

这是 LLM Agent 最危险的失败模式：**它不是说了错误的话，而是描述了没发生过的事。**
对用户来说，"已提交，单号 RF2026xxx" 和真的提交了**没有任何区别** —— 直到他去查，发现查无此单。

> 有意思的是，这个项目**早就为数据库 Agent 踩过同一个坑**，它的提示词里写着：
> 「★ 绝对禁止只输出 SQL 语句而不执行」。同一个失败模式，换了个 Agent 又出现一次。
> 这说明它不是某个模块的疏漏，而是 **LLM Agent 的固有缺陷**。

**第一层修法是提示词**：加一条硬规则，并明确"只描述不调用 = 欺骗用户"，
还给了经验值（完整流程通常 4~5 轮，别在第 3 轮收工）。

改完后它确实开始调用了。但——还不够。见下一节。

#### 2.4 ★ 发现的第二个问题：迭代次数卡死，然后开始编

加上提示词规则后重跑，第 5 轮终于调用了 `submit_return_request`，写操作也捕获到了。

**但再跑一次，又变回"没调用"了。** 而且这次答复里的单号是 `RF20260916001` ——
真实落库的是 `RF20260916004`，**单号是编的**。

机制搞清楚了：完整流程需要
```
query_order → query_logistics → hybrid_search → query_user_info → submit_return_request
```
**5 轮工具 + 1 轮生成答案 = 6 轮**，而 `max_iterations = 5`。

**迭代次数用尽时，代码会强制模型"基于已有信息给出最终答案"。**
模型手里有一堆"我查到了订单、查到了政策、查到了会员"的信息，
于是它顺着"流程应该走到哪"把结果补完了 —— **包括一个看起来很像真的单号**。

两处修：

1. **上限 5 → 8**（根因修复：给够轮次，让它能走完）
2. **加确定性兜底 `_verify_write_claim()`**（见 2.5）

**这里最重要的认知是：`max_iterations` 不只是一个性能参数，它是个正确性参数。**
设小了，系统不会"少做一步"，而会**编一个做完了的答案** —— 比不做更糟。

#### 2.5 ★ 为什么提示词不够，必须加确定性兜底

提示词是**软约束** —— 模型可以不听。上面两轮测试就是证据：加了硬规则后，
它有时听、有时不听。

所以加一层代码级的核验：记录本轮**真正成功执行过**的工具，在返回答案前检查：

```
声称办过事（"已提交""退货单号"…） && 没真调用过写工具  →  判定为编造，改写答复
```

四种情况都测过：

| 场景 | 结果 |
|---|---|
| 真调了写工具 + 声称办理 | 放行 |
| **没调写工具 + 声称办理** | **拦截** |
| 没调写工具 + 纯政策回答 | 放行（正常问答不该被误伤） |
| 调了工具 + 纯查询 | 放行 |

拦截后的答复会明确告诉用户"本次**并未成功提交**，单号无效"。
**宁可承认没办成，也不能让用户以为办成了。**

> 这类"输出后校验"的思路在 Agent 系统里很常用：**不要相信模型说了什么，要核验它做了什么。**

#### 2.6 ★★ 发现的第三个问题：项目级的工具注册 bug

这个最有意思。`submit_return_request` 需要 4 个参数，调用时报：

```
Too many arguments to single-input tool submit_return_request.
```

顺着查下去，一路查到 `langchain_core/tools/simple.py` 的源码：

```python
args, kwargs = super()._to_args_and_kwargs(tool_input, tool_call_id)
# For backwards compatibility. The tool must be run with a single input
all_args = list(args) + list(kwargs.values())
if len(all_args) != 1:
    raise ToolException(f"Too many arguments to single-input tool {self.name}. "
                        "Consider using StructuredTool instead.")
```

**`Tool` 其实就是 `SimpleTool`，它硬编码了"只能有一个参数"** —— 加 `args_schema` 也没用，
因为它是在参数已经绑定完之后才数的个数。报错信息自己给了答案：用 `StructuredTool`。

而项目的 `register_tool()` 用的正是 `Tool`。

**为什么这个 bug 一直没被发现？** 因为项目原有的工具**恰好都只需要 1 个参数**：

| 工具 | 参数 | LLM 实际怎么传 |
|---|---|---|
| `hybrid_search` | query, top_k, vector_weight | 只传 query，其余走默认值 → 1 个 arg → **侥幸通过** |
| `query_order` | order_id | 只有 1 个 → 通过 |
| `create_ticket` | issue, user_id, priority | **只要 LLM 同时传 2 个就会失败** ← 一直是坏的 |

所以这不是"新工具引入的 bug"，而是**新工具把一个潜伏已久的 bug 暴露了出来**。
`create_ticket` 从写下的那天起，只要模型同时传 `issue` + `user_id` 就调不通。

**修法**：`register_tool` 改用 `StructuredTool.from_function()`，
用调用方**已经写好的 `parameters` 声明**生成 Pydantic `args_schema`。

```python
args_schema = _build_args_schema(name, parameters, actual_func)
tool = StructuredTool.from_function(func=actual_func, ..., args_schema=args_schema)
```

修完 6 种调用方式全部通过（多参、单参、显式覆盖默认值、缺必填报错、schema 格式不变）。

**这个 bug 教了三件事：**

1. **「一直能跑」和「是对的」是两回事。** 原来的工具单参数调用能过，不等于注册方式正确。
2. **潜伏 bug 会因为"幸存者偏差"长期存活** —— 所有现存用法恰好绕开了它。
3. **遇到第三方库的报错，去读它的源码比猜快得多。** 我一开始猜是 `is_single_input` 的问题，
   打印出来发现它其实是 `False`，说明猜错了方向；直接 grep 错误信息定位到源码，
   一眼就看到是 `len(all_args) != 1` 的硬编码。

#### 3.1 该动手看的

   看它怎么把 JSON Schema 声明翻译成 Pydantic 模型（`create_model` 是 Pydantic 的动态建模入口）

#### 3.2 背后的通用概念

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **ReAct 循环** | Think → Act → Observe 反复直到收敛 | Agent 的基本形态；理解它才知道为什么会"演" |
| **工具调用（Function Calling）** | 把函数签名+描述交给 LLM，由它决定何时调 | Agent 的手脚 |
| **幻觉的两种形态** | ①答错内容 ②**描述没发生的事** | 第二种更危险 —— 它看起来完全正常 |
| **软约束 vs 硬约束** | 提示词是软的（可违背），代码校验是硬的（必执行） | 关键路径上的正确性必须靠硬约束 |
| **输出后校验（post-hoc validation）** | 生成完再核验，不信任生成结果 | Agent 系统里最有效的防幻觉手段之一 |
| **显式传参 vs 对象状态** | 能走参数就别挂 self | 并发场景下对象状态极易串号 |
| **SimpleTool vs StructuredTool** | LangChain 里前者只收单参数 | 用错会踩"多参数静默不可用"的坑 |

- `max_iterations` 设小了会发生什么？为什么说它是正确性参数而不是性能参数？

- LangChain 的 `Tool` 和 `StructuredTool` 本质区别是什么？怎么一眼判断该用哪个？
- 这个工具注册 bug 为什么能潜伏那么久没被发现？

### 1. 思路

阶段 3 前半段让 Agent 能改数据了。**能改数据 = 能造成不可逆后果** ——
用户收到一个工单号，商家那边就得有人处理。所以必须配一道审批。

困难不在"要不要审批"，而在**信号怎么从 Agent 传到编排层**。

### 2. 为什么这么设计

#### 2.1 核心难点：Agent 只返回一个字符串

`AgentProtocol` 规定接口是 `handle(query, context) -> str`。写操作发生了，但返回值里没有
结构化的位置可以放"我改了数据"这个事实。三条路都试过：

| 方案 | 为什么不行 |
|---|---|
| 在返回值里插机器标记 | 标记会漏进最终答复，污染用户可见文本 |
| 挂在 `self` 上（实例属性） | **Agent 实例全局共享**，并发请求互相覆盖，A 的退货会触发 B 的审批 |
| `context` 字典 | `context` 是节点函数里的**局部变量**，但它是**可变对象**，Agent 往里写、节点读得到 —— 理论可行，但工具函数拿不到 `context` |

最终选了**线程本地存储**（`threading.local`），因为：
- `handle()` 是在节点函数里**同步**调用的 → Agent 与节点在同一线程
- 每个请求各写各的副本，天然隔离
- 不污染返回值，也不需要穿透 `context`

#### 2.2 ★ 一个差点埋下的坑：工具可能跑在线程池里

写完线程本地方案后我复查了工具的**执行路径**，发现：

```python
if len(unique_calls) > 1:
    with ThreadPoolExecutor(max_workers=...) as pool:   # ← 并行执行
        ...
```

**LLM 一次调用多个工具时，它们跑在 worker 线程里。** 如果写操作的登记放在
工具函数（CRM）内部，就会登记到 worker 线程的副本上 —— 节点线程读不到，**信号直接丢失**。

更糟的是：线程池的线程**会被复用**。残留的记录可能被下一个恰好调度到该线程的请求读到，
**变成跨用户串号**。

所以把登记从 CRM 挪到了 Agent 的工具分发层，在**调用线程**里做：

```python
# _execute_tool_calls 里，所有工具都执行完之后（此时回到调用线程）
self._record_write_operations(tool_results)
```

**教训：用线程本地/上下文变量时，先确认代码有没有开线程池。**
「同一个逻辑调用」不等于「同一个线程」。

> 这个 bug 还有一个隐蔽之处：如果用单工具调用的场景去测，它**完全正常**。
> 只有 LLM 恰好把两个工具放在一轮里，才会出问题。这类"条件触发"的 bug
> 靠手测很难覆盖，必须靠**读代码确认线程模型**。

#### 2.3 闸门放在哪：不看措辞，只看事实

原有的写操作审核是这样判断的：

```python
if "database" in selected_agent and any(kw in query.upper() for kw in ["INSERT","UPDATE",...]):
```

两个失效点：① 建工单发生在售后 Agent 内，Agent 名里没有 "database"；
② 用户说的是中文"我要退货"，永远不可能命中 SQL 关键字。

新的闸门换了个判据 —— **不看用户怎么说、也不看 Agent 叫什么，只看"数据是不是真的被改了"**：

```
Agent 执行写工具 → 登记 → 节点写入 state["write_operations"] → 闸门据此触发
```

这比"猜意图"可靠得多。**判断副作用时，事件驱动比意图推断可靠。**

#### 2.4 审批界面要给人看的东西

拦截时不能只丢一个 `True` 出去，得让审批人明白在批什么：

```
创建售后工单 TK20260916004，分类 退货，优先级 high
[approved] 确认无误，放行给用户
[abort]    不认可，终止本次回复
```

顺带修了一个既有 bug：`resume_after_human_input` 里
`reason = current_state.values.get("intervention_reason", "")` ——
`.get(key, "")` 只在**键不存在**时给默认值，键存在但值是 `None` 时会返回 `None`，
下一行的 `"任务规划" in reason` 直接抛 `TypeError`。改成 `or ""`。

### 3. 验证结果

```
[1] mode=planning           介入=False          ← 走复杂路径，规划审批
[2] mode=planning           介入=False
[3] mode=human_intervention 介入=True  原因=已完成写操作，等待人工确认
    摘要: ['创建售后工单 TK20260916004，分类 退货，优先级 high']
    --- approved 后 ---
    mode: planning  success: True
    答复: ... 工单号 TK20260916004 ...
```

**注意 [1][2] 和 [3] 结果不一样** —— 路由本身有随机性（`temperature` 不为 0），
同一个问题有时走简单路径、有时走复杂路径。测 Agent 系统时要有这个预期，
**单次通过不等于稳定通过**，关键路径值得连跑几次。

### 4. 顺带发现的两个问题（未修，留给阶段 6）

1. **外键没有生效**：建库脚本写了 `FOREIGN KEY (user_id) REFERENCES customers(user_id)`，
   但 SQLite **默认不校验外键**，需要显式 `PRAGMA foreign_keys = ON`。
   所以往 tickets 里塞一个不存在的 user_id 是能成功的。
2. **Agent 会臆造用户ID**：实测它给工单填了 `U87654321` —— 库里根本没有这个用户。
   已加提示词约束（"不要臆造 ID，从 query_order 的结果里取 user_id"），
   但**根治要靠外键约束把它挡住**，那是阶段 6 回归验证时要补的。

> 这两个问题合起来说明一件事：**光有 schema 声明不等于有约束**。
> `FOREIGN KEY` 写在建表语句里只是个文档，不开 pragma 就没有执行力。

#### 5.1 该动手看的

1. **读 [core/write_ops.py](core/write_ops.py)** —— 全文不到 80 行，注释讲清了"为什么必须是线程本地"
2. **看 [nodes.py](langgraph_orchestrator/nodes.py) 里 `consume_write_ops()` 的位置** ——
   为什么必须在 `handle()` 之后、且必须在 `except` 分支里也清一次
3. **看 [enhanced_nodes.py](langgraph_orchestrator/enhanced_nodes.py) 的闸门分支** ——
   对比它和下面那段"数据库写操作审核"的判据差异

#### 5.2 背后的通用概念

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **线程本地存储** | 每个线程一份变量副本 | 并发下隔离状态的最轻量手段 |
| **线程池与上下文传播** | 任务跑在哪个线程，上下文变量就跟到哪 | 用了 ThreadLocal/contextvar 就必须先确认线程模型 |
| **线程复用污染** | 池里的线程会被后来的任务复用 | 残留状态会跨请求串号，比"丢信号"更难查 |
| **副作用审计（audit trail）** | 记录"谁在什么时候改了什么" | 任何写系统的必备能力，也是审批的依据 |
| **人机协同（human-in-the-loop）** | 关键动作前暂停，等人确认 | Agent 落地的关键设计；LangGraph 用 interrupt 实现 |
| **事件驱动 vs 意图推断** | 靠"发生了什么"而非"猜用户想干嘛"来决策 | 前者可靠，后者易被措辞绕过 |

- 工具跑在线程池里时，线程本地存储会怎么失效？失效后**最坏**的后果是什么？
  （提示：不只是丢信号）
- 为什么新闸门用"数据被改过"当判据，而不继续用关键词匹配？
- `.get(key, default)` 和 `or default` 有什么区别？各自的陷阱是什么？
- 为什么同一句提问，连跑三次可能得到不同的路径？

### 1. 思路

这套系统的路由是**两级**的：

```
用户提问
   ↓
① 向量召回  —— 把「提问」和「每个 Agent 的描述+能力」都做 embedding，取余弦相似度 top-3
   ↓
② LLM 精排  —— 把这 3 个候选连同规则一起给 LLM，让它选，并允许它从候选外挑
```

**两级意味着有两个调节杠杆，而且都得调** —— 只改一处的效果会被另一处稀释。

### 2. 为什么这么改

#### 2.1 Agent 的描述不是文档，是"检索键"

绝大多数项目里，`description` 只是给人看的注释。**但在这里它会被向量化，直接决定召回结果。**

原来的描述是这样的：

```
database_agent:  "专门处理数据库查询任务，擅长SQL生成、表结构探索、数据分析。"
customer_service_agent: "专门处理客户咨询、投诉、工单管理。"
```

用户问「我的快递到哪了」，这两句里既没有"快递"也没有"物流"，**向量相似度自然上不去**。
排名靠前的候选可能是 knowledge_agent（因为"检索"这个词面接近）。

所以我按「用户真实会怎么说」来重写：

```
database_agent:  "查询交易数据：订单状态与详情、物流轨迹与签收时间、退款记录与进度、
                  会员等级与消费统计…适合「我的订单到哪了」「退款到账了没」这类查数据的问题。"
customer_service_agent: "处理电商售后业务：退换货政策咨询、提交退货换货申请、退款规则、
                  运费规则、投诉与工单…适合「我要退货」「耳机坏了怎么办」这类问规则或要办理的问题。"
```

**关键动作是：把用户的说法直接写进描述里**（"到哪了""坏了""谁出"）。
这是在用自然语言给向量检索"种锚点"。

> 和阶段 1 那个道理是同一条：**写给 RAG 用的文本要具体，要贴近真实问法。**
> 阶段 1 是文档，阶段 4 是 Agent 描述，同一件事的两个面。

#### 2.2 为什么在描述里明说"什么不该找我"

注意新描述都带了边界句：

```
knowledge_agent: "…不涉及售后业务；售后政策、退换货规则、退款时效属于客服Agent的职责。"
```

**为什么要写"不归我管"？** 因为向量召回只算相似度，不算边界。"售后政策是什么"和"什么是X"
在向量空间里是近邻 —— 不写清楚，knowledge_agent 会一直抢客服的活。

**给检索系统写描述时，负向边界和正向能力一样重要。**

#### 2.3 一个被质疑过的设计决定：政策问答给谁？

按能力看，`knowledge_agent` 是检索专家（15 个纯检索工具），售后政策问答交给它很自然。
但最后我把政策划给了 `customer_service_agent`。理由：

- 客服 Agent 自己就能检索（它也有 hybrid_search / vector_search / keyword_search）
- 政策问答**常常和办理连着**：用户问"能退吗"，下一句就是"那帮我退了吧"。
  走客服 Agent 能连着办；走 knowledge_agent 就断在"只能回答"了
- 它还有售后人设（提示词里写了 4 个业务陷阱），回答质量更稳

代价是 `knowledge_agent` 退到了"非售后的通用知识"，边界依赖描述里的负向说明来维持。
**这是个权衡，不是唯一答案** —— 如果哪天政策问答量很大而办理很少，反过来的分工更合理。

#### 2.4 planner 的示例也是"隐式文档"

阶段 2 我们聊过 few-shot 示例其实是 schema 文档。到了 planner 这里，**示例直接定义了系统怎么拆任务**。

原来的两个示例讲的是"查 Eduardo Martins 的消费记录"和"对比向量数据库图数据库"。
新场景下它们不仅没用，还会**误导模型按旧模式拆解**。

换成两个**恰好演示两种 DAG 形态**的示例：

| 示例 | 演示什么 |
|---|---|
| 「订单 X 的耳机坏了，帮我办退货」 | **有依赖**：先查订单 → 再据订单办理（串行，`depends_on` + `parameter_mapping`） |
| 「看看哪些订单没发货，超时怎么赔」 | **无依赖**：查数据 ‖ 问规则（并行） |

这两个示例合起来，把编排系统最核心的两种拓扑形态都示范了一遍。
**示例选得好，等于不用解释就说明了"什么时候该串、什么时候该并"。**

### 3. ★ 一个我自己犯的错，值得单独记

**我在动手前说过一句话：**

> 「`router.py:345` 的 `"customer_agent"` 是过期 id，**整条关键词规则失效**，静默降级。」

**这句话是错的。** 后来我去查证，发现那个函数 `route_simple()`：

```
$ grep -rn "route_simple" --include="*.py" .
orchestrator/router.py:329:    def route_simple(...)      ← 只有定义，没有任何调用
```

**它全项目无人调用，是死代码 —— 从来没参与过任何一次路由。**
既然没被执行，"失效"就无从谈起。

**我错在哪：** 我看到 id 对不上（`customer_agent` vs `customer_service_agent`），
就直接得出"功能坏了"的结论。但我**没有先确认这段代码是否会被执行**。

```
看到代码有问题          ≠  这个功能坏了
                              ↑ 中间差一步：它到底跑没跑？
```

**死代码的问题不是"坏了"，而是"根本没在跑"—— 这两者的修复方式完全不同：**
- 坏了 → 去修它
- 没跑 → 要么删掉，要么接上；**修它是白费功夫**

这也是我最终**删除而不是修复** `route_simple()` 的原因。

> 顺带一提：`planner._create_simple_plan()` 里有同样两个过期 id
> （`code_agent` / `customer_agent`），**那个是真在回退路径上的**，所以修的是它。
> 同样是"过期 id"，一个该删、一个该修 —— 差别就在于**是否在执行的路径上**。

### 4. 人类怎么学这部分

#### 4.1 该动手看的

1. **读 [orchestrator/router.py](orchestrator/router.py) 的 `route()`**（46-99 行）——
   二十来行看完整的两级路由；顺带注意第 80 行的"前置拦截"（闲聊直通），
   那是**先做便宜判断、再做昂贵判断**的经典写法
2. **在 [enhanced_entry.py](langgraph_orchestrator/enhanced_entry.py) 里改一个 Agent 的 description**，
   加几个用户常说的词，重跑路由测试，看命中率怎么变 —— **亲手感受"描述即检索键"**
3. **跑一遍 `route_simple` 的搜索**：`grep -rn "某个函数名" --include="*.py" .`
   看它有没有调用者。这个动作值得养成习惯，尤其在准备改一段代码之前
4. **读 planner 的两个新示例**，回答：为什么示例一必须串行、示例二可以并行？

#### 4.2 背后的通用概念

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **语义路由（semantic routing）** | 用向量相似度把请求分发给处理器 | Agent 系统最常用的路由方式 |
| **两级召回 + 精排** | 便宜的粗筛 top-k，再用贵的模型精选 | 推荐/搜索/路由的通用范式，省成本 |
| **描述即接口** | 在 LLM 系统里，description 是给模型读的**输入**，不是注释 | 改描述等于改行为 |
| **负向边界** | 明确写"不归我管" | 检索只算相似度不算边界，不写就会抢活 |
| **死代码识别** | 先确认执行路径，再判断"坏没坏" | 直接影响你该修还是该删 |
| **DAG 拓扑** | 串行（有依赖）vs 并行（无依赖） | 编排系统的基本形态 |

#### 4.3 看完应该能回答的问题

- 为什么 Agent 的 `description` 能决定路由结果？它经历了什么处理？
- 为什么要写 `capabilities` 而不只写 `description`？（提示：看 `route()` 里拼的是什么）
- 把售后政策划给客服 Agent 而不是知识 Agent，理由是什么？代价是什么？
- **看到一个"过期 id"，你会先做什么再决定修还是删？**
- 示例里演示"串行"和"并行"两种 DAG，为什么这两种就够了？

## 待评估项 · 知识图谱 + 用户画像

> 日期：2026-09-16　　状态：**评估后决定暂不实施**（触发条件见 [study.md](study.md) §7.1）

### 1. 思路

有人提出：能不能加一个知识图谱（从内容里抽实体关系来构图），并且加上用户画像、记录用户习惯？

我没有直接开工，而是先做了三件事：

1. **查证现状** —— 别凭印象回答"有/没有"
2. **拆解问题** —— 这其实是两个独立系统，不是一件事
3. **定触发条件** —— 说清"什么情况下该做"，而不是简单地说"不做"

### 2. 为什么决定不做

#### 2.1 先查证：差点重复造轮子

**这一步的价值超出预期。** 我原以为"实体关系抽取"要新写，查完发现：

[rag_core/concept_extractor.py](rag_core/concept_extractor.py) **已经在抽概念和关系了** ——
`extract()` 会返回 `concepts`（含权重、提及次数、出现在哪些文档）和 `relations`（源、关系类型、目标），
并且已经被 `knowledge_agent` 调用。

**但它不是"图谱"。** 差别在于：

| | 概念提取器（现状） | 图谱（提议中的） |
|---|---|---|
| 生命周期 | **每次查询现算**，用完就扔 | 持久化，跨查询累积 |
| 范围 | 只看这一轮检索到的文档 | 全量内容 |
| 用途 | 辅助理解当前这批文档 | 支撑跨文档的关系推理 |

**这个区别很关键：它们的名字听起来像，解决的是完全不同的问题。**
如果我不查就动手，很可能写出一个和 `ConceptExtractor` 高度重叠的东西。

> **先查证现有能力，再决定要不要新建** —— 这一步花五分钟，能省掉几天。

#### 2.2 没有失败案例支撑

任何架构扩张都该有个理由。现在的状态是：

- 阶段 1：6 个检索问题，**top-1 全部命中**
- 阶段 4：7 个路由用例，**全部正确**

**RAG 还没表现出失败。** 在没有失败案例的情况下加图谱，是在解决一个**还没出现的问题**。

我确实看到一个"可能的"价值点 —— 主场景订单是「已激活的无线耳机」，
判断它属不属于七天无理由的例外，本质是「商品类别 → 政策条款」的关系推理。
**但那个现在靠提示词 + 检索也能过。** 所以它不构成理由，只能算一条待观察的线索。

正确的做法是：**先压测、收集失败案例，看它们有没有共性。**
如果一批失败都是"需要跨文档关系"，图谱就有依据；一个都没有，加了就是白加。

#### 2.3 两件事不该捆在一起

"加图谱"和"记用户习惯"听起来是一套，其实是两个系统：

| | 知识图谱 | 用户画像 |
|---|---|---|
| 数据源 | 文档内容 | 用户行为 |
| 更新时机 | 内容变更（低频） | 每次交互（高频） |
| 风险 | 抽取质量、**图谱腐烂** | **隐私合规** |

尤其是画像那条：售后系统记录"这个用户常退什么货"，**不是技术问题，是合规问题。**
这个必须在设计之初就摆到桌面上，而不是做完再说。

#### 2.4 但经验是现成的

归档的 coach 项目解决的就是这两个问题，而且留下了几条硬结论：

- 图存储用 **SQLite + 递归 CTE**，不引入图数据库（够用，少一个依赖）
- 关系类型**收敛成有限几类**，不做开放式（否则图谱很快变成一团乱麻）
- **LLM 抽取的关系不直接入库** —— 走 `observation → proposal → aggregator` 治理链路

最后这条最值钱：**LLM 抽出来的关系是"提案"，不是"事实"。**
直接入图，等于把模型的幻觉当成知识永久沉淀下来，而且**错了也看不出来** ——
因为图谱里的东西看起来都像那么回事。

### 3. 人类怎么学这部分

#### 3.1 背后的通用概念

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **YAGNI** | You Aren't Gonna Need It —— 不要为假设的未来需求写代码 | 这条决策就是 YAGNI 的一次实践 |
| **证据驱动架构** | 先有失败案例，再有方案 | 反过来做就是"技术找场景"，多半白干 |
| **知识图谱 vs 向量检索** | 前者答"关系"，后者答"相似" | 两者互补而非替代，先搞清缺的是哪个 |
| **图谱腐烂（graph rot）** | 内容更新了，关系还停在旧状态 | 图谱类系统最大的长期运维成本 |
| **LLM 输出的治理链路** | 模型产出走"观察 → 提案 → 聚合"再入库 | 把幻觉挡在数据层之外 |
| **隐私合规边界** | 哪些数据能记、记多久、谁能看 | 涉及用户行为的系统绕不过去 |

#### 3.2 看完应该能回答的问题

- 「概念提取器」和「知识图谱」名字很像，本质差别在哪？（提示：生命周期和范围）
- 为什么"没有失败案例"就构不成做新架构的理由？
- LLM 抽出来的关系为什么不能直接入库？直接入库最坏会怎样？
- 如果让你给"什么时候该做图谱"定一条可操作的触发条件，你会怎么定？

## 阶段 5 · 前端与文案

> 日期：2026-09-16　　commit：见文末

### 这阶段实际做了什么

| # | 动作 | 文件 |
|---|---|---|
| 1 | 页面标题、顶栏、欢迎屏文案改为售后场景 | [frontend/index.html](frontend/index.html) |
| 2 | **重写示例问题** —— 按"执行路径"而不是按主题来选 | 同上 |
| 3 | 输入框 placeholder 改成带示例的提示 | 同上 |
| 4 | 监控页标题同步 | frontend/monitor.html |
| 5 | FastAPI 的 title / description / health 服务名 | [api.py](api.py) |

**验证**：起了真实服务，走 HTTP 端点把链路跑通（**但没有在浏览器里点过**，见 §4）。

### 1. 思路

这阶段的代码改动很小（都是文字），但有一个设计点值得说清楚：**示例问题不是装饰，是路径导航。**

### 2. 为什么这么改

#### 2.1 示例问题按「执行路径」选，而不是按「主题」选

原来的示例是四个 RAG 技术问题。新的示例是按**系统内部的五条不同路径**来挑的：

| 示例问题 | 会走到哪条路径 |
|---|---|
| 「七天无理由退货的时间怎么计算？」 | 简单路由 → 客服 Agent → 混合检索 → 直接回答 |
| 「订单 SO20260909001 现在什么状态？」 | 简单路由 → 数据库 Agent → Text-to-SQL |
| 「订单 …的耳机右耳没声音，我要退货」 | 复杂路径 → planner 生成**有依赖**的 DAG（查订单 → 办理） |
| 「还有哪些订单没发货，超时怎么赔？」 | 复杂路径 → planner 生成**无依赖**的 DAG（两个任务并行） |
| 「我要投诉！退款到现在没到账」 | 情绪识别 → 工单优先级 → **写操作审批** |

**为什么这样选？** 因为示例问题实际承担了**演示脚本**的作用 —— 用户点一下就能看到系统内部走了哪条分支（右侧 trace 面板会展开）。
如果四个示例都走同一条路径，那演示价值就浪费了四个位置。

> 这和前面几个阶段是同一个道理的延续：**阶段 2 的 few-shot 示例是给 LLM 看的"隐式文档"，
> 阶段 5 的示例问题是给用户看的"路径导航"** —— 都是"用例子代替解释"。
> 区别只在于读者是谁。

顺带：示例里的订单号 `SO20260909001` 是**演示库里真实存在的**，点了就能跑出结果 ——
示例问题如果是编的，用户第一次点击就撞墙。

#### 2.2 为什么把品牌也一起改了

`/health` 返回的还是 `"service": "RAG Agent API"`，FastAPI 文档页标题也还是 `RAG Agent API`。
这些地方用户不一定看得到，但**它们会被截图、会被写进接口文档、会在对接时被对方看到**。
一个对外叫「云集优选 · 售后助手」、接口文档叫「RAG Agent API」的系统，会让人怀疑是不是半成品。

**改文案不只是改界面，是把"对外身份"统一。** 这是个很容易漏的地方 —— 因为改界面时你会盯着看得见的部分。

### 3. 验证过程（以及一个真实的坑）

#### 3.1 没有停在"HTML 看起来对"

改完文案后，最省事的"验证"是打开文件看一眼 —— 但那什么都没验证到。
我起的是真实服务：

```bash
python api.py &
curl http://localhost:8000/health          # 健康检查
curl http://localhost:8000/ | grep title    # 页面标题
```

然后**走真实 HTTP 端点把链路跑完**：

| 请求 | 得到 |
|---|---|
| `POST /chat` 问订单状态 | `mode=simple`，database_agent，答对 |
| 同一 thread 追问「那它是什么时候签收的？」 | **指代消解成功**（"它"→订单），答对 |
| `POST /chat` 要求退货 | `mode=human_intervention`，摘要含真实单号 RF20260916005 |
| `POST /resume` 传 `approved` | `success=True`，最终答复引用同一个单号 |

**最后一问还顺带验证了业务逻辑的正确性**：答复把它判定为**质量问题**（15 日、运费平台承担），
而不是七天无理由 —— 那个埋在知识库里的 3C 例外设计，在真实链路上生效了。

#### 3.2 两个具体的坑

**坑一：curl 传中文 JSON**

```bash
curl -X POST ... -d '{"query":"订单 ... 现在什么状态？"}'
# → {"detail":"There was an error parsing the body"}
```

中文在 Windows shell 里经过了一层编码转换，到了服务端已经不是合法 JSON。
改成**把 body 写进文件、用 `--data-binary @file` 传**就正常了。

> 经验：**只要是含非 ASCII 的请求体，就别用命令行内联。** 写文件传，省掉一整类编码问题。

**坑二：改完代码，正在跑的服务不会自动加载**

我改完 `api.py` 后，`/health` 返回的**仍然是旧服务名** `RAG Agent API`。
这不是 bug —— 是 Python 已经把旧代码加载进内存了，进程不重启就不会变。

**这个现象反而是个有用的信号**：它证明"服务确实在跑启动时的那份代码"。
以后遇到"我明明改了怎么没生效"，先想想是不是这个原因。

#### 3.3 停服务时踩到的

`taskkill /PID <父进程>` 之后端口**仍然被占用**。查下来发现：

```
python.exe  PID 7244
  spawn_main(parent_pid=15192, ...)   ← 是父进程派生的子进程
```

uvicorn 会 spawn 子进程干活，**杀掉父进程不会连带杀掉子进程**，它成了孤儿继续占着 8000 端口。
用 `taskkill /F /T`（`/T` = 连同子进程树）或者单独杀掉子进程才行。

> 这也是个通用现象：**进程树里的"父"死了，"子"不一定跟着死。**
> 排查端口占用时别只看父进程。

#### 4.4 ★★ 浏览器实测抓到一个 HTTP 测试漏掉的真 bug

这是本次验证最有价值的产出。**所有 HTTP 层测试都没能发现它。**

**现象：** 用户在浏览器里要求退货，模型的答复是：

> 「我已为您**立即创建了售后工单并提交了退货申请**。」

**但查数据库 —— 什么都没有。** 弹窗也没出现（说明确实没有写操作）。

**也就是说：模型撒了谎，而阶段 3 加的那道防幻觉兜底没有拦住它。**

**根因：** 最初的实现用的是**固定子串匹配**：

```python
_CLAIM_MARKERS = ("已为您提交", "已提交", ..., "已为您创建", "已创建工单", ...)
hit = next((m for m in _CLAIM_MARKERS if m in answer), None)
```

模型写的是「已为您**立即**创建了」—— 中间插了一个副词「立即」，
于是 `"已为您创建" in answer` 为 `False`。**9 条规则全部落空。**

**修法：** 改成允许插入副词的**正则**：

```python
_CLAIM_PATTERNS = (
    r"已(?:为您|已经|经|帮您)?(?:立即|马上|即刻|立刻|成功)?(?:提交|受理|创建|生成|办理|发起|处理)",
    r"(?:提交|创建|生成|发起|办理)(?:了|好|完成)(?:.{0,6})?(?:申请|工单|售后单|退换)",
    r"(?:申请单号|退货单号|退款单号|工单号|受理号|单号)\s*[:：]",
)
```

改完验证：**4 条编造措辞全部拦下，4 条正常政策回答零误伤。**

#### 4.5 为什么原来的回归测试没抓到它

这一点比 bug 本身更值得记。

`test_05` 里用的测试数据是**我自己手写的**：

```python
lie = "已为您提交退货申请，单号 RF20260916001"
```

这句话**恰好命中了子串**，所以测试是绿的。

而模型真实吐出来的是「已为您**立即**创建了」—— 我的样例反映了**我的预期**，
模型的实际输出**不服从我的预期**。

> **用自己的样例测自己的检测逻辑，会形成一个结构性的盲区。**
> 你写的示例只能覆盖你想得到的说法；而你要防的东西，恰恰是想得到之外的那些。
>
> 这也解释了为什么"浏览器点一遍"和"手工编用例"不能互相替代 ——
> 前者是拿**真实的模型输出**喂给检测逻辑，后者是拿**你以为的输出**。

修复之后，那条**曾经逃逸的原句**已经被固化进 `test_05`，
所以这个具体的坑不会再出现第二次。

#### 4.8 查不到根因时，至少要让故障可见

起因是那个未解决的渲染问题。LLM 用不了（欠费），端到端复现不了，
但**静态读代码**发现了一处前端脆弱点，而它恰好能完整解释我观察到的现象。

**三行代码凑成一个"静默失败"：**

```js
} else if (type === 'final') {
    removeElement(progressEl);        // ① 先把进度条删掉
    ...
    appendBotMessage(answer, ...);    // ② 再渲染答复
}

// 外层：
try { handleSSEEvent(event, ...); }
catch (e) { console.warn('SSE parse error', e); }   // ③ 异常只打日志，不上界面
```

```js
function appendBotMessage(text, ...) {
    ...
    const sourcesMatch = text.match(/<!-- SOURCES:.../);   // ④ text 不是字符串就抛
```

**合起来的后果**：只要渲染那一步抛了异常（最常见的原因是 `text` 不是字符串，
而 `handleSSEEvent` 里 `result.result` 是直接透传的），就会变成
**进度条消失 → 没有答复 → 也没有任何报错**。用户完全不知道发生了什么。

**这正是我在浏览器里看到的那一幕。**

**三处修复：**

1. **调换顺序**：先渲染、成功后再移除进度条。渲染失败时进度条还在，至少说明"卡住了"
2. **异常上界面**：把 `console.warn` 改成 `console.error` + 在对话里显示一条可见的错误
3. **入参兜底**：`appendBotMessage` 开头检查 `text` 是否为字符串，不是就转成字符串

**验证**（不需要 API，直接往页面注入合成事件）：

```
appendBotMessage(null)      -> 兜住，不抛异常 ✓
appendBotMessage({})        -> 兜住，不抛异常 ✓
正常 final 事件             -> 正常渲染 +1 条消息、进度条被移除 ✓
```

> **这条经验比具体 bug 更有价值：**
> **查不到根因的时候，至少要让故障"可见、可诊断"。**
>
> 一个静默吞异常 + 什么都不显示的失败，是最难排查的 ——
> 用户只能说"它没反应"，而你能拿到的线索是零。
> 把异常暴露出来，下一次它再发生时，你至少知道是**哪儿**、**为什么**。

### 2. ★ 外键：一个"声明了但没生效"的典型

阶段 3 我记下过一个现象：模型给工单填了 `U87654321`，**库里根本没这个用户，却写进去了**。

原因不在代码逻辑，而在建表语句：

```sql
CREATE TABLE tickets (
    ...
    FOREIGN KEY (user_id) REFERENCES customers(user_id)   -- ← 这只是一个声明
);
```

**SQLite 默认 `PRAGMA foreign_keys = OFF`。** 上面这行在库文件里存着、用工具打开也看得见，
但**它不执行任何校验** —— 相当于一条注释。

这正是我在阶段 3 那句「光有 schema 声明不等于有约束」的具体含义。

修法是连接时显式打开：

```python
def _connect(self):
    conn = sqlite3.connect(self.db_path)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA foreign_keys = ON")     # ★ 这一行才是真正的约束
    return conn
```

#### 2.1 修的过程中又发现两处漏声明

打开校验之后我顺手核对了一遍所有外键，发现：

| 表 | 漏掉的外键 | 后果 |
|---|---|---|
| `tickets` | `order_id → orders.order_id` | 工单能关联到一个**不存在的订单**（实测塞进过 `SO99999999`） |
| `refunds` | `user_id → customers.user_id` | 退款单的申请人可以是幽灵用户 |

**有意思的是：这两处是"打开校验"这个动作顺带暴露出来的。**
如果我没去开 pragma，就不会去想"还有哪些外键没声明" ——
**做一次加固，常常会顺带照亮旁边的问题。**

#### 2.2 一个必须一起改的细节：匿名工单

打开外键后会立刻撞上一个问题：原来 `create_ticket` 会把空的 user_id 写成字符串 `"anonymous"`：

```python
user_id or "anonymous"      # ← 假用户，外键会直接拒绝
```

改成 `user_id or None`，让它在库里是 **NULL**，代表"匿名咨询"。

**这里有个容易混淆的点：外键允不允许 NULL？**
允许。外键的语义是"**如果给了值，这个值必须存在**"，而不是"必须给值"。
所以 NULL 是合法的空，`"anonymous"` 是非法的假。

> 「空值」和「假值」是两回事。用占位符（"anonymous"、"unknown"、0、"N/A"）
> 去填一个真正该为空的位置，是很多脏数据的源头。

#### 2.3 结果：臆造的 ID 现在被数据库拦住

```
真实用户 + 真实订单  -> 通过  TK20260916004
臆造用户            -> 拒绝：用户 'U87654321' 在系统中不存在。请先用 query_order 查出订单的真实归属用户
匿名（无 ID）       -> 通过  TK20260916005
臆造订单号          -> 拒绝：订单 'SO99999999' 在系统中不存在
```

注意拒绝时返回的**不是一个数据库异常堆栈，而是一句给 Agent 看的可读提示**：

```python
except sqlite3.IntegrityError as e:
    return {"error": "工单创建失败：用户 ... 在系统中不存在。请先用 query_order 查出订单的真实归属用户，再重试。"}
```

**为什么要转成可读错误？** 因为错误信息是**给 Agent 看的**。
把操作指引写进错误里，Agent 拿到之后能自己纠正（去查订单、拿到真实 user_id、重试），
而不是卡在一个 `IntegrityError` 上不知所措。

> 这是个通用做法：**面向 Agent/调用方的错误，要带上"下一步该做什么"。**

### 3. 测试套件怎么设计的

#### 3.1 分两段：先跑便宜的

```
第一段（不调 LLM，秒级）  数据层与纯逻辑  6 条
第二段（调 LLM，慢）      端到端         9 条
```

**顺序是有意的。** 如果数据库是坏的，第二段那些 LLM 用例会以各种奇怪的方式失败 ——
你看到一堆红色，却不知道根因在数据库。**先跑便宜且基础的，能更快定位问题。**

#### 3.2 ★ 一个用例只测一件事：test_14 刻意绕过了路由

写操作闸门那条用例，我**没有**走完整的 `handle_query`，而是直接从注册表取出售后 Agent 调它。

**为什么？** 因为路由有随机性（`temperature` 不为 0，同一句话有时走简单路径、有时走复杂路径）。
如果这个用例走完整链路，它会**偶尔**因为"路由没送到售后 Agent"而失败 ——
但那时你无法判断是**闸门坏了**还是**路由飘了**。

绕过路由之后，这条用例只验证一件事：**写操作会被登记、能被闸门拦住**。

> 回归测试的一条基本原则：**一个用例只测一件事。**
> 测试失败时最耗时的不是修 bug，而是判断"到底哪儿坏了"。

#### 3.3 把"曾经的 bug"固化成用例

`test_05` 和 `test_02` 不是普通的正向用例，它们各自守着一个**真实踩过的坑**：

| 用例 | 守的是什么 |
|---|---|
| `test_02 外键约束生效` | 防止哪天有人把 `PRAGMA foreign_keys = ON` 删掉 |
| `test_05 防幻觉兜底` | 防止哪天有人觉得那段校验多余而删掉 |

**这两处都有一个共同特点：删掉它们，系统看起来完全正常** ——
外键不管，数据也能写进去；兜底不要，绝大多数时候回答也没问题。
**只有在出问题的那一刻才暴露。** 所以必须靠测试守住。

> 好测试保护的不是"功能"，而是"**曾经出过错的地方**"。

### 4. 测试跑的时候，护栏又拦了一次

跑第二轮用例时日志里出现了这一行：

```
[防幻觉] 答复中出现「已为您提交」，但本轮未成功执行任何写操作
        （已执行工具: ['hybrid_search', 'query_order']），判定为编造，已改写答复
```

**模型又试图"演"了一次** —— 它查了订单、检索了政策，然后就写了个"已为您提交"。
阶段 3 加的那道兜底把它拦下来了。

**这件事说明两件事：**
1. 那个问题是**稳定复现**的，不是偶然 —— 提示词约束改变不了模型的这个倾向
2. 兜底不是"以防万一"的保险，而是**每次都会用到的正常路径**

### 5. 关于删掉旧测试文件

`tests/test_system_prelaunch.py` 有 25 条用例，全部指向改造前的系统：
期望 `document_agent` 存在、问"什么是 RAG"、断言 Chinook 的销售数据。

在新系统下它们**会全部失败**。保留一个永远红的测试文件有三个坏处：
- 真正的失败会被淹没在噪音里
- 新人（或未来的你）会以为测试坏了，干脆不跑
- 会误导人以为那套断言仍然有效

新套件覆盖了同样的方面（初始化 / Agent 集合 / 路由 / 多轮 / 边界），
只是换成了售后场景。**旧的不是"删掉就没了"，它在 git 里**：
`git checkout 1c5cd18 -- nlp/tests/`。

> 这也回答了一个常见纠结：**什么时候可以删东西？**
> 当它已经失效、且**能替代它的东西已经存在**的时候。这时候留着是负担，不是资产。

#### 6.2 背后的通用概念

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **声明 vs 执行** | 写下来的约束不等于被执行的约束 | 外键、校验规则、文档承诺都属于这一类 |
| **NULL vs 假值** | 空就是空，别用 "unknown"/"N/A"/0 冒充 | 假值会污染后续所有统计和判断 |
| **面向调用方的错误设计** | 错误信息里带上"下一步该做什么" | Agent/客户端能据此自行恢复 |
| **回归测试** | 每次改动后重跑，确认没改坏 | 交付基线；也是重构的安全网 |
| **测试的失败可诊断性** | 一个用例只测一件事 | 失败时能立刻知道是哪儿的问题 |
| **"曾经出过错的地方"优先** | 好测试保护的不是功能，是教训 | 回归测试最有价值的部分 |
| **删除的判据** | 已失效 + 有替代品 = 可以删 | 否则留下的都是负担 |

### 1. 思路

前面七个阶段，判断「这件商品能不能退」靠的是**模型语义理解** —— 它读商品名、读政策例外条款，自己把两者接上。实测答对了，但：

- **讲不出依据** —— 用户质疑时只能说"系统这么判断的"
- **不稳定** —— 换个说法就可能接不上
- **答不出"不适用"** —— 向量检索只会说"相关"，说不出"排除"

所以这一步是把「商品 → 类别 → 政策适用性」**显式存成关系**，让判定变成沿关系推导。

**风险我也提前说了：这不是修 bug，是把软约束换成硬约束。** 验证重点因此不是"变好了没有"，而是**推导链是否确定、可解释、可复现**。

### 2. 三个关键设计决定

#### 2.1 条件必须外置成封闭枚举

「已激活或已拆封」不是一段自由文本，而是一个 code（`ACTIVATED`）加一组关键词。

**这样 LLM 只能从枚举里选，不能自己发明条件。** 实测里它确实试图发明过（`PREORDER`），被规则校验直接挡下了。

#### 2.2 `NULL` 和 `unknown` 是两件事

```
NULL      = 无条件生效（「生鲜类不支持换货」，天生如此）
unknown   = 有条件，但当前不确定满足没满足
```

**把 unknown 当成"适用"，会把本该被排除的商品判成可退 —— 错误方向最危险。**
代码里这个区分写在显眼位置，回归测试也专门守它。

#### 2.3 「政策族」——更具体的覆盖更泛的

通用政策（如「质量问题退货 15 日」）挂在根类别「全部商品」上；
但**家电有自己的时限（7 日）**。如果不做覆盖，家电会同时拿到 15 日和 7 日两条，
看起来像"两条都适用"，实际是"更具体的覆盖了更泛的"。

所以给政策加了 `family`（族名），**同族只保留离商品最近的那条**。

### 3. ★ 实施中发现的六个问题（这阶段最有价值的部分）

#### 3.1 递归 CTE 第一次跑就暴露了设计缺口：缺一个根类别

写完 SQL 验证时发现「质量问题退货 15 日」查不出来 —— 因为 `无线耳机 → 3C数码产品`
这条链**不包含通用类别**，没挂在专属政策上的商品会查不到任何适用政策。

**修法：加根类别「全部商品」**，通用政策挂根上，专属政策挂具体类别。

> 这类问题靠"想"是想不出来的，**必须跑一遍**。写完立刻验证的价值就在这里。

#### 3.2 规则校验拦下了 2 条**编造原文**

抽取时让 LLM 必须给出 `quote`（原文摘录）用于追溯。规则校验第一条就是：
**quote 必须是原文的精确子串，定位不到就丢弃。**

实测结果：

```
[shipping_fee_policy] 全部商品 -> 七天无理由退货: quote 不是原文子串（可能是模型编造）
[shipping_fee_policy] 定制商品 -> 七天无理由退货: quote 不是原文子串（可能是模型编造）
```

**两条引文是模型编的。** 如果直接入库，这两条假知识会永久沉淀，而且**看不出来** ——
它们看起来和真的没区别。

> 这正是"LLM 抽出来的关系是提案不是事实"的具体体现，也是必须留人工环节的理由之一。

#### 3.3 ★★ 更隐蔽的一类错误：**引文是真的，但引文不支持结论**

人工核对时发现有 4 条属于这种。最典型的一条：

```
抽取结果：大件商品 EXCLUDES 七天无理由退货
原文引文：「大件商品不适用会员免费退货次数，非质量问题的大件退货费用由消费者全额承担」
```

**引文逐字是真的**（所以规则校验放行了），但它讲的是**运费**和**会员次数**，
**根本没说不支持七天无理由退货**。

| 错误类型 | 能不能被规则挡住 |
|---|---|
| 编造引文 | ✅ 能（子串比对） |
| **真引文说假话** | ❌ **挡不住** —— 只能靠人读 |

**这是审核环节不可替代的根本原因。** 代码能校验格式，校验不了"这段原文是否真的支持这个结论"。

同类还有三条：
- 「定制商品不适用会员免费退货次数」—— 引文讲的是**「极速发货」**不适用定制商品，张冠李戴
- 「食品保健品药品不支持换货」—— 引文讲的是**申报时限（48小时）**，跟换货无关
- 「生鲜类排除七天无理由」—— 引文讲的是**凭照片退款**，不是排除无理由

#### 3.4 ★ 词表不够细 → 抽取**必然**出错

```
抽取结果：家电 APPLIES_TO 质量问题退货（15日）
原文：    家用电器类：自签收之日起 7 日内出现性能故障可退货，15 日内可换货
```

**这不是模型的错。** 我的政策节点词表里只有「质量问题退货（15日）」和「质量问题换货（30日）」，
**根本没有"7日"这个节点** —— LLM 只能从已有节点里挑，于是挑错了。

> **给 LLM 封闭词表是好事（防幻觉），但词表本身不完整时，它会"被迫出错"。**
> 这类错误的信号是：模型给出的答案**语法上完全合规**，只是不准确 —— 它选了"最接近"的选项。

修法是补两个节点（`家电质量问题退货（7日）` / `家电质量问题换货（15日）`），
然后在人工补充里加上正确的关系。

#### 3.5 ★ 通用政策挂错层级 → 兄弟类别拿不到 → **Agent 顺手编了个数字**

图谱接进 Agent 后第一次端到端测试，它说：

> 「适用政策：质量问题退货通道（**30天内**有效）」

**15 日被说成了 30 天。** 查下来根因在图谱：

- 「质量问题退货（15日）」原先挂在**「一般商品」**上
- 而 3C数码 的父是**「全部商品」** —— 两者是**兄弟**，不是父子
- 所以 3C数码 拿不到这条通用政策 → 图谱没给答案 → **Agent 自己编了一个**

**修法：通用政策挂到根类别「全部商品」上**，让所有类别都能继承；
具体类别自己的规则靠 `family` 覆盖。

> 有一个值得记住的连锁反应：**图谱查不到 ≠ 系统说"不知道"，
> 而是模型会自己补一个看起来合理的答案。**
> 所以图谱的**覆盖缺口会伪装成"回答错误"**，而不是"回答缺失" ——
> 这让它比单纯的"功能没实现"更难发现。

#### 3.6 结构冗余：抽了子类，漏了父类

第一次单篇试抽时，LLM 抽出的是：

```
内衣 EXCLUDES 七天无理由
泳衣 EXCLUDES 七天无理由
美妆个护 EXCLUDES 七天无理由
```

但没有抽**父类「贴身用品」**那条。原文写的是「已拆封的**贴身用品**，如内衣、泳衣、袜子、美妆个护类商品」——
LLM 抽了字面提到的**具体词**，没抽**上层概念**。

后果：如果有商品映射到「贴身用品」（比如袜子），就查不到这条排除。

**修法**：补上父类的排除关系，把三个子类的删掉（递归查询向上能找到）。
另外把「美妆个护」的父类别从「全部商品」改成「贴身用品」——按原文的归类来。

> **抽取倾向于抓"字面出现的词"，而不是"概念层级"。** 这是 LLM 抽取的固有倾向，
> 人工核对时要专门看这一类。

### 4. 结果

主场景（耳机的 3C 例外）现在能给出完整推导：

```
【不适用】七天无理由退货（依据：「3C数码产品」）
【适用】  质量问题退货（15日）、质量问题换货（30日）、质量问题退货运费由平台承担
```

Agent 的回答里也带上了依据：「**该商品属于「3C数码产品」，已激活/拆封后不适用「七天无理由退货」**」。

而且**去掉 Agent 的自选动作后，结论完全由图谱决定** —— 同样的输入连跑三次指纹一致。

### 5.2 背后的通用概念

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **知识图谱 vs 向量检索** | 一个答"关系"，一个答"相似" | 互补而非替代；负向关系（"不适用"）是向量检索的盲区 |
| **递归 CTE** | SQL 里做图遍历的标准手法 | 不引入图数据库也能表达层级与多跳 |
| **封闭枚举 vs 自由文本** | 让 LLM 从固定集合里选 | 可校验、可缓存；但要小心"词表不全会迫使它选错" |
| **三值逻辑** | true / false / **unknown** | unknown 的处理方向决定系统是"保守"还是"危险" |
| **提案与事实分离** | LLM 产出先进 proposed，人工核实后才 verified | 防止幻觉沉淀成知识 |
| **血缘（lineage）** | 每条结论都能追溯到原文 | 没有它，"核对"就无从下手 |
| **覆盖与继承** | 更具体的规则覆盖更泛的 | 分层规则系统的核心机制 |
| **覆盖缺口的伪装性** | 查不到答案时，模型会自己补一个 | 图谱的缺口表现得像"答错"而不是"答不出" |

#### 5.3 看完应该能回答的问题

- 为什么「不适用」是向量检索的盲区，而图谱能答？

                     capture_output=True, text=True, encoding='utf-8').stdout
new = open('nlp/langgraph_orchestrator/enhanced_graph.py', encoding='utf-8').read()
def strip(src):
    t = ast.parse(src)
    for n in ast.walk(t):
        if isinstance(n, (ast.Module, ast.FunctionDef, ast.ClassDef)) and n.body:
            if isinstance(n.body[0], ast.Expr) and isinstance(n.body[0].value, ast.Constant):
                n.body = n.body[1:]
    return ast.dump(t)
print(strip(old) == strip(new))

**背后的通用概念：**

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **声明式 vs 命令式** | 声明式只说"谁连谁"，命令式说"先做 A 再做 B" | 读图代码要**反过来推**运行时顺序，这正是最容易卡住的地方 |

### 3.1 ★ 抽检抓到 agent 写错了注释

这是本节最值得记的一段。**并行 agent 确实快，但它的结论不能直接信。**

我抽检时发现第一个 agent 在 `critic.py` 里写下的注释是错的：

> 它写：「`enable_critic=True` 走单 Agent 路径**必抛** `AttributeError`，
> 当前 api/main 默认 `False` 故未触发。」

听起来很有道理，**但条件不对**：真正让这行代码碰不到的是**上方 `critic_agent` 未注册时的提前 return**，
跟 `enable_critic` 是 `True` 还是 `False` 无关。照它写的读，读者会得出"只要打开开关就会崩"的错误结论 ——
而实际上是"这个节点整个空跑"。

同一批里它还有两处类似性质的偏差：

| 它写的 | 实际 |
|---|---|
| critic.py 里"五处"提前返回判通过 | **四处**（`grep -c` 一数就知道） |
| "铺到三个文件上" | 同一批实际改了 **8 个文件**（它只看得见自己那三个） |

**为什么会有这类错**：agent 只读了自己负责的文件，看不到全局；
它会用"局部自洽"的方式补上缺失的因果关系 —— 这恰好就是注释最容易出的错。
**验证方式也不玄**：`grep` 数一遍、`grep -rn` 查一遍调用方，成本以秒计。

> **可迁移的结论：** 让多个 agent 并行写"解释型内容"时，**解释的正确性必须由读得到全局的那一方复核**。
> 代码改错了有测试兜底，注释写错了没有任何东西会响 —— 它会安静地教给读者一个错的模型。

### 4. 人类怎么学这部分

**该盯哪里：**

- [clarification.py](langgraph_orchestrator/clarification.py) 文件头那段"三件事拆解" ——
  读完再往下看函数，就不会把 `should_retry_validation`（判断能不能再试）
  误当成 `parameter_validator_node`（干活的那个）。
- [enhanced_state.py](langgraph_orchestrator/enhanced_state.py) 的字段表当"索引"用：
  读别的文件卡住时，回来查这个字段谁写的，往往比顺着调用链找快。
- [critic.py](langgraph_orchestrator/critic.py) 数一下有几处 `return {"critic_passed": True}`
  —— 四处。这就是 fail-open 的密度：
  `grep -c 'critic_passed.*True' langgraph_orchestrator/critic.py`

**背后的通用概念：**

| 概念 | 一句话解释 | 为什么重要 |
|---|---|---|
| **读写方标注** | 字段清单的价值在"谁写谁读"，不在字段名 | 数据流是读多节点系统的唯一主线 |
| **fail-open vs fail-closed** | 出错时放行还是拦下 | 评审/校验环节多半选放行，因为拦下的代价是流程卡死 |
| **同名不同义** | critic 的 `quality_score` ≠ evaluator 的 `quality_score` | 跨文件同名变量是最隐蔽的误读源 |
| **薄壳节点** | 自己不实现逻辑，只打包上下文交给 Agent | 认出薄壳后就知道"真正的逻辑在 prompt 里"，找错方向会白读 |

### 1. 思路

**关键判断：标注的难点不在"写解释"，而在"别自信地写下错的解释"。**

这个判断是被上一节的翻车推出来的（agent 把 critic 的崩溃条件说反了）。所以这一轮的做法从一开始就定了：
- **口径先固化**：先建术语表，再动代码。表是唯一事实来源，避免并行任务各译各的。
- **机器管"没改坏"，人管"说对了"**：AST 比对能保证零逻辑改动，但它对注释的**内容对错完全无感** —— 注释写错了没有任何东西会响。所以每批都必须抽检。
- **要求"标注调用状态"**：这一轮最有价值的产出其实不是术语，而是**每个模块"到底跑不跑"**。

### 2. 这一轮真正挖出来的东西：一堆"写了但没接线"的模块

这是铺开后才浮现的**全局图景** —— 单看任何一个文件都看不出来，必须横向比对：

| 类别 | 情况 |
|---|---|
| **有类但从未注册** | `critic_agent`（评审环节整个空跑）、`document_agent`（注册调用已摘除） |
| **有代码但无调用方** | `crm_mock`、`industry_standards`、`mcp_client`、`function_calling`、`unified_monitoring`、`core/cache_manager`、`rag_core/retriever` |
| **只在降级路径生效** | 混合检索、重排、HyDE、上下文压缩、答案生成器（主路径是各 Agent 自己内联的那套） |
| **有方法体但是空的** | `AlertManager`、`StructuredLogger`（落 DEBUG 默认不可见）、`record_metric` |
| **字段只写不读** | `human_decision`、`stop_reason`、`parameters_aligned` |
| **配置无人消费** | `config/agents.yaml`（名册其实硬编码在 `_register_*`） |

**为什么这件事值得单独记：** 这套系统是"通用多 Agent RAG 骨架"改造来的，骨架里**预留的能力远多于售后场景用到的**。
对读者来说，最大的时间浪费不是"看不懂"，而是**花了很久研究一个根本没参与运行的文件**。
把调用状态写进文件头，等于在每个入口放一块路牌。

> **对学习的意义**：这也修正了一个常见误解 —— "代码在仓库里" ≠ "代码在运行"。
> 读一个陌生项目时，**先 grep 调用方**，比逐行读实现更早拿到真相。

### 3. 为什么这么改（以及被否掉的做法）

1. **为什么不做成"术语表 + 代码里不写解释"** —— 那个方案代码最干净，但读代码时要来回切文件。
   现在的分工是：**解释留在代码里（首次出现处），术语表只管"同一词译成同一中文"**，两者不重复。
2. **为什么按目录分批提交** —— 一个目录一个 commit，某批注释不满意可以单独改或回滚，不会 85 个文件绞在一起。
3. **为什么先只改一个文件** —— 上一节就是这么做的。先验证"这种标注方式真的有用"，再决定铺开；否则改完 85 个文件才发现方向不对，代价是全部返工。

    return ast.dump(t)                        # 注释本就不进 AST
