# 第一部分 · 系统是什么

## 1. 一页速览

| 项 | 值 |
|---|---|
| 定位 | 电商售后助手：答政策 / 查订单物流 / **办退换货** / 收投诉 / 识破损图 |
| 与"问答机器人"的区别 | 带工具、会查数据、**会写数据**，且动数据前有一道人工审批 |
| 编排 | LangGraph `StateGraph` 状态机，DAG 波次调度 |
| 分层 | 5 层（接入 / 编排 / Agent / 能力 / 数据） |
| 现役 Agent | **5 个**：knowledge · database · customer_service · vqa · chat |
| 规模 | 92 个 `.py`，约 3.0 万行 |
| 数据 | 10 篇售后政策（ChromaDB 34 chunk）· SQLite 6 张表 |
| 模型 | Qwen-Plus / Qwen-VL-Max（DashScope，走 OpenAI 兼容接口） |
| 测试 | 20 条，分两段：第一段不调 LLM（秒级）、第二段端到端（约 3 分钟） |

**三个必须先知道的边界**（细节见第 8 节）：

1. **会话不持久化** —— `MemorySaver` + `MemoryStore` 都在进程内，重启即丢。
   Redis 只做缓存，不存会话。
2. **没有单任务回退能力** —— 共享状态 + 单向无环 DAG 的固有代价（#36）。
3. **五条人工介入通道只有两条真能触发** —— 另外三条的触发条件恒不成立（#38 / #39）。

## 3. 运行时语义

### 3.1 两条路径

系统先判断"这一个问题要不要多个不同类型的 Agent 协作"，据此分两条路：

| | **simple 路径** | **complex 路径** |
|---|---|---|
| 入口判断 | `complexity_classifier` 二分类（解析失败 → **降级为 simple**） | 同左 |
| 选 Agent | `router` 两级：先按 description 向量召回 top-3，再 LLM 精排 | `planner` 拆成带 `depends_on` 的任务图 |
| 执行 | 单个 Agent，一次 `handle()` | `Send` 并行扇出根任务；波次调度续发 |
| 收尾 | 直接进 `duplicate_detection` | `parameter_validator` 校验上游产出够不够下游用 |

**这两条路的关键差异不在"几个 Agent"，而在"要不要维护一张任务图"。**
simple 路径 `plan` 为 `None`，下游所有依赖 `plan` 的节点都会短路跳过 ——
所以 `parameter_validator` 及其全部重试机器在 simple 路径下**不参与**。

### 3.2 一次请求的数据流（complex 路径）

```
用户问句
  │
  ├─ 指代消解（在 make_agent_node 里，每个 Agent 各做一次）
  │     ⚠️ 注意：complexity_classifier / router / planner 全在它**之前**，
  │        且都用**未消解**的 query —— 这三步恰恰最需要消解（#32）
  │
  → planner 产出 plan{tasks:[{task_id, agent_id, depends_on, …}]}
  → fan_out 只发 depends_on 为空的根任务
  → 每个 Agent 节点：读 state → 构造 context → handle(query, context)
  → ↺ wave_scheduler 找"依赖全满足且未完成"的任务续发
  → parameter_validator → duplicate_detection → aggregator
  → evaluator 三维打分 → human_intervention_check → END
```

### 3.3 会话与持久化边界

| 存储 | 存什么 | 活多久 |
|---|---|---|
| `MemorySaver` | 图状态（`thread_id` 隔离） | **进程内**，重启即丢 |
| `MemoryStore` | 长期记忆（跨会话） | **内存字典** |
| Redis | 缓存（LLM / 检索 / 语义） | 配了就持久，**不配降级为纯内存** |

> **可迁移结论**：LangGraph 的 checkpointer 决定了"断点恢复"的能力边界。
> 这里能做人机协同（`interrupt_before` 挂起再 `/resume`）**正是因为图状态在进程内还在** ——
> 换成无状态服务或重启，这套审批闸门立刻失效。想做生产级的人机协同，
> 第一件事是把 checkpointer 换成持久化的（如 `SqliteSaver` / `PostgresSaver`）。

## 4. 核心机制

> 每节固定三段：**要解决什么问题 → 方案 → 代价**。
> 「代价」这一栏是重点 —— 只讲方案的话，会把这个系统读成没有取舍的宣传册。

### 4.1 多智能体编排

#### 4.1.1 按复杂度分流

**问题**：不是所有问题都值得起一张任务图。"退货政策是什么"一个 Agent 就够，
起 DAG 纯属浪费 token 和延迟。

**方案**：`complexity_classifier` 用 LLM 做二分类，判据是「**是否需要多个不同类型
的 Agent 协作**」。两条路并存，不互相替代。

**代价**：多了一次 LLM 调用（在每次请求的最前面）。且分类错了会走错路 ——
所以解析失败时**降级为 simple**（宁可少拆，不可拆错）。

#### 4.1.2 任务图与波次调度

**问题**：复杂任务拆出的子任务之间有依赖，必须等上游出结果才能跑下游。

**方案**：`planner` 产出任务图，每个任务带 `depends_on` 列表。
调度是**波次**的：

- `fan_out_dag_tasks` 只发**依赖为空的根任务**
- 每波跑完，`wave_scheduler` 找"依赖全满足且自身未完成"的任务发下一波
- 就绪判据：`depends_on ⊆ completed_task_ids`

**★ 值得单独记的一点**：**没有 `current_wave` 这个字段**。
就绪判定完全由共享的**已完成集合反推**（[router.py:243-255](langgraph_orchestrator/router.py#L243-L255)），
而不是维护一个"现在第几波"的游标。

**为什么这是对的**：波次游标是要**同步**的状态 —— 一旦某个任务失败重跑、
或某个 Agent 跑得慢，游标和实际进度就对不上，而且这类 bug 只在并发下出现。
用"已完成集合"当唯一真相源，**天然规避了状态同步类缺陷**。
这是本项目最值得拿走的一条调度设计：**用可推导的量替代需要同步的量**。

**代价**：已完成集合**只增不减** → 没有单任务回退能力（#36）。
"A 检索 → 需要 B 的数据 → 回到 A 回答"这种形态**拆得出来、跑得起来，但语义是错的** ——
A 的第二次执行看不到 B 的产出。这是**设计边界，不是缺陷**：换来的是"必然终止、
不会静默卡死"。（同类局限见 §8.2）

#### 4.1.3 汇聚环节自判最终轮次

**问题**：每波跑完都要判断"还有没有下一波"。如果交给 LLM 判断，就是每波一次无效调用。

**方案**：`wave_scheduler` **自己看** —— 挑不出就绪任务就 `return "done"`
（[router.py:257-259](langgraph_orchestrator/router.py#L257-L259)），一个 token 都不花。

**实现上有一个必须写对的细节**：若就绪任务全被跳过（Agent 未注册），
**必须显式返回 `"done"`，不能返回空列表** —— 返回空列表等于一个分支都不发，
条件边的映射表接不上，流程就到不了 `evaluator`。**"什么都不发"和"发完了"不是一回事。**

**代价**：多波 DAG 的收敛是"跑到挑不出活为止"，没有全局预算上限。

### 4.2 长期记忆系统（存储 / 检索 / 治理遗忘）

跨会话记住"这个用户是 VIP""他上次的订单有问题"这类事实，但**不能让记忆库无限膨胀**。

#### 4.2.1 存储：结构化沉淀

不是存原始对话，而是**离线沉淀成结构化事件**：

| 步 | 做什么 |
|---|---|
| 事件总结 | 把一段对话压成一条可复用的事实 |
| 实体/关系抽取 | 抽出人、订单、商品及其关系（LLM 输出是**提案**，要人工核对） |
| 多域隔离 | 每条记忆归属一个 `category_name`（取自知识图谱类别体系），支持多场景复用 |

> **可迁移结论**：长期记忆**不要存原文**。存原文 = 未来检索时要在噪声里捞针，
> 且无法治理。**存"抽取后的事实"**才有后面"合并 / 遗忘"的可能。

#### 4.2.2 检索：三段式注入

```
生成可检索问题 → 多阶段混合检索排序 → 检索结果叙事化 → 注入 prompt
```

**三段各自的理由**：

- **生成可检索问题**：用户原话往往不适合直接做检索 query（太短、有指代）
- **混合检索排序**：见 §4.3.1，复用同一套 RRF
- **叙事化**：记忆是结构化字段（`category_name` + 事实），直接塞给 LLM 是一堆键值对。
  转成一段叙述，**LLM 才好用**。

> **可迁移结论**：这是**低上下文成本**的记忆增强做法 —— 只注入与当前问题相关的几条，
> 且转成自然语言。对照的反面做法是"把整个记忆库拼进 system prompt"，
> 那样上下文会被迅速吃满，且越加越差。

#### 4.2.3 治理：能定期回收

| 机制 | 作用 |
|---|---|
| 重复归档 | 同一事实反复出现 → 去重 |
| 相似合并 | 语义相近的记忆合并成一条 |
| 低重要度 + 长期未访问 → 遗忘 | 控制规模 |

> **可迁移结论**：**记忆系统一半的难度在"删"不在"存"。**
> 只写不删的记忆库，检索质量会随规模单调下降 —— 因为噪声也在增长。
> 治理规则要能**定期跑**，且是**规则驱动**（不是每次写入都调 LLM）。

### 4.3 混合检索与读写分离

#### 4.3.1 双路召回 + RRF 融合

**问题**：向量检索擅长语义相近，关键词检索擅长精确匹配（订单号、型号）。
两者的**分数量纲不可比** —— 向量余弦相似度是 0~1，BM25 是无上界的实数，
直接加权求和没有意义。

**方案**：**只取排名，不取分数**，用 RRF（Reciprocal Rank Fusion，排名倒数融合）：

```
score(doc) = Σ_路径  1 / (k + rank(路径, doc))
```

**为什么这解决了量纲问题**：RRF 只用"这篇排第几"，**完全丢弃原始分数**，
所以两条量纲不同的路径可以直接相加。

> **★ 可迁移结论（这条最通用）**：**多路召回融合时，如果两路的分数量纲无法校准，
> 就用排名而非分数。** 这个技巧在任何"多检索源合并"的场景都适用
> （多模型投票、多排序器融合、多召回策略叠加）。

#### 4.3.2 读写分离

**问题**：LLM 生成 SQL 很强，但**让它生成写语句就是灾难**。

**方案**：按读写分开，两条路走完全不同的机制：

| | 读（开放式查询） | 写（改数据） |
|---|---|---|
| 机制 | **Text-to-SQL** —— 图转结构化查询，LLM 自由生成 | **固定访问方法** —— 参数化的专用函数 |
| 防护 | [agent.py:632](agents/database_agent/agent.py#L632) 前缀检查 `startswith("SELECT")`，非 SELECT 直接拒 | **三重校验**：① 订单存在 ② 归属正确 ③ 状态允许售后 |
| 为什么 | 读的形态无法穷举，必须让 LLM 自由构造 | 写的形态可穷举，**穷举出来就不给 LLM 自由度** |

**三重校验的每条都在挡一个具体的错**（[ecommerce_crm.py:365-369](core/ecommerce_crm.py#L365-L369)）：

1. **订单存在** —— 挡模型臆造一个 `/order_id`
2. **归属正确** —— 订单真实存在，也不能证明是本人下的；**挡 A 用户退 B 的订单**
3. **状态允许** —— 已取消 / 待发货的订单没有可退的货，本该走取消流程

> **★ 可迁移结论**：**Agent 系统里"写"和"读"的安全模型完全不同。**
> 读：让 LLM 自由构造 + 事后检查（成本低、覆盖面广）。
> 写：**根本不给 LLM 构造权**，只让它选函数 + 填参数（自由度的转移）。
> 后者才是安全性的来源 —— 检查是兜底，不是主防线。

**一个诚实的补注**：读路径的 `startswith("SELECT")` 是**前缀检查，不是 SQL 解析器**。
它挡得住"模型想执行 DELETE"，挡不住精心构造的绕过。真正的护栏是
`sqlite3` 的 `execute()` 默认只执行单条语句。

#### 4.3.3 ★ 写操作审批闸门

**问题**：系统真的能改数据库（提退货申请 / 建工单）。这类操作**不可逆**，
且触发它们的往往只是一句用户闲聊。

**方案**：Agent 能写，但**写之前停下来等人确认**。

```
Agent 执行写工具 → 登记（线程本地）→ Agent 节点写入 state["write_operations"]
  → human_intervention_check 据此挂起（interrupt_before）
  → 前端弹审批框 → 人点「批准继续」→ POST /resume → 继续执行
```

**★ 最关键的一处设计判断**：判据是「**数据是不是真的被改了**」，
**而不是**「用户说了什么关键词」。

同一个文件里**两条长得很像的"写操作"通道**，认准这条：

| 通道 | 判据 | 实际效果 |
|---|---|---|
| **通道 2（这条）** | `state["write_operations"]` 非空 —— 程序**实际做了什么** | ✅ 唯一可靠的写闸门 |
| 通道 3 | 用户**中文原话**里含 `INSERT`/`UPDATE` 等词，且 Agent 名含 `database` | ❌ 用户只会说"我要退货"，**永远不可能命中** |

> **★★ 可迁移结论（本项目最值得拿走的一条）**：
> **审批 / 风控的判据要取"实际动作"，不能取"用户措辞"。**
> 措辞可以被绕过（换个说法、加个副词就能骗过子串匹配），
> 而"程序有没有真的调用写工具"是**事实**，绕不过去。
> 同理，**不要用 Agent 的名字做风控判据** —— 名字是元数据，可以改，也不反映行为。

**代价**：用户会看到一次打断，点击后才继续。这是**有意的摩擦**，不是缺陷 ——
对不可逆操作，摩擦是特性。

#### 4.3.4 ★ 防幻觉兜底

**问题**：LLM Agent 最危险的失败模式**不是答错，而是描述没发生的事**。
实测中模型会写出「已为您提交退货申请，单号 RF2026xxx」，而数据库里什么都没有 ——
用户以为退货了，实际没退。

**方案**：输出后校验（[_verify_write_claim](agents/customer_service_agent/agent.py#L974)）——
**答复里声称办过事，就必须本轮真调用过写工具**；否则改写答复，明确告诉用户"并未提交"。

关键实现细节：核验用的是**本轮真正执行过的工具名集合**（`executed_tools`），
在执行 `handle` 时记录。

> **★ 可迁移结论**：**LLM 系统的"幻觉"有两类：幻觉知识 和 幻觉动作。**
> 前者答错了用户还能自己判断；**后者让用户以为一件事办了而实际没办**，
> 后果严重得多。防御手段只有一种：**拿"声称"去比对"实际执行记录"**。
> 前提是系统**保留了执行记录** —— 没记录就没法校验。
> 这也解释了一个看似奇怪的设计：为什么不能靠提示词让模型"别说谎"，
> 而必须在**代码层**再核一遍。

---

### 4.4 质量闭环与成本控制

#### 4.4.1 三维加权评分 + 阈值重跑

**方案**：`evaluator` 对最终答复打三个分，加权求和
（[nodes.py:588-590](langgraph_orchestrator/nodes.py#L588-L590)）：

| 维度 | 权重 | 单项否决线 |
|---|---|---|
| relevance（相关性） | 0.4 | < 6 |
| completeness（完整性） | 0.3 | < 6 |
| accuracy（准确性） | 0.3 | < 6 |

低于阈值时，把 evaluator 给出的**具体改进要求**（`feedback`）拼回 query，
**回到流程入口整体重跑**。

**★ 为什么"带具体改进要求"很重要**：不带反馈的重跑 = 让模型重新掷一次骰子，
大概率得到同样差的结果。**带反馈的重跑才有方向**。
这是"自我修正"能不能生效的分水岭。

#### 4.4.2 迭代配额强制收敛

`iteration` 在 evaluator 里**每评一次就 +1（无条件，不看分数）**，
上限由 `check_quality` 控制。**任何自评分系统都必须有硬上限** ——
否则"评分不过 → 重跑 → 评分不过"就是死循环。

> **可迁移结论**：**自评 / 自我修正的回路，必须有外部强制的配额。**
> 把终止条件交给模型自己判断（"你觉得够好了就停"），等于没有终止条件。

#### 4.4.3 重复熔断

**问题**：重试时如果模型给出和之前**一模一样**的结果，再评审再汇总纯属浪费。

**方案**：`duplicate_detection` 比对结果指纹（精确匹配 + 向量相似度），
命中就**熔断**：跳过 `critic` 和 `aggregator`，直接进 `evaluator`
（[enhanced_graph.py:231](langgraph_orchestrator/enhanced_graph.py#L231)）。

> **可迁移结论**：**在重试环里，先花便宜的办法判断"这次重试有没有意义"。**
> 检测重复是纯计算，比再跑一轮 LLM 便宜几个数量级。
> 注意 `duplicate_detection` **永远排在 `critic` 前面** —— 顺序本身就是"先便宜后贵"。

#### 4.4.4 两层缓存

| 层 | 命中什么 |
|---|---|
| 业务缓存 | **完全相同**的问题 |
| 语义缓存 | **问法被改写过、意思一样**的问题（向量相似度） |

> ⚠️ **核实的实际情况**：语义缓存在全项目**只有 `knowledge_agent` 一个 Agent 接线**
> （[agent.py:841-865](agents/knowledge_agent/agent.py#L841-L865)）。
> 写成"全项目两层缓存"是不实的。

> **可迁移结论**：**缓存的键要按语义层设计，不能按字符串。**
> 用户的问法千变万化，精确匹配的命中率会很低；语义缓存才是"重复问答"的主战场。
> 但语义缓存有**误命中风险**（相似 ≠ 相同），所以阈值要保守，
> 且**不适合放在写操作路径上**。

# 第二部分 · 契约

> 这一部分是本文档最硬的东西，也是**唯一必须对着代码重新核实**的部分。
>
> **为什么它值得单列**：本项目反复挖出的问题（#33 / #34 / #37 / #38 / #39 / #40）
> **全是同一类** —— *代码看起来是通的，实际没接线*。根因一句话：
> **`context` 和 `state` 的类型都是 `Dict[str, Any]`，塞什么取什么都不报错。**

## 5. 契约表

### 5.1 为什么这类问题专挑 `context` 出现

| | 有编译器检查吗 |
|---|---|
| `handle(query, context)` 的**签名** | ✅ 注册时校验（但**只查方法在不在，不查签名**） |
| `context` **里面有哪些键** | ❌ **完全没有** —— 类型就是 `Dict[str, Any]` |

所以：

- 塞什么、取什么**都不会报错**
- `.get("不存在的键", 默认值)` **静默通过**，拿到默认值继续跑
- 契约 docstring 是唯一的"文档"，而 **docstring 不会被验证**

### 5.2 `context` 全键表

**唯一构造点**：`make_agent_node`，[nodes.py:162-207](langgraph_orchestrator/nodes.py#L162-L207)

| 键 | 谁写 | 谁读 | 状态 |
|---|---|---|---|
| `_agent_name` | nodes.py:207 | knowledge · database · customer_service · document | ✅ 活 |
| `_stream_writer` | nodes.py:206 | 同上 4 个 | ✅ 活 |
| `history` | nodes.py:193（仅当有 session_memory） | customer_service:813 · database:422 · knowledge:1008 | ✅ 活 |
| `image_urls` / `image_paths` / `image_base64_list` | nodes.py:171-176（仅当有图） | vqa_agent:318/322/327 | ✅ 活 |
| `file_paths` | nodes.py:178（仅当有文件） | **无** | ❌ 只写不读 |
| `dependencies` | nodes.py:164 | **无** | ❌ 只写不读（#34：上游数据改走 query 拼接） |
| `original_query` | nodes.py:167 | **无** | ❌ 只写不读 |
| `image_url` / `image_path` / `image_base64`（单数） | **无** | vqa_agent:334/338/344 | ❌ 只读不写 —— 被 `if not images:` 兜底分支挡住，永不触发 |
| `user_id` | **无** | knowledge:830,1355 · customer_service:1052 · database:589 | ❌ 只读不写 → **恒为 `"anonymous"`** |

| `urgent` | — | — | ✅ 已删除（原死代码 #22） |
| `messages` | — | — | ⚠️ 转发已删；但 [protocol.py:59-66](core/protocol.py#L59-L66) 的 docstring **仍列着它** → 契约文档过期 |

**三条要单独说的**：

1. **`user_id` 是最隐蔽的一类** —— 代码看起来完全正常：
   `context.get("user_id", "anonymous")` 到处都在读，日志、审计、记忆隔离都在用这个值。
   但**全项目没有一处写过它** → 恒为 `"anonymous"`。
   危险不在"没用"，而在**"看起来有用"**。
2. **`conversation_history` 是键名笔误级别的死链** —— 节点注入 `history`，
   chat_agent 读 `conversation_history`。两边都用了 `.get(..., [])` 带默认值，
   所以**一声不响**地拿到空列表。
3. **`dependencies` 保留着但不该依赖它** —— 它仍被构造，但 0 个读者。
   上游数据交接已改走"拼进 query"（query 是每个 Agent 必然读到的唯一入口）。
   **看到 `context["dependencies"]` 还在，不要以为数据交接走这条路。**

### 5.3 `state` 字段表（死字段部分）

完整字段清单及逐字段的写/读注释见
[enhanced_state.py](langgraph_orchestrator/enhanced_state.py)（该文件本身已是字段文档）。
这里只列**当前没有读取方、或值恒定不动**的字段：

| 字段 | 情况 |
|---|---|
| `messages` | 只累积、无人消费。Agent 读的是 `context["history"]` |
| `parameters_aligned` / `parameter_alignment_errors` | 只在 `enhanced_entry` 初始化，**无任何读方** |
| `critic_passed` | 恒为初始 `True` —— 唯一写方 critic 节点**从未进图**（`enable_critic=False`） |
| `critic_validation` / `critic_issues` | 同上，恒为初始值 |
| `stop_reason` | 重复检测会写，但**代码内无读取方**，仅留档排查 |
| `validation_*` 一族 | 因 §5.5 所述守卫，**整条链路从不执行** |
| `plan_approved` | 只在 resume 分支写；通道 1 恒不成立（#38），基本无效 |

### 5.4 Agent 协议

```python
handle(query: str, context: Dict[str, Any]) -> str
```

- **鸭子类型**：`runtime_checkable` 的 `Protocol`，`isinstance` 检查
  —— 不要求继承基类，只要**有** `handle` 属性就通过
- **★ 代价**：`isinstance` **只核对方法名在不在，不核对签名**。
  实测 `handle(self)`（一个参数都没有）**同样能注册成功**。
  校验挡的是"忘了写 `handle`"，**挡不住"`handle` 写错了"**
- **返回类型限定 `str`** —— 多一个字段都放不下。所以"我刚改了数据"这类**结构化信号
  无法从返回值带出**，只能改用**线程本地登记**（`core/write_ops.py`）。
  **这条约束是那套登记机制的起因** —— 看到 `write_ops` 时回想一下这里

### 5.5 写操作生命周期（全链路 ✅ 活）

```
① Agent 执行写工具
② _record_write_operations 登记到线程本地   customer_service_agent/agent.py:680
③ 节点 consume_write_ops() 取出             nodes.py:249
④ 写入 state["write_operations"]（挂 operator.add）
⑤ human_intervention_check 通道 2 读它 → 挂起
⑥ 前端弹审批 → 人点批准 → POST /resume
⑦ enhanced_entry resume 分支置 write_approved = True
⑧ 继续执行
```

**为什么用线程本地登记而不是返回值**：见 §5.4 —— `handle` 只能返回 `str`。
**必须在线程内、`handle()` 之后立刻读取**，因为记录器是线程本地的。

### 5.6 人工介入的 5 条通道

`human_intervention_check` 里串着 5 条**互不相干**的触发通道，按顺序判断、
命中一条就返回。**名义 5 条，实际只有 2 条能触发**：

| # | 触发条件 | 状态 | 死因 |
|---|---|---|---|
| 1 | `plan["complexity"] == "complex"` 且未批准 | ❌ **不可达** | plan 里**从没有** `complexity` 这个键；复杂度实际存在 `state["is_complex"]`（#38） |
| **2** | `write_operations` 非空且未批准 | ✅ **活** | — 唯一可靠的写操作闸门 |
| 3 | 用户原话含写关键字 且 Agent 名含 `database` | ❌ **不可能命中** | 查的是用户**中文原话**里的 `INSERT`/`UPDATE` |
| **4a** | `quality_score < 0.4` 且 `iteration >= 2` | ✅ **活** | — |
| 5 | `critic_passed` 为假 | ❌ **不可达** | `critic_passed` 恒为初始 `True`（#39） |

**两类死法的对照（这张表本身就是教材）**：

- 通道 1 死于 **"key 从没被写过"** → 条件 `plan.get("complexity")` 恒为 `None`
- 通道 5 死于 **"字段值恒定不动"** → 条件 `not critic_passed` 恒为假

**两条都不报错、不打日志** —— 光看这两处的逻辑**是对的**，
必须去追"字段的值从哪来"才能发现。这是本项目最贵的一课。

## 6. ★ 方法论：怎么发现一条「看起来在工作」的链路

这一节是**本项目花最大代价换来的东西**，也是最能迁移到其他项目的一节。
下面 5 个案例全部真实，每个对应一种**不同的死法**。

### 6.1 五种死法

| 死法 | 特征 | 案例 | 怎么查 |
|---|---|---|---|
| **只写不读** | 写方在，读方为零 | `context["dependencies"]`、`original_query`、`file_paths` | 对键名 grep 两次：谁写 / 谁读 |
| **只读不写** | 读方一大堆，写方为零 → **恒取默认值** | `context["user_id"]` 恒 `"anonymous"` | 同上，看**写方**是否为空 |
| **键名不匹配** | 两边都"有"，但键名不同 | `history` vs `conversation_history` | 同上，逐字比对键名 |
| **条件恒假** | 条件依赖一个从没被写过的值 | 通道 1 死在 `plan["complexity"]`（#38） | 顺着条件里的 key 往回找**写入点** |
| **守卫挡死** | 整段代码被一个永远成立的前置条件挡住 | `parameter_validator` 被"Agent 返回纯文本 → 跳过校验"挡死（#37） | 找**最前面的 if** —— 后面写得多好都没用 |

### 6.2 可复用的检测法

**① 双向核对法（最简单、覆盖最广）**

```bash
# 对每个键，分别数写入点与读取点
grep -rn '"键名"' --include=*.py agents/ core/ langgraph_orchestrator/ orchestrator/
```

| 核对结果 | 含义 |
|---|---|
| 写方为零 | **"读了但拿不到"** —— 最隐蔽，因为代码看起来是通的（`user_id`） |
| 读方为零 | **"写了没人用"** —— 无害但误导读者（`dependencies`） |
| 两边都为零 | 死代码，该删（`urgent`） |

**② 别信 docstring，信 AST**

项目里有不止一处"注释与事实不符"。`AST` 能证明"某个函数实际 return 了什么类型"
（#37 就是这么发现"5 个 Agent 的 `handle` 没有一个 return dict"的），
`docstring` 只能证明"当初想让它返回什么"。

**③ 检查守卫（最容易被漏掉的一步）**

**在追一条链路之前，先看它前面有没有"永远成立"的 if。**
`parameter_validator` 里字段校验的代码写得完整、重试机制一应俱全，
但最前面一道守卫（"Agent 返回纯文本 → 跳过字段校验"）**永远触发** ——
因为契约规定 `handle() -> str`，所以**这条链路的全部代码从不执行**。

**④ 看"触发条件依赖的值"从哪来**

条件写得再对，**只要那个值从来没人写过，条件就恒不成立**。
通道 1（#38）和通道 5（#39）都是这么死的，而且**静默跳过，连日志都不打**。

### 6.3 一条更根本的经验

**"看起来在工作"的链路，四件套往往是齐的**：

> 触发文案（"任务规划完成，等待人工审核"）· 前端按钮 · 答复翻译逻辑 · 进度事件
> —— **唯独缺那个让条件成立的写入。**

所以：**判断一条链路活不活，不要看它周围有多少配套，要看它的"入口"有没有人喂。**
配套齐全**恰恰**是最危险的信号 —— 它说明这条链路在某个时点是被认真设计过的，
只是**接线那一步漏了或后来断了**，而周边的东西留了下来。

# 第三部分 · 可拿走的东西

## 7. 可迁移的设计原则

按"能迁移到别的 agent 项目"筛出来的，每条标注本项目里的落点。

### 编排

1. **用可推导的量替代需要同步的量** —— 波次调度的就绪判定用"已完成集合反推"，
   而非维护 `current_wave` 游标（§4.1.2）。凡是要在多处保持一致的状态，
   先问"能不能改成算出来的"。
2. **"什么都不发"和"发完了"必须区分** —— 调度器返回空列表会让流程接不上，
   必须显式返回终止信号（§4.1.3）。
3. **复杂度的分流要能降级** —— 分类失败时走简单路径，宁可少拆不可拆错（§4.1.1）。

### 安全

4. **审批判据取"实际动作"，不取"用户措辞"** —— ★ 写操作闸门看
   `write_operations` 而非关键词（§4.3.3）。措辞可绕过，事实不可。
5. **不要用名字做风控判据** —— Agent 的名字是元数据，可改、不反映行为。
6. **读和写用完全不同的安全模型** —— 读让 LLM 自由构造、事后检查；
   写根本不给构造权，只让它选函数填参数（§4.3.2）。
7. **LLM 的"幻觉动作"比"幻觉知识"危险** —— 防御手段唯一且必须：
   **拿"声称"比对"实际执行记录"**（§4.3.4）。前提是保留了执行记录。

### 自修正与成本

8. **自评回路必须有外部强制配额** —— 把终止交给模型自己判断 = 没有终止（§4.4.2）。
9. **重跑要带具体反馈** —— 不带反馈的重跑是重新掷骰子（§4.4.1）。
10. **自评的权重和否决线要能调** —— 三维加权而非单一分数，
    且单项有独立的否决线（§4.4.1）。
11. **在重试环里先花便宜的办法判断"重试有没有意义"** —— 重复检测排在 LLM 评审前面（§4.4.3）。

### 检索与记忆

12. **多路召回分数量纲不可校准时，用排名而非分数** —— ★ RRF（§4.3.1）。
13. **长期记忆存"抽取后的事实"，不存原文** —— 否则无法合并与遗忘（§4.2.1）。
14. **记忆系统一半的难度在"删"** —— 只写不删，检索质量随规模单调下降（§4.2.3）。
15. **注入记忆要转成叙事，不要塞键值对** —— 转成自然语言 LLM 才好用（§4.2.2）。
16. **缓存的键按语义层设计，不按字符串** —— 但语义缓存有误命中风险，
    不放写操作路径（§4.4.4）。

### 接口与契约

17. **隐式契约（`Dict[str, Any]`）是 bug 的温床** —— 宁可用显式类型，
    或至少维护一份"谁写/谁读"的表（§5.1）。
18. **单一返回值类型会逼出旁路通道** —— `handle() -> str` 导致结构化信号
    只能走线程本地登记（§5.4）。**接口窄了，复杂度不会消失，只会换个地方出现。**
19. **对契约做双向核对** —— 每个键都 grep 两次：谁写、谁读（§6.2）。

## 8. 已知边界与局限

> 区分两件事：**设计边界**（刻意不做的取舍）和**缺陷**（该做没做 / 做了没接上）。
> 把它们混在一起，会把"这是有意为之"误读成"这是 bug"。

### 8.1 设计边界（不改，是取舍）

| 边界 | 换来了什么 |
|---|---|
| 无单任务回退能力（#36） | 流程**必然终止**，不会静默卡死 |
| 会话不持久化（MemorySaver 在进程内） | 零外部依赖即可跑起来 |
| Agent 之间不互调（契约只有 `handle`） | 接口极简，任意类都能当 Agent |
| 五条介入通道保留未删的死通道 | 保留未来接回 critic / 计划审核的位置 |

### 8.2 当前未解决的缺陷

| 项 | 说明 |
|---|---|
| `parameter_mapping` 字段级取值（#37） | 整段被守卫挡死，从不执行。连带 `validation_*` 一族全死 |

| 申请原因不受政策校验（study.md §7.2） | 用户说什么理由都收，不与政策条款比对 |
| `protocol.py` 的 docstring 过期 | 仍列着已删除的 `messages` 键 |

**改造过程中挖出并修复的 4 个真问题**（都在 [idea.md](idea.md)）：

1. **工具注册无法传多参数** —— `register_tool` 用的 LangChain `Tool` 硬编码只接受
   1 个参数，加 `args_schema` 也无效。原有工具恰好都只传 1 个参数所以从未暴露，
   `create_ticket` 其实一直是坏的
2. **防幻觉兜底被措辞绕过** —— 固定子串匹配挡不住模型在中间插副词
3. **SQLite 外键默认不生效** —— 建表语句里写了 `FOREIGN KEY` 只是声明，
   不开 `PRAGMA foreign_keys = ON` 就没有执行力，导致臆造的 `user_id` 能写进库
4. **前端静默失败** —— 渲染抛异常时进度条已移除、异常只打日志，
   用户看到的是"什么都没有"
