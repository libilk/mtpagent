### ⚠️ 这个模板有四个槽 nlp 填不了 —— 先说，别踩

**这个方向（业务规模 → 微服务组件 → 线上慢 SQL）是为"生产系统"设计的。
nlp 是本地 POC —— 照搬会逼你编 QPS 和 Nginx。** 逐槽对照：

| 模板要的 | nlp 的实际情况 | 怎么答 |
|---|---|---|
| 业务规模：**用户量 / QPS** | 本地跑，**无线上流量** | 换**数据规模**：10 政策 / 34 chunk / 6 表 / 20 条测试 |
| 架构模式：微服务 / 前后端分离 | **单体 + 进程内图编排** | **主动说"刻意不做微服务"** 并给理由（零外部依赖、clone 即跑）—— 是取舍，不是缺陷 |
| 组件：Nginx / Redis / MQ / 熔断 / 灰度 | 只有 FastAPI + ChromaDB + SQLite；Redis **可选** | **别编组件**。把"熔断 / 降级"换成真实对应物：循环上限 / 重复熔断 / 复杂度降级 |
| 性能：慢 SQL **2s → 200ms** | 无线上性能数据 | 讲**机制**不编**倍数**：缓存命中不进循环 / 先便宜后贵 / 分流省一次 DAG |
| **线上故障复盘** | 无线上；**但本地实测抓到 5 个真 bug** | ★ **直接用真 bug 复盘** —— 这条 nlp **很强**，见升华 3 |

> **一句话**：模板的**故事线**照用，模板的**生产组件清单**换成 nlp 的真实对应物。
> **填不了的槽宁可说"这是 POC，没有这部分"** —— 一个编出来的 QPS 撑不过一句追问。

### ★ 选型 Why（面试官问"为什么用它"时才展开 —— 别说"我们用了 X"）

| 选型 | 为什么是它 | 代价 / 什么时候换 |
|---|---|---|
| **Chroma** 而非 Milvus / Qdrant | 10 篇文档 / 34 chunk —— **这个量级选型没有性能意义**；要的是**零服务依赖**（`PersistentClient` 不用起进程） | 元数据过滤弱 → 退化成应用层白名单；到百万级或要复杂过滤 → **Qdrant** |
| 混合检索用 **RRF** 而非加权求和 | 向量余弦是 0~1、BM25 **无上界** —— **分数量纲不可比**，直接加权没有意义。RRF 只用排名不用分数，所以两条量纲不同的路径能直接相加 | 丢弃了分数信息；但换来"可融合" |
| **读写用完全不同的机制** | 读的形态**无法穷举** → 让 LLM 自由构造 SQL + 事后检查；写的形态**可穷举** → **穷举出来就不给 LLM 自由度**，只让它选函数填参数 + 三重校验 | 写操作的形态必须能预先枚举 |

> **★ 第三条最值钱**：**安全性来自"自由度的转移"，检查只是兜底。**
> 读：让模型自由构造；写：根本不给它构造权。**读和写的安全模型是两套。**

### 🚀 升华 1 · 稳定性设计（30 秒）

**模板问的是"限流 / 熔断 / 灰度"。nlp 没有这些名词，但有功能等价的真实机制** —— 讲对应物：

| 模板的概念 | nlp 的真实对应物 | 防什么 |
|---|---|---|
| **循环上限** | ReAct 迭代上限**写死**（knowledge 5 / 售后 8） | LLM 反复调工具停不下来 |
| **强制收敛** | 到顶注入"别再调工具、直接回答" | 同上 |
| **熔断** | 重复检测命中 → **跳过** critic + aggregator | 重试无意义时别再花钱 |
| **降级** | 复杂度分类失败 → simple；无可用工具 → 降级流程 | 宁可少拆，不可拆错 |
| **工具容错** | `handle_tool_error=True`（异常转错误字符串） | 一个工具报错拖垮整条链 |
| **数据护栏** | 外键 `PRAGMA foreign_keys=ON` + 三重校验 | 臆造数据写进库 |
| **★ 防幻觉** | 声称 vs **本轮执行记录**比对 | 让用户以为办了、实际没办 |

> **一句话**：*"稳定性上我做的不是限流熔断，而是**保证这套带环的流程必然终止、且不撒谎**。"*

### 🚀 升华 2 · 性能优化（20 秒）

- **两层缓存**（精确 + 语义）：命中直接 `return`，**连 ReAct 循环都不进**
- **先便宜后贵**：重复检测（纯计算）排在 LLM 评审**前面**
- **分流**：简单问题不起 DAG，省一次任务规划 + 一次评审
- **⚠️ 没有"2s → 200ms"这种线上数字 —— 别编。讲机制，不讲倍数。**

### 🚀 升华 3 · 故障复盘（60 秒，★ nlp 最强的一环）

**模板要"一个线上故障案例"。nlp 没有线上 —— 但本地实测抓到了 5 个真 bug，
每一个都能走完「定位 → 根因 → 修复 → 预防」的完整复盘。** 挑一个讲：

| # | 潜伏 bug | 为什么值钱 |
|---|---|---|
| 1 | `create_ticket` **一直是坏的** —— 底层 LangChain `Tool` 硬编码只收 1 个参数，传 `args_schema` 也没用 | 原有工具**恰好都只传 1 个参数**，所以从没暴露。证明你**不信"在用 = 没问题"** |
| 2 | 防幻觉兜底**被措辞绕过** —— 第一版是固定子串匹配，模型中间插个副词就骗过 | 你**实测**抓到，改成比对**本轮真实执行过的工具名集合**（可判定，不可绕过） |
| 3 | SQLite 外键**默认不生效** —— 建表写了 `FOREIGN KEY` 只是声明 | 补 `PRAGMA foreign_keys = ON` + 两处漏声明，**臆造 `user_id` 才被真正挡住** |

> 第 3 个特别适合讲：**"声明了约束"和"约束有执行力"是两回事** —— 这句在面试官耳朵里是"这人踩过真坑"。

**★ 把一个 bug 讲成完整复盘的模板（挑 SQLite 外键那个最顺）：**

> **现象**：Agent 臆造了一个 `user_id`（填过 `U87654321`），**却写进了库**。
> **定位**：顺着写路径查 —— 建表语句里**明明写了 `FOREIGN KEY`**。
> **根因**：SQLite 的 `FOREIGN KEY` 默认**只是一句声明，没有执行力** ——
> 必须显式 `PRAGMA foreign_keys = ON`。
> **修复**：补 PRAGMA，并补齐两处漏掉的外键声明（`tickets.order_id`、`refunds.user_id`）。
> **预防**：**"声明了约束"和"约束有执行力"是两回事** —— 之后所有数据护栏都先进测试验证才认。

**另外两个备选（各留一句根因即可）：**

- **防幻觉兜底被"措辞"绕过** —— 定位靠**浏览器实测**（HTTP 层测试漏了）→ 根因是**固定子串匹配** → 修复成比对**本轮执行过的工具名集合** → 预防：**判据取事实，不取措辞**。
- **`create_ticket` 一直是坏的** —— 根因是 LangChain `Tool` **硬编码只收 1 个参数** → 修复用 `StructuredTool` → 预防：**"在用"不等于"没问题"**（原有工具**恰好都只传 1 个参数**，所以从没暴露）。

> "系统能改数据，所以写之前要停下来等人确认。这里有一处设计判断：判据是
> **`state['write_operations']` 非空**，也就是**程序实际有没有调用写工具** ——
> 而不是'用户原话里有没有出现写操作关键词'。后者**永远不可能命中**，用户只会说'我要退货'。
> **代价**是用户会看到一次打断、点一下才继续 —— 但这是**有意的摩擦**，对不可逆操作，
> 摩擦是特性不是缺陷。
>
> 做完之后踩到一个只有真做过才知道的坑：**工具是并行执行的、跑在线程池里**，
> 我最初把写操作登记放在工具内部，结果**信号丢失、甚至跨请求串号**。
> 原因是登记器是**线程本地**的，必须挪到调用线程、在 `handle()` 返回后立刻读。
> 这个坑反过来印证了接口约束 —— `handle()` 只能返回 `str`，结构化信号带不出来，
> 才逼出这套线程本地登记。"

**主线 3 · 契约核对与"死链路"排查（41 项台账）**

> "上线前我做了一遍**全字段、全 `context` 键的双向核对** —— 每个键 grep 两次：谁写、谁读。
> 挖出一批**看起来在工作、实际没接线**的链路：5 条人工介入通道**只有 2 条真能触发**，
> 参数校验整条链路被一道守卫永远挡死，`user_id` 全项目只读不写、日志审计全记成 `anonymous`。
> **两条死通道不报错、不打日志** —— 光看逻辑是对的，必须去追'条件里那个值从哪来'。"

> **这条线最可迁移的一句（比代码更值钱）**：
> **看到有配套 UI / 文案 / 事件的链路，先怀疑它不跑。
> 完整度不是活性证据，是"曾经被设计过"的证据。**

### 分层：每层各备一个「想 A → 改 B → 因为 C」

面试官挑哪层，你都有话说：

| 层 | 本来想 A | 改成 B | 因为 C |
|---|---|---|---|
| 编排 | 维护 `current_wave` 波次游标 | 用**已完成集合反推**就绪 | 游标是要同步的状态，任务失败重跑 / 跑得慢就对不上，**这类 bug 只在并发下暴露** |
| 能力（工具） | LangChain `Tool` | `StructuredTool` + `args_schema` | `Tool` 硬编码只收 1 个参数，多参数工具静默失效 |
| 记忆 | 上游结果走 `context["dependencies"]` 结构化传递 | **拼进 query** | `dependencies` 只写不读（0 个读者）；query 是每个 Agent 必然读到的唯一入口 |
| 治理 | 关键词子串拦截写操作 | 比对 `write_operations` 实际动作 | 措辞可绕过，事实不可 |
| 接入 | 渲染异常只打日志 | **按 options 渲染**按钮 | 原来渲染抛异常时进度条已移除、异常只进日志，用户看到"什么都没有" |

### 四个必须主动讲的深度点（否则被判定为"调 API 的"）

| 深度点 | 本项目落点 |
|---|---|
| **上下文工程** | 上游结果拼进 query 而非结构化传递；`messages` 单条截断 8000 字；发现 `messages` 是"只写不读"的死字段白占内存 |
| **失败处理** | 工具执行带去重 + `handle_tool_error=True`（失败转错误字符串让模型换参数重试）；ReAct 循环上限写死（knowledge 5 / 售后 8）；重复调用强制收敛；**防幻觉兜底** |
| **评测体系** | 两段式 **20 条**测试；检索 **6 问题 top-1 命中 6/6**；**缺独立 eval set**（要主动承认） |
| **成本与延迟** | 两层缓存（精确 + 语义）；**重复熔断排在 LLM 评审前**（先便宜后贵）；复杂度分流省一次 DAG |

### 追问怎么接

- **Q：为什么不用 workflow 写死，而用 LLM 自主决策？**
  → **先否定前提**："绝大部分环节我确实是写死的 —— 确定的用代码兜底（写操作只让模型选函数填参数，不给它构造 SQL 的自由）；交给模型的只有**语义判断**：复杂度分类、选 Agent、拆任务图。"
- **Q：怎么保证它不越权 / 不删数据？**
  → "读：LLM 自由构造 SQL + 前缀检查（只允许 `SELECT`）；**写：根本不给构造权**，只有参数化的固定方法，加三重校验（订单存在 / 归属正确 / 状态允许），再加人工确认。**读和写用完全不同的安全模型** —— 这才是安全性来源，检查只是兜底。"
- **Q：多 Agent 有必要吗？**
  → "**大多数场景不需要。** 单 Agent + 工具能覆盖绝大多数需求，正确顺序是：单 Agent → 工具多到互相干扰 → 才拆。本项目用**客观判据**分流，简单问题不建图。"
- **Q：这是 agent 还是 workflow？** ⚠️ 必须诚实
  → "**workflow。** LLM 只在固定几处被调用，**从不自己决定下一步走向**，走向是图结构定死的。按 Anthropic 的分类它是 workflow 不是 agent。**别包装成自主 agent** —— 懂行的一问'谁决定下一步'就露。"
- **Q：如果重做一次，你会改什么？**
  → 准备一个真的：**"先把 checkpointer 换成持久化的（`SqliteSaver`），再补一个独立 eval set。"** 前者决定能不能真的上线（现在 `MemorySaver` 重启即丢，人机协同的断点恢复只在进程活着时成立）；后者决定改 prompt 时知不知道自己在变好还是变坏。

### ⚠️ 避坑

- **别只念组件名** ——"用了 LangGraph + RAG + 向量库"没有信息量。
- **别把架构全说成自己的** —— 见上"划界"。
- **别讲满 10 分钟** —— 先给骨架（**开场 → 三层洋葱 → 升华**），留钩子让面试官追问。
- **别全是定性描述** —— 至少给 3 个数字（10 政策 / 34 chunk / 6 表 / 20 条测试 / 3-of-3）。
- **⚠️ 别照搬生产模板** —— 这是 POC，**没有 QPS / 微服务 / Nginx / 线上慢 SQL**。
  编这些撑不过一句追问；**换成 nlp 的真实对应物**（数据规模 / 单体取舍 / 循环上限与熔断 / 机制级优化）。

## 7. 架构能力：为什么要搞成那个样子？真的有这个需求吗

### 考点

不是"能不能画架构图"，而是**能不能做取舍并说清代价**。
问"真的有这个需求吗"的时候，他测的是**你会不会过度设计** —— 这是高级岗和初级岗的分水岭。

### 答案骨架

1. **架构 = 约束下的取舍**。先说约束（规模、并发、团队、时间、可维护性），再谈方案。
2. **每选一个方案，都说出放弃了什么**。说不出代价的方案，通常是你没想过。
3. **主动指出哪些设计超出了真实需求** —— 这是加分项，不是减分项。

### 本项目的说法

从"代价"这一栏讲，三个现成的例子：

| 设计 | 换来了什么 | 代价 |
|---|---|---|
| 波次调度用**已完成集合反推**，不维护波次游标 | 规避状态同步类缺陷（这类 bug 只在并发下暴露） | 已完成集合只增不减 → **无单任务回退能力** |
| 简单问题走**单 Agent 直答**，不起图 | 省一次 DAG 的 token 与延迟 | 分类错了会走错路（故解析失败降级为 simple） |
| 写操作走**固定访问方法**而非 Text-to-SQL | 安全性 —— 写语句不由模型构造 | 写操作的形态必须能穷举 |

### ★ "真的有这个需求吗" —— 诚实的答案是：有过度设计

本项目 **5 条人工介入通道有 3 条是死的**，**参数校验整条链路从不执行**，
`user_id` 字段从没被设置过（日志、审计全记成 `"anonymous"`）。

这些不是要藏起来的部分，是**能主动讲出来的部分**。
能指出自己的过度设计，比假装每处设计都必要更可信 —— 而且证明你**真的读完了自己的代码**。

### 追问怎么接

## 16. RAG 文档怎么切？为什么这么切？数据量扩大怎么办

### 考点

chunking（分块）是**最影响 RAG 效果的一环**，且没有万能参数。他要听的是**你的推理过程**，不是某个数字。

### 本项目的实际参数

[init_vector_db.py:251-271](tools/scripts/init_vector_db.py#L251-L271)：

```python
RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", "。", "！", "？", ".", "!", "?", "，", ",", " ", ""],
    chunk_size=800, chunk_overlap=100
)
```

10 篇售后政策 → **34 chunk**（平均约 800 字/块）

### 为什么这么切（三条理由，都要能说出来）

1. **按语义边界优先，长度只是兜底**
   `separators` 从粗到细排列（段落 → 换行 → 句号 → 逗号 → 单字符）。
   `RecursiveCharacterTextSplitter` **优先在粗粒度分隔符处切**，只有超长才退到细粒度。
   所以切出来的块通常是**完整段落/句子**，不会从句子中间砍断。

2. **中文标点必须显式列进去**
   `。！？，` 是中文的断句点。**只用默认的英文 `.!?` 会让中文文档退化成按字符硬切** ——
   这是中文 RAG 最常见的坑之一。

3. **800 字 ≈「一条政策条款」的量级**
   一条售后规则（如"7 天无理由的起算与例外"）正好在这个量级。
   切太小 → 上下文不全，答不完整；切太大 → 命中后噪声多，且占满 prompt。

**`overlap=100` 存在的理由**：条款的意思常跨句（"除……之外，均可退货"）。
重叠 100 字保证**跨越切点的语义在至少一块里是完整的**。代价是存储与检索冗余。

### ★ 数据量扩大怎么办（追问重点）

**分四层答，顺序不能反 —— 先廉价后昂贵**：

| 层 | 手段 | 本项目现状 |
|---|---|---|
| 1 | **元数据过滤** —— 先缩小候选范围再检索 | 已有：`document_metadata.json` + `ALLOWED_DOC_IDS` 白名单 |
| 2 | **混合检索** —— 向量 + BM25 双路 | 已实现（RRF 融合） |
| 3 | **扩大召回 + 重排** —— 召回 top-20，rerank 到 top-3 | 已有开关（`use_rerank`），按 Agent 决定是否开 |
| 4 | **索引与分片** —— HNSW/IVF 参数调优、按业务拆 collection | **未做**：单 collection `knowledge_base` |

**再往上才是换向量库**（见第 20 条）。

> **⚠️ 不要一上来就说"数据量大了换 Milvus"。** 换库的运维成本最高，且通常**不是**瓶颈。
> 先做过滤和重排，两者都是纯应用层改动。

### 追问怎么接

- **Q：为什么是 800，不是 512 / 1024？**
  → 没有理论最优值，是**按语料形态定的**。判据是"一个检索单元的完整语义"。
    诚实的补充：**我没有做过切分参数对召回率的 A/B 实验，这是该补的**。
- **Q：怎么知道切得好不好？**
  → 用真实问题测 **top-1 命中率**。本项目 6 个真实售后问题，top-1 全部命中正确文档，分数 0.575~0.827（阈值 0.45）。

## 17. ★ 为什么普通 pipeline 不行？ ⚠️ 陷阱

### 考点

表面问 pipeline 的局限，**实际测你会不会过度设计**。
答"pipeline 不行所以要多 Agent"就上钩了 —— 那是"因为 multi-agent 火所以我用"的另一种说法。

### 答案骨架（先否定问句的前提）

> **pipeline 往往够用。绝大多数生产场景就该用 pipeline。**
> 要先能说出"什么时候不够"的**具体信号**，再决定上不上更复杂的编排。

### 本项目的说法

**这个项目没有抛弃 pipeline，而是分流**：

```
complexity_classifier ─┬─ simple  → router → 单个 Agent      ← 这就是 pipeline
                       └─ complex → planner → 任务图(DAG)
```

判据是 LLM 二分类：「是否需要**多个不同类型**的 Agent 协作」。
且**解析失败时降级为 simple** —— 宁可少拆，不可拆错。

### pipeline 真正不够的信号（有这些才上 DAG / 多 Agent）

1. **步骤数事先不定** —— 需要边做边决定下一步（pipeline 的步骤是写死在代码里的）
2. **子任务依赖是动态的** —— 例如"先查到订单，才知道该查哪个政策族"
3. **需要不同知识域 / 工具集协作**，且它们之间要交换**结构化中间结果**
4. **需要人在环中的断点** —— 审批发生在流程**中间**，而不是末尾

### ★ 要主动说的反面

多 Agent 的真实代价是**延迟、token、状态同步复杂度、调试难度**（本项目就吃了状态同步的亏）。
所以正确顺序是：**单 Agent + 工具 → 工具多到互相干扰 → 才拆多 Agent**。

### 追问怎么接

- **Q：那你项目里 DAG 真的用上了吗？**
  → 用上了，但**复杂路径是少数**。诚实说：demo 里大部分问题走 simple 路径；
    complex 路径的价值在于**能力存在且可验证**。
- **Q：怎么判断分类器准不准？**
  → **现在没测，这是缺陷**。该做的是构造一批标注好"该走哪条路"的样本算准确率。

## 18. LangGraph 的状态怎么存

### 考点

checkpointer 机制 + **状态被并发写入时的语义**。后者是区分"用过"和"读懂过"的地方。

### 答案骨架（三层）

#### ① 状态是「共享字典 + 归并函数」

`StateGraph` 的 state 是一个 TypedDict，节点通过**返回一个 dict** 来更新它。
核心概念是 **reducer（归并函数）**：

- 挂了 reducer 的字段是**追加**（`Annotated[List, operator.add]`）
- **没挂的是"后来者覆盖前者"** —— 同一次超步里多个节点写同一个没挂 reducer 的字段，只有最后一个生效

本项目的实际用法：

| 字段 | reducer | 为什么 |
|---|---|---|
| `messages` | `add_messages` | 消息必须追加 |
| `agent_results` | `operator.add` | 多个 Agent 并行，都要保留 |
| `write_operations` | `operator.add` | 多个写操作都要登记 |
| `completed_task_ids` | `operator.add` | 只增不减，用来推就绪 |
| 其余字段 | 无 | 覆盖语义 |

> **★ 这是最容易漏的知识点**：并行扇出时同一个字段被多个分支写，
> **忘了挂 reducer 结果会随机丢失** —— 而且**只在并发下复现**，串行测永远测不出来。

#### ② 存哪里：checkpointer

本项目用 `MemorySaver` —— **存在进程内存里**。用 `thread_id` 做会话隔离。

#### ③ ★ 关键推论

`interrupt_before`（人工介入断点）能工作，**正是因为图状态还在进程内**。
换成无状态服务、或进程一重启，状态就没了，`/resume` 无从恢复。

**生产建议**：换 `SqliteSaver` / `PostgresSaver`。这是「能 demo」和「能上线」的分界线之一。

### 追问怎么接

- **Q：长期记忆呢？**
  → **是另一套，不要混答**。图状态 = 一次请求的执行过程；长期记忆 = 跨会话的事实。
    本项目长期记忆走 `database/memory.db`（结构化沉淀 + 治理），不是 checkpointer。
- **Q：状态太大怎么办？**
  → 本项目 `messages` 单条截断 8000 字。而且发现 `messages` 是**"只写不读"的死字段**
    （Agent 实际读的是 `context["history"]`）—— 说明状态里可能有过期字段在白白占内存。

## 19. AI 的结果怎么验证

### 考点

LLM 输出不可信，怎么建立信任。**这题几乎必问。**

### 答案骨架：分四层，从确定到不确定

| 层 | 验什么 | 手段 | 本项目 |
|---|---|---|---|
| 1 格式 | 输出结构对不对 | schema 校验 | 参数校验器 `TaskSchema`（**但见下方诚实说明**） |
| 2 事实 | **声称的事有没有真发生** | 比对执行记录 | ★ 防幻觉兜底 `_verify_write_claim` |
| 3 质量 | 答得好不好 | LLM 自评 + 阈值 | evaluator 三维加权（0.4 / 0.3 / 0.3） |
| 4 业务 | 业务规则满不满足 | 领域校验 | ★ 三重校验（订单存在 / 归属正确 / 状态允许） |

### ★ 最能体现深度的一点：第 2 层和第 3 层性质完全不同

- **第 3 层（质量评分）是主观的、LLM 自评的** —— 它只能说"答得好不好"
- **第 2 层（防幻觉）是客观的、可判定的** —— 「**声称办过事，就必须本轮真调用过写工具**」

幻觉分两类：**幻觉知识**（答错，用户自己能判断）和**幻觉动作**
（让用户以为一件事办了而实际没办，后果严重得多）。
后者只能靠**"拿声称比对执行记录"**来防 —— 前提是**系统保留了执行记录**。
这也解释了为什么不能靠提示词让模型"别说谎"，而必须在**代码层**再核一遍。

### ★ 诚实说明（面试加分）

第 1 层的参数校验在本项目里**整条链路从不执行** —— 被一道守卫挡死：
「Agent 返回纯文本（非 dict）→ 跳过字段校验」，而契约就是 `handle() -> str`，
**守卫永远触发**。连带 `upstream_retry` / `parameter_retry_count` 全是死机器。

**能说出"我这层实际没在工作"，比声称四层全在跑更可信。**

### 追问怎么接

- **Q：质量评分能信吗？LLM 自评本身不也不可靠？**
  → 对，所以它是**相对判据而非绝对判据**：配合**硬上限配额**（迭代次数）强制收敛，
    且三个维度各有独立的否决线（单项 <6 分即触发重跑）。
- **Q：重跑就能变好吗？**
  → **必须带具体反馈**。不带反馈的重跑 = 重新掷一次骰子，大概率还是同一个差答案。
    所以 evaluator 必须产出 `feedback` 并拼回 query —— 这是"自我修正"能不能生效的分水岭。

## 20. 向量数据库怎么选？为什么是 Chroma

### 考点

**选型判据**，不是背参数。

### 答案骨架：先给判据，再用判据解释选择

判据维度：① 规模（10 万 / 千万 / 亿）② 运维成本（嵌入式库 vs 分布式服务）
③ 过滤能力（metadata filter）④ 是否要事务 / 与业务表 join ⑤ 混合检索是否内置

| 库 | 定位 | 什么时候选 |
|---|---|---|
| **Chroma** | 嵌入式（`PersistentClient`，无服务进程） | **POC / 单机 / 数据量小**，pip 装完就能跑 |
| FAISS | 是**库**不是服务，ANN 最快 | 只要最近邻，元数据与持久化自己管 |
| **Qdrant** | 独立服务，Rust，**过滤强、性能好** | 生产、要复杂过滤、要水平扩展 |
| Milvus | 分布式，超大规模 | 亿级向量、有专门运维 |
| pgvector | PostgreSQL 扩展 | **已有 PG、要事务一致性、要和业务表 join** |
| Pinecone 等云托管 | SaaS | 完全不想运维 |

### 本项目的选择理由（要能自圆其说）

1. **零服务依赖** —— 目标是"clone 下来就能跑"，`chromadb.PersistentClient` 不需要起任何进程
2. **数据量小** —— 10 篇文档 / 34 chunk。**这个量级上选型没有性能意义**
3. **Python 原生 + LangChain 生态默认** —— 少写胶水代码
4. 本地文件持久化，无需额外运维

### ★ 主动说出取舍（加分部分）

- **不足**：元数据过滤能力弱于 Qdrant —— 本项目退化成用 `ALLOWED_DOC_IDS` 白名单**在应用层过滤**
- **不足**：单机、无分布式，数据量上去会撞墙
- **如果重做**：到百万级或要复杂过滤 → **Qdrant**；本来就有 PG 且要事务 → **pgvector**

### 追问怎么接

- **Q：换库要改多少？**
  → 取决于**检索有没有封装在接口后面**。本项目 `rag_core/` 下 `chroma_store` 与
    `hybrid_retriever` 是分开的，换库主要改 store 层，检索策略层不动。
- **Q：为什么不直接用 FAISS？**
  → FAISS 只管向量，**元数据、持久化、删除都要自己实现**。Chroma 把这些包好了，
    代价是性能上限和规模上限。

## 21. ★ 为什么要多 Agent？ ⚠️ 陷阱

### 考点

和第 17 条配对。测你是不是"因为 multi-agent 火所以用"。

### 答案骨架（先否定问句的前提）

> **大多数场景不需要多 Agent。** 单 Agent + 工具能覆盖绝大多数需求。
> 要先问"单 Agent 哪里不够"。

### 本项目的说法

本项目用**客观判据**决定要不要多 Agent，而不是默认多 Agent：

- `complexity_classifier` 做二分类，判据是「是否需要多个**不同类型**的 Agent 协作」
- 简单问题 → 单 Agent 直答（**不建图**）
- 复杂问题 → 才拆任务图

### ★ 必须如实说的一个判断（最能拉开差距）

这个项目的 agent 程度是「**LLM 作为节点**」而非「**LLM 作为决策者**」。
LLM 只在固定几处被调用（分类、规划、选 Agent、生成 SQL、评分），**从不自己决定下一步走向** ——
走向是**图结构定死的**。

按 Anthropic《Building effective agents》的分类，它更接近 **workflow** 而不是 **agent**。
**不要把它包装成"自主 agent"** —— 懂行的面试官问一句"谁决定下一步"就露。

### 多 Agent 的真实代价

1. **延迟与 token 翻倍** —— 每个 Agent 至少一次 LLM 调用
2. **状态同步复杂度** —— 本项目吃过的亏：`depends_on` 最初只实现了"执行顺序"，
   字段级数据交接**从未接线**
3. **调试难度** —— 跨 Agent 的问题很难定位
4. **语义陷阱** —— 共享状态 + 单向无环 DAG **不支持"带着中间结果回到同一个 Agent"**，
   而这种形态在多 Agent 里很常见

### 什么时候才真的需要

- 不同 Agent 需要**不同的工具集/知识库**，放一起会互相干扰（工具太多 → 选择错误率上升）
- 任务能自然拆成**有依赖的任务图**，且拆解本身可以交给 LLM
- 每个 Agent 需要**不同的上下文/提示词策略**

### 追问怎么接

- **Q：那你这算 agent 还是 workflow？**
  → 诚实答：**workflow**。它有条件分支和循环（质量重试环），但**决策权在图，不在 LLM**。
- **Q：那多 Agent 这部分有意义吗？**
  → 有意义的地方在于**能力边界被验证了**（波次调度、参数交接、人在环中、断点恢复），
    而不是"用了多 Agent 所以先进"。

## 23. 怎么验证 AI（系统级评测）

### 考点

和第 19 条不同：第 19 条问**运行时**怎么验证单次输出；这条问**上线前你怎么知道这东西是好的**。

### 答案骨架：分三层

| 层 | 是什么 | 本项目 |
|---|---|---|
| **确定性测试** | 不调 LLM，纯逻辑与数据层 | 第一段：外键约束、三重校验、防幻觉、知识图谱推导、白名单（**秒级**） |
| **端到端测试** | 调真实 LLM，测全链路 | 第二段：路由分派、政策问答、订单查询、多轮指代、写操作链路（**约 3 分钟**） |
| **可观测** | 线上能追查 | LangSmith 链路追踪 + 问答日志 |

### ★ 为什么要分两段（最有价值的说法）

**LLM 调用又慢又不确定。** 如果把数据层逻辑和 LLM 测在一起，
一个失败你分不清是**逻辑错了**还是**模型随机**。

**分开之后：第一段是秒级的确定性回归，第二段才承担不确定性。**
退出码 0 就能直接接 CI —— 反馈速度是测试设计的核心指标之一。

### ★ 必须主动说的坑（本项目真实踩过）

`test_14` **依赖模型的随机决策** —— 模型有时先要求用户补凭证再提交（这是**合理行为**），
但测试断言"必须写" → **偶发失败**。

**教训**：LLM 测试要么**消除随机性**（固定 prompt、mock 模型、固定 seed），
要么**把断言放宽到"行为区间"**，绝不能断言模型的某次具体选择。
**这是 AI 测试和传统测试最大的区别。**

### 追问怎么接

- **Q：怎么测"答案质量"？**
  → 现在靠 evaluator 的 LLM 自评（主观）。更硬的做法是**构造带标准答案的 eval set 算准确率** ——
    本项目"6 个真实问题 top-1 命中率"就是这种思路的雏形。
- **Q：模型换了怎么知道没退化？**
  → 需要**固定的 eval set + 回归基线**。本项目第二段测试扮演这个角色，
    但它依赖真实 LLM，因此有波动 —— 要更稳就得把关键路径的模型输出录下来做回放。

## 24. 状态机

### 考点

概念 + 为什么用它 + 和 pipeline/DAG 的区别 + **它的经典陷阱**。

### 答案骨架

- **状态机** = 一组**状态** + 一组**转移**（由事件/条件触发）。
  核心价值是**行为的确定性**：给定当前状态和输入，下一步可预测。
- **和 pipeline 的区别**：pipeline 线性无分支；状态机可以有**分支、循环、并行**。
- **和 DAG 的区别**：**DAG 无环**，所以"重试/循环"表达不了；
  状态机允许回到之前的状态 —— 代价是**必须自己保证能终止**。

### 本项目的说法：LangGraph 的 `StateGraph` 就是显式状态机

| 状态机概念 | LangGraph 对应 |
|---|---|
| 状态 | `EnhancedGraphState`（TypedDict） |
| 转移函数 | 节点 |
| 转移条件 | 条件边（`route_by_complexity` / `check_quality`） |
| 状态持久化 | checkpointer（`MemorySaver`） |
| 外部事件 | `interrupt_before` + `/resume` |
| 循环 | 质量重试环（`evaluator` → 回到入口），**有迭代配额上限** |

### ★ 状态机的经典陷阱 —— 本项目最有价值的教学点

> **「图上画了这条边」≠「这条边可达」。**

`human_intervention_check` 有 **5 条转移通道，只有 2 条实际可达**：

| 通道 | 转移条件 | 为什么不可达 |
|---|---|---|
| 1 | `plan["complexity"] == "complex"` | **全项目从没有往 `plan` 里写过 `complexity` 这个键** → 条件恒为假 |
| 5 | `not critic_passed` | `critic_passed` **恒为初始 `True`**（唯一会改它的节点从未进图） |

两条都**不报错、不打日志**，**静默跳过**。
**光看转移逻辑是对的** —— 必须去追"条件里那个值从哪来"。

**→ 通用教训（可迁移）**：状态机的**每个转移条件所依赖的每个输入变量，
都要确认存在写入方**。可做成一条检查：
对条件里出现的字段 grep 它的写入点，**写方为零 = 该转移不可达**。

### 追问怎么接

- **Q：怎么保证状态机不会卡死？**
  → 两个机制：① 波次调度的就绪判定用"已完成集合反推"，而**已完成只增不减 → 必然终止**；
    ② 质量重试环有**迭代配额上限**。
    **任何带环的状态机都必须有配额**，把终止条件交给 LLM 判断等于没有终止条件。
- **Q：状态机 vs 事件驱动？**
  → 状态机通常是**单个请求内的编排**（本项目：一次请求跑完一张图）；
    事件驱动是**长驻服务**（worker + 队列 + 重试 + 死信），本项目**没有**这一层。
