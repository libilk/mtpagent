# 语义缓存与RAG系统性能优化

## 概述

RAG系统在生产环境中面临的最大挑战之一是响应延迟。一次完整的RAG调用包含Embedding计算、向量检索、BM25检索、重排序、LLM生成等多个环节，总延迟可达3-10秒。通过多级缓存策略，可以将重复或相似查询的响应时间降低到毫秒级。

---

## 一、三级缓存架构

### 第一级：语义缓存（Semantic Cache）

基于查询Embedding的相似度判断是否命中缓存：
- **原理**：计算新查询与缓存中已有查询的Embedding余弦相似度
- **命中条件**：相似度 > 0.95（可调整）
- **缓存内容**：查询文本 + 检索结果 + 生成答案
- **优势**：即使用户换了措辞，只要语义相同就能命中

示例：
- "RAG系统怎么优化" 和 "如何提升RAG系统性能" → 语义相似度0.96 → 命中缓存

### 第二级：检索缓存（Retrieval Cache）

缓存查询到文档ID的映射：
- **Key**：查询文本的哈希值
- **Value**：文档ID列表 + 分数
- **TTL**：1小时（知识库更新后自动失效）
- **作用**：跳过Embedding计算和向量检索，直接获取文档

### 第三级：LLM缓存（Generation Cache）

缓存LLM的生成结果：
- **Key**：查询文本 + 检索上下文的哈希值
- **Value**：生成的答案文本
- **TTL**：24小时
- **注意**：上下文变化时缓存失效（同一问题检索到不同文档）

## 二、Redis缓存实现

### 为什么选择Redis

- **高性能**：单节点10万+ QPS，延迟 < 1ms
- **数据结构丰富**：String（答案缓存）、Hash（元数据）、Sorted Set（LRU淘汰）
- **TTL支持**：自动过期，无需手动清理
- **持久化**：RDB/AOF双重持久化，服务重启不丢缓存

### 降级策略

当Redis不可用时，系统自动降级：
- **降级到内存缓存**：使用Python dict + LRU淘汰策略
- **限制缓存大小**：内存缓存最多存储1000条
- **无缓存兜底**：直接执行完整RAG流程，性能下降但功能不受影响

## 三、性能优化策略

### Embedding优化

- **批量Embedding**：将多个文本合并为一次API调用
- **Embedding预计算**：文档入库时预计算，查询时只需计算查询的Embedding
- **降维压缩**：使用PCA或量化方法减少向量维度，降低存储和计算成本

### 检索优化

- **预过滤**：利用元数据先缩小搜索范围，再执行向量检索
- **近似最近邻（ANN）**：使用HNSW等索引加速，接受微小精度损失
- **并行检索**：向量检索和BM25检索并行执行

### LLM调用优化

- **流式输出（Streaming）**：使用SSE流式推送，用户无需等待完整生成
- **模型选择**：简单查询用小模型（快+便宜），复杂查询用大模型（准+贵）
- **Token控制**：压缩上下文长度，减少输入Token数量
- **提前终止**：检测到答案已完整时提前停止生成

## 四、性能基准与目标

| 指标 | 无缓存 | 命中语义缓存 | 命中检索缓存 | 目标 |
|------|--------|-------------|-------------|------|
| 总延迟 | 3-8秒 | <100ms | 1-3秒 | P95 < 3秒 |
| Embedding耗时 | 200-500ms | 0ms | 0ms | - |
| 向量检索耗时 | 50-200ms | 0ms | 0ms | - |
| BM25检索耗时 | 10-50ms | 0ms | 0ms | - |
| LLM生成耗时 | 1-5秒 | 0ms | 1-5秒 | - |
| API调用成本 | 满额 | 0 | 仅LLM | 缓存命中率>40% |

### 缓存预热

系统启动时预热高频查询：
- 从历史日志中提取Top 100高频查询
- 批量执行检索和生成，填充缓存
- 预热完成后才对外提供服务
