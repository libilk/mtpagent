# LLM提示工程与RAG系统中的Prompt优化

## 概述

提示工程（Prompt Engineering）是影响LLM输出质量的关键因素。在RAG系统中，Prompt不仅用于最终的答案生成，还贯穿查询改写、意图识别、任务规划等全链路。本文总结RAG场景下的Prompt设计原则和实战技巧。

---

## 一、RAG系统中的Prompt类型

### 1. 检索阶段Prompt

**查询改写Prompt**：将用户原始问题转化为更适合检索的形式
```
你是一个查询优化专家。请将用户的口语化问题改写为适合知识库检索的规范化查询。
要求：保留核心意图，补充必要的上下文关键词，去除口语化表达。

用户问题：{query}
改写后的查询：
```

**HyDE Prompt**：生成假设性文档用于语义检索
```
请针对以下问题，写一段可能出现在知识库文档中的回答段落（200字以内）。
不需要完全准确，重点是覆盖相关的专业术语和概念。

问题：{query}
假设性文档段落：
```

### 2. 生成阶段Prompt

**RAG答案生成Prompt**（核心模板）：
```
你是一个专业的问答助手。请根据以下检索到的参考资料回答用户问题。

要求：
1. 只使用参考资料中的信息回答，不要编造内容
2. 如果参考资料不足以回答，请明确告知
3. 引用具体的信息来源

参考资料：
{context}

用户问题：{query}
回答：
```

### 3. Agent阶段Prompt

**ReAct推理Prompt**：
```
你是一个智能助手，拥有以下工具：
{tools_description}

请按照 Think → Act → Observe 的模式解决用户问题：
- Think: 分析当前情况，决定下一步行动
- Act: 选择并调用合适的工具
- Observe: 分析工具返回的结果

用户问题：{query}
```

## 二、Prompt设计核心原则

### 1. 结构化与角色设定

- 明确角色："你是一个XXX专家"
- 任务边界："只使用参考资料回答"
- 输出格式："请以JSON/Markdown/列表格式输出"

### 2. Few-Shot示例

对于复杂任务，提供1-3个输入-输出示例比纯文字描述更有效：
- 示例应覆盖典型场景和边界情况
- 示例风格应与期望输出一致

### 3. Chain-of-Thought（思维链）

对于需要推理的任务，引导LLM逐步思考：
- "请一步一步分析这个问题"
- "先列出关键信息，再给出结论"

## 三、RAG特有的Prompt优化技巧

### 上下文窗口管理

LLM的上下文窗口有限，RAG Prompt需要权衡：
- **信息密度**：压缩检索结果，去除冗余内容
- **相关性排序**：最相关的文档放在最前面（"Lost in the Middle"问题）
- **分段处理**：超长上下文拆分为多次调用，最后合并

### 幻觉防控

RAG系统的核心价值是减少LLM幻觉，Prompt层面的防控措施：
- 明确指令："如果参考资料中没有相关信息，请回答'知识库中未找到相关内容'"
- 引用要求："回答时请标注信息来源"
- 置信度提示："如果不确定，请说明并给出置信度评估"

### 多轮对话上下文

在对话式RAG中，需要维护对话历史：
- 摘要记忆：对过长的对话历史进行摘要压缩
- 滑动窗口：只保留最近N轮对话
- 关键信息提取：从历史对话中提取对当前问题有帮助的实体和背景

---

## 四、Prompt与RAG质量的关系

| 环节 | Prompt质量影响 | 优化方向 |
|------|---------------|----------|
| 查询改写 | 直接影响检索召回率 | 增加领域术语，消歧义 |
| 意图识别 | 决定路由到哪个Agent | Few-shot示例覆盖更多意图类型 |
| 答案生成 | 决定最终回答质量 | 严格限定信息来源，防止幻觉 |
| 质量评估 | 影响评估准确性 | 明确评分维度和评分标准 |
