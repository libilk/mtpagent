# 术语表 —— 英文词统一口径

> **这份表不负责解释代码，只负责「同一个英文词，全项目译成同一个中文」。**
> 具体解释仍然写在代码里（术语首次出现处的注释），这份表是查口径用的。
>
> 建立于 2026-09-19。起因：读代码时"有的能读懂、有的读不懂"，逐文件加标注时
> 必须有唯一口径，否则同一个 `evaluator` 在 10 个文件里会有 10 种译法。
>
> **覆盖范围**：`nlp/` 下全部 85 个 `.py` 文件已按本表完成标注（2026-09-19）。
> 铺开过程中遇到的新词已补录进下表 —— 所以这份表是**全项目实际用到的词**，
> 不是凭印象列的清单。词条按 A~H 分类，不确定某个词在哪类就从上往下扫一遍。

## 怎么用

1. **读代码卡住时** —— 按词查这里的「统一译名」和一句话解释，再回代码看上下文。
2. **改代码时** —— 注释里要提某个英文词，译名用本表的，别另起一个。
3. **写新文件时** —— 术语首次出现处标一次（见下方「标注约定」）。

## 标注约定

| 规则 | 取值 |
|---|---|
| 标注位置 | 同一术语**在同一个文件里首次出现处标一次**，后面重复出现不再标 |
| 标注形式 | 注释/文档字符串里：`evaluator（评估器）`；代码标识符/字符串用行尾 `#` 注释 |
| 译名来源 | 本表。表里没有的新词，先加进本表，再统一使用 |
| 硬约束 | **只加注释和文档字符串，不改任何可执行逻辑** —— 改动后用「剥离注释比对 AST」验证（做法见 [idea.md](idea.md)） |
| 注释内容 | 说明**为什么**和**是什么机制**，不复述代码在做什么 |

## A. 编排与图（LangGraph）

| 英文 | 统一译名 | 一句话解释 |
|---|---|---|
| LangGraph | 图编排框架 | 把多步流程画成图的框架：节点干活，边决定下一步走谁 |
| node | 节点 | 图上一个干活的函数 |
| edge | 边 | 决定"这一步做完走谁" |
| conditional edge | 条件边 | 不写死下一个节点，调用函数、用它的返回值查映射表来定 |
| START / END | 虚拟起点 / 终点 | 图的入口与出口标记，本身不是节点 |
| state | 状态 | 全图共享的数据字典，节点靠读它、往它里写返回值来传数据 |
| reducer | 归并函数 | 声明同一字段被多个节点并发写入时怎么合并（如 `operator.add` 累加） |
| Annotated | 类型标注 | 把 reducer 挂到某个字段上的写法，如 `Annotated[List, operator.add]` |
| Send | 分发指令 | "把这份数据送给某个节点"，用于一个节点扇出成多个并行分支 |
| DAG | 有向无环图 | 有依赖顺序、且不能绕回自己的任务图 |
| fan-out / fan_out | 扇出 | 一个节点同时把任务发给多个下游，并行执行 |
| wave scheduler | 波次调度 | 有依赖的 DAG 不能全并发，每轮只发"依赖已全部完成"的那批 |
| checkpointer | 检查点 | 每走完一步就把 state 存一份快照，暂停/恢复全靠它 |
| MemorySaver | 内存存档器 | 内置 checkpointer，快照存在内存里，进程重启即丢 |
| interrupt_before | 执行前中断 | 走到某节点之前先停下，把控制权交回调用方 |
| checkpoint | 检查点快照 | 某个时刻 state 的存档 |
| compile | 编译 | 把"画好的图纸"变成能真正执行的图 |
| thread_id | 会话 ID | 隔离不同对话窗口/用户的记忆，互不串味 |
| node name | 节点名 | 连边时引用的字符串，必须和 add_node 时一致 |
| mapping | 映射表 | 条件边函数"返回值 → 节点名"的对照表；两边必须一致，没有类型检查兜底 |
| partial update | 部分更新契约 | 节点只返回"要改的字段"，不是返回整个 state |
| fail-open / fail-closed | 出错放行 / 出错拦下 | 校验环节出错时，是放过还是挡住。评审类环节多选放行，免得卡死主流程 |

## B. 编排角色（本项目的各个节点）

| 英文 | 统一译名 | 一句话解释 |
|---|---|---|
| complexity_classifier | 复杂度分类器 | 判断问题该走简单路径还是复杂路径 |
| router | 路由器 | 简单问题：挑一个最合适的 Agent |
| planner | 规划器 | 复杂问题：拆成带依赖关系的任务列表 |
| aggregator | 聚合器 | 把多个 Agent 的结果汇总成一份 |
| evaluator | 评估器 | 最终质量把关（相关性/完整性/准确性），不过关就打回重试 |
| critic | 评审 | **校验任务衔接是否合理** —— 是"这段输出能不能接上后续任务"，不是给输出打分 |
| duplicate_detection | 重复检测 | 结果和之前重复就没必要再重试，直接熔断 |
| parameter_validator | 参数验证器 | 检查上游输出的字段够不够下游用，只查字段、不调 LLM |
| upstream_retry | 上游重试 | 字段缺了，把缺字段的那个上游 Agent 重跑一遍 |
| parameter_aligner | 参数对齐器 | 按 `parameter_mapping` 从上游结果里提取、补齐下游要的入参 |
| human intervention | 人工介入 | 流程暂停，等真人确认后再继续 |
| retry | 重试 | 质量不达标就回头再跑 |
| iteration | 迭代轮次 | 当前是第几轮重试 |

## C. Agent 与工具

| 英文 | 统一译名 | 一句话解释 |
|---|---|---|
| agent | 智能体 | 能自己决定调哪个工具、调几次的 LLM 程序 |
| tool | 工具 | Agent 可调用的函数，带名字和参数说明 |
| StructuredTool | LangChain 工具类 | 用 Pydantic Schema 声明参数，自动做参数校验 |
| args_schema | 参数结构 | 工具入参的类型声明 |
| Pydantic | 数据校验库 | 用类型标注定义数据结构，运行时自动校验 |
| ReAct | 推理-行动循环 | 想一步 → 调工具 → 看结果 → 再想，直到给出答案 |
| max_iterations | 最大迭代次数 | ReAct 循环的上限，防止无限调工具 |
| handle | 处理入口 | Agent 对外统一的方法签名 |
| registry | 注册中心 | Agent 名册，按名字取实例 |
| AgentProtocol | Agent 接口契约 | 规定 Agent 必须实现哪些方法 |
| Harness | 约束层 | 强制 Agent 符合统一接口的基础设施 |
| prompt | 提示词 | 喂给 LLM 的指令文本 |
| few-shot | 少量示例 | 在提示词里给几个例子，让模型照着做 |
| fallback | 降级兜底 | 主路径失败时退到备用方案 |
| stream / SSE | 流式输出 | 答案一个字一个字吐出来，不用等全部生成完 |
| StreamWriter | 流式事件写入器 | 节点执行过程中往外推进度事件的接口 |
| token | 词元 | LLM 处理文本的最小单位，也是计费与长度单位 |
| LLM | 大语言模型 | 底层模型本身（本项目是通义千问） |
| function calling | 函数调用 | 让 LLM 以结构化形式说"我要调哪个函数、参数是什么"的能力 |
| tool_calls | 工具调用请求 | 模型返回的"我要调这些工具"的结构化消息 |
| tool_call_id | 调用配对 ID | 把"这次调用"和"它的返回结果"配成一对的编号 |
| handle_tool_error | 工具报错处理 | 工具抛错时怎么收场（转成给模型看的错误文本，还是直接失败） |
| temperature | 采样温度 | 越低越确定、越高越发散；0 附近适合要结果的场景 |
| max_tokens | 最大生成长度 | 单次回答的 token 上限，防止话说不完被截断 |
| context window | 上下文窗口 | 模型一次能读进去的 token 总量上限 |
| factory | 工厂函数 | 返回一个函数的函数，用来预先把参数"焊"进去（闭包） |
| 泛型 / TypeVar | 类型变量 | 让函数对"元素类型"保持中立，调用时才确定 |
| Protocol / runtime_checkable | 协议 / 运行时可检查 | 只按"有没有这个方法"判断类型，不要求继承 —— 鸭子类型的实现方式 |
| 鸭子类型 | — | "走起来像鸭子就当它是鸭子"：不看继承关系，只看有没有实现该有的方法 |
| Enum | 枚举 | 一组固定的取值，避免字符串写错 |
| no-op | 空操作 | 什么都没做的实现（占位，或"这个分支故意不处理"） |
| hallucination | 幻觉 | 模型描述了没发生的事 —— LLM Agent 最危险的失败模式 |
| 指代消解 / anaphora | — | 把"它""那个订单"还原成具体指的是哪条数据 |
| invariant | 不变量 | 无论怎么执行都必须成立的约束 |
| P95 | 95 分位 | 100 次里第 95 慢的那次，用来衡量"最差体验"而非平均 |
| trace | 追踪 | 一次请求从头到尾的完整记录，用于排查每一步发生了什么 |
| 冷启动 | — | 进程刚起来、缓存还是空的那段时间，首个请求最慢最贵 |

## D. RAG 检索

| 英文 | 统一译名 | 一句话解释 |
|---|---|---|
| RAG | 检索增强生成 | 先检索资料，再让 LLM 基于资料回答 |
| chunk | 文本块 | 文档切分后的片段，检索的最小单位 |
| embedding | 向量化 | 把文本变成一串数字，语义相近的文本向量也相近 |
| embedder | 向量化模型 | 干向量化这件事的模型实例 |
| vector | 向量 | 文本的数字表示 |
| cosine similarity | 余弦相似度 | 比较两个向量方向有多接近，取值 0~1 |
| top_k | 取前 k 条 | 只保留得分最高的 k 个结果 |
| recall | 召回 | 从全库里把可能相关的捞出来这一步 |
| retriever | 检索器 | 负责召回文档 |
| BM25 | 关键词检索算法 | 按词频和稀有度打分，擅长精确匹配 |
| hybrid retrieval | 混合检索 | 向量检索 + 关键词检索一起用 |
| RRF | 倒数排名融合 | 把多路检索结果按排名倒数相加，融合成一个列表 |
| reranker | 重排序器 | 对召回结果做精排，把最相关的顶上来 |
| cross-encoder | 交叉编码器 | 把「问题+文档」一起送进模型打分，比向量更准但更慢 |
| HyDE | 假设文档嵌入 | 先让 LLM 编一个假答案，再拿它去检索 |
| Chroma / ChromaDB | 向量数据库 | 存向量并做相似度搜索的库 |
| doc_id | 文档 ID | 每篇文档的唯一标识 |
| metadata | 元数据 | 附在文档/向量上的结构化信息，用来过滤和分层 |
| score | 分数 | 相关性得分 |
| query | 查询 | 用户问的那句话 |
| context | 上下文 | 喂给 LLM 的参考资料 |
| citation | 引用溯源 | 答案里标出"这句来自哪篇文档" |
| Self-Consistency | 自洽性 | 同一问题生成多次，取多数一致的答案 |
| context compression | 上下文压缩 | 把检索到的长文档压短，省 token |
| precision | 精确率 | 捞回来的东西里，有多少是真的相关（召回是"该捞的捞到了没"） |
| multi-query | 多路检索 | 同一个问题换几种问法各检索一遍，再合并结果 |
| IDF / TF | 逆文档频率 / 词频 | BM25 的两个组成：词越稀有越有分量，出现越多越有分量 |
| tokenize / 分词 | — | 把句子切成词；中文要专门切（本项目用 jieba） |
| corpus | 语料库 | 拿来检索/训练的全部文本集合 |
| normalize | 归一化 | 把数值缩放到统一量纲，否则不同来源的分数量纲没法比 |
| HNSW | 近邻图索引 | 向量库里加速相似度搜索的索引结构，避免全量比对 |
| collection | 集合 | 向量库里的一个"表"，一组向量的容器 |
| distance metric | 距离度量 | 衡量两个向量有多近的方式（l2 欧氏 / ip 内积 / cosine） |
| LRU / FIFO | 最近最少使用 / 先进先出 | 缓存满了先淘汰谁：LRU 淘汰最久没用的，FIFO 淘汰最早进来的 |
| TTL | 存活时间 | 一条缓存/一条数据的有效期，过期即失效 |
| 指数退避 | exponential backoff | 失败后等 1s、2s、4s… 再重试，避免把对方打垮（本项目用 tenacity） |
| stub / 存根 | — | 只有方法签名、没有真实实现的占位代码：让调用点能跑通，但不是"功能在工作" |
| RRF | 倒数排名融合 | 合并多路检索结果：按排名的倒数相加，而不是把分数直接相加 |
| MRR | 平均倒数排名 | 正确答案排得越靠前分越高，衡量检索排序质量 |
| ROUGE | — | 衡量生成文本和参考答案重合度的指标 |
| Faithfulness | 忠实度 | 答案是否真的出自检索到的资料，而不是模型自己编的 |
| ground truth | 标准答案 | 人工认定的正确答案，用来对指标做基准 |

| Node.js / npm | — | JavaScript 运行时 / 它的包管理器；MCP Server 是 npm 包，装不上就用不了 |
| dry-run | 空跑 | 只打印"将要做什么"，不真的动手 —— 危险脚本的常用安全开关 |
| DPI | 每英寸点数 | 扫描/图片的分辨率，越高 OCR 越准也越慢 |
| TESSDATA_PREFIX / 语言包 | — | Tesseract 的识别数据目录；缺语言包时不会报错，只会识别出空文本 |
| pdfplumber / pytesseract | — | 解析 PDF 取文字 / 调用 Tesseract 的 Python 封装 |

## G. 测试

| 英文 | 统一译名 | 一句话解释 |
|---|---|---|
| fixture | 测试夹具 | 测试前准备好的前置数据/环境 |
| mock | 模拟对象 | 用假的替身顶掉真实依赖 |
| assert | 断言 | 断定"这里必须是这个值"，不成立就报错 |
| E2E | 端到端测试 | 从入口到出口完整跑一遍 |
| regression | 回归测试 | 改完之后重跑，确认没把原来好的弄坏 |
| FAIL vs ERROR | 断言失败 / 执行出错 | FAIL = 断言不成立（被测行为不对）；ERROR = 代码直接抛异常（测试自己坏了）。两者含义不同，别混看 |
| 正向证明用例 | — | 专门用来证明"某个设计真的起作用"的用例（如外键真拦住了臆造数据），区别于普通的"功能跑得通" |

## 附：术语的译名为什么这么定

两个原则，都是为了"看起来不费劲"：

1. **优先用中文习惯叫法，而不是字面直译。**
   例：`aggregator` 译"聚合器"而不是"汇总者"；`critic` 译"评审"而不是"批评家"。
2. **译名必须能在中文里独立成句。**
   `fan_out` 译"扇出"是因为中文里已有这个词（电路/流程设计的既有说法），
   而"扇出到多个分支"能直接读通；如果只想得到"分发"，会和 `Send` 撞义。

**最容易译错的一个是 `critic`** —— 字面看像"给输出打分"，实际是**校验任务衔接**
（[critic.py](langgraph_orchestrator/critic.py) 找的是下游任务）。
猜错的注释比没有注释更糟：读者会带着一个错误的模型继续往下读。
